# Feature Specification: Tools "This session / All time" and the Copilot CLI MCP list as the primary source

**Feature Branch**: `020-tools-all-time-and-mcp-cli-primary` (milestone 10)
**Created**: 2026-10-16
**Status**: Implemented (milestone 10; see tasks.md). Evidence tags: test: unit tests, sim: simulator driver `scripts/shots-m10.js`; nothing here was run against a real account (no credits). Changes spec 019 (MCP settings, FR-001, FR-003, FR-006, FR-007) and adds to its Tools view (FR-012, FR-013). Delta 2026-10-17 (issue #7): per-folder import from VS Code's `.vscode/mcp.json`, FR-020..FR-031 (`test:` mcp §9, `sim:` `scripts/shots-i7.js`).
**Input**: Vikram, two steering messages. (A) Tools view: toggle "This session" / "All time"; all-time counts are cumulative, kept on disk in the app's userData folder, survive restarts, are keyed by tool, MCP server and agent, and hold no secrets or arguments. (B) `~/.copilot/mcp-config.json` (the Copilot CLI list) is the primary MCP source: auto-loaded and shown in Settings and Tools with no separate configuration or import step; per-agent toggles stay; the app's own servers become optional extras, clearly labelled, and they exist **only per folder/workspace** (stored per folder, applied only to agents in it). There is no app-level global list of extras: the only global list is `~/.copilot/mcp-config.json`. Trust prompts for exact definitions stay.

## User scenarios

1. **I open Tools and see what happened this session, or ever.** A switch at the top: **This session** (as today: counts since the app started, per agent) and **All time** (cumulative since the first run, kept across restarts). The numbers are per tool and per MCP server, with "used by" per agent. A one-line note says since when All time counts and that it stores only tool names, server names, agent names and counts.
2. **My Copilot CLI servers just work.** I never configure anything in the app: the servers in `~/.copilot/mcp-config.json` (and the built-in GitHub server) are listed in Settings under "MCP servers" with their exact command or URL, and in Tools. The runtime loads them in every session. If I edit the file, the next time I open Settings or Tools it shows the new list. If the file is missing or malformed, the screen says so.
3. **Extras for one folder.** In a room's header (and from an agent's MCP dialog) I can open "MCP extras" for that folder: add a server that only agents in this folder get. It is clearly labelled "Extra, this folder only". Switching one on shows its exact command first (trust), and asks again if the definition changes. Another folder does not see it.
4. **Per-agent switches** work as before, over both lists.
5. **Servers I added in the old global list** (milestone 8) are not applied any more. They stay on disk, listed in a folder's extras dialog as "Old app-level servers (not applied)": **Move here** puts one into this folder (off, to be trusted again), **Remove** deletes it.

## Clarifications (2026-10-16)

- **Q: Is the CLI list trust-gated?** **Decided (Vikram, 2026-10-16): No. CLI-list servers (`~/.copilot/mcp-config.json` plus the built-in `github-mcp-server`) get no trust prompt, same as Copilot CLI.** They are in the user's own Copilot CLI config, the runtime starts them in every session anyway, and Settings shows the exact command or URL (never env or header values). A prompt that cannot stop the runtime would be theatre, and the only real gate (listing unconfirmed names in `disabledMcpServers`) would make them not work until confirmed, unlike the CLI. The trust prompt with exact-definition hashing (spec 019 FR-005) applies to **folder extras only**, the only servers Agent Durbar itself passes to a session. Tested: CLI-list entries carry no trust state (test-mcp §6).
- **Q: What does the on/off switch of a CLI-list server do?** What it did for "ambient" servers: it lists the name in `disabledMcpServers` for **new** sessions started by this app. It never edits the CLI file.
- **Q: Same name in the CLI list and in a folder's extras?** Refused when saving the extra ("already defined in the Copilot CLI list"): a name must mean one server. If the CLI file later gains a clashing name, the extra is skipped for sessions and Settings says so.
- **Q: What is a folder/workspace key?** The saved-folder key of spec 006: the `.code-workspace` file when the agent was added from one, else the folder path. An agent gets the extras of its own key only.
- **Q: What is the agent key of an all-time count?** `"<agent name> · <folder name>"` (folder base name only, no path). Agent names are the persona names, so the same name in two folders is two entries; a counted agent can reappear after a restart with the same key. Counts of agents you no longer have stay (they are history); **Reset** clears them.
- **Q: VS Code `mcp.json` and "Import"?** The import screens are removed: the CLI list needs none, and a global import has no scope any more. A per-folder import from VS Code's file was a `[KNOWN GAP]` at milestone 10; it is specified in the 2026-10-17 delta below (FR-020..FR-031, issue #7).
- **Q: Persisted when?** Counters are written at most every 2 s after a change and on quit; a crash loses at most that window.

## Changes

### 2026-10-17: per-folder import from VS Code's `.vscode/mcp.json` (issue #7; FR-020..FR-031, T013..T020)

**Why.** Many folders already describe their MCP servers for VS Code. Typing them again in the extras form is slow and error-prone. The global import screens were removed on purpose (a global import has no scope any more), so the import comes back **only per folder**, in the folder's extras screen, and only as a way to fill the same per-folder extras that the form fills. It never adds anything to the global list and never touches `~/.copilot/mcp-config.json` (the CLI list stays the only global list, read-only).

**Clarifications (`/speckit.clarify`, 2026-10-17).** No human was available to answer, so each open question below got the **safest** answer, recorded here and in the PR so Vikram can overrule it.

- **Q: Which file is read?** `<folder>/.vscode/mcp.json` of the folder behind the extras screen. A workspace (`.code-workspace`) has several folders: the file of each of its folders is read (at most 8 folders), and the preview says which folder each server comes from. VS Code's user-level `mcp.json`, `settings.json` and workspace-file `mcp` blocks are not read (`[KNOWN GAP]`). The renderer never sends a path: it names the folder key (checked against the agents in the office), and the main process derives the file paths.
- **Q: Are imported servers on?** **Never.** Each import creates an extra of this folder that is **off and untrusted**. The first switch-on shows the existing trust dialog with the exact command or URL (spec 019 FR-005); a later change of command/args/URL/cwd/type drops trust again. Nothing is started by importing.
- **Q: Are the boxes in the preview ticked?** **No.** Nothing is ticked by default; "Select all importable" is one click. Entries that cannot be imported have a disabled box and a reason.
- **Q: What about secrets (`env`, `headers`)?** The preview shows **keys only, values masked** (`••••••`, or "no value"). Values never reach the renderer, logs, toasts or screenshots. A **literal** value is copied by the main process into the same secret store typed values use (encrypted with the OS store when available, otherwise kept in memory for this run only; spec 019 FR-002), exactly like the add form. A value that contains a `${...}` reference (for example `Bearer ${input:token}` or `${env:TOKEN}`) is **not copied and not resolved**: the key is imported with no value, the server shows "needs secrets" and does not start until the user enters it in the edit form.
- **Q: What do we do with `inputs` (VS Code asks for a value on first use)?** **Agent Durbar never prompts for, stores or resolves VS Code inputs.** The `inputs` array is only read to name the ids in a note. A `${input:id}` in `env`/`headers` leaves that value empty (above). A `${input:id}` (or any other unresolved `${...}`) in `command`, `args`, `url` or `cwd` makes the entry **not importable** (disabled box, reason "needs a value VS Code asks for; add it by hand"), because arguments and URLs are stored in clear and shown in the trust dialog, so a guessed or literal `${...}` would run something different from what the user reviewed. Only `${workspaceFolder}` is resolved (to the absolute path of the folder that holds the file); `${userHome}`, `${env:...}`, `${workspaceFolderBasename}` and others are not.
- **Q: Name clashes?** Names are cleaned to the app's rule (letters, digits, `_ . -`, at most 48, cleaned names are noted). A name equal to a Copilot CLI/built-in name or to an existing extra of this folder with a **different** definition is imported as `<name>-vscode` (then `-vscode-2`...), with a note; an existing extra with the **same** definition (same trust hash) is shown as "already added" and cannot be ticked.
- **Q: Which fields are ignored?** Anything the app has no field for (`envFile`, `sandbox`, `dev`, `disabled`, `gallery`, `version`, `headers` on a stdio server, `env`/`args` on a remote server, unknown keys). The preview lists them per server in a note ("Ignored: ..."). The top-level `inputs` is listed once. Nothing is silently dropped.
- **Q: Bad files?** Missing file: "No `.vscode/mcp.json` in this folder." Too big (over 1 MiB), unreadable, or not valid JSON after comments and trailing commas are tolerated: a clear message, nothing imported, nothing written. A file with no `servers` map: "No servers in this file." Entries that are not objects, have an unknown `type`, or have neither `command` nor `url` are skipped and counted.
- **Q: What if the file changes between preview and import?** The preview carries a digest of the file text. Apply re-reads the file and refuses with "The file changed since the preview. Open the import again." if the digest differs, so what is imported is what was shown.

**Requirements.**

- **FR-020** `[IMPLEMENTED]` (test: mcp §9, sim) The folder's extras screen has a button **Import from VS Code...** next to *Add extra server*. It opens a preview dialog; nothing is imported until the user confirms. There is no import in Settings or anywhere else, and it never writes `~/.copilot/mcp-config.json` or `.vscode/mcp.json` (both are only read, the second only through this action).
- **FR-021** `[IMPLEMENTED]` (test: mcp §9) Parsing is tolerant: UTF-8 BOM, `//` and `/* */` comments, and trailing commas are accepted (comment markers inside strings, such as `https://...`, are kept). The servers are the `servers` map of the file (VS Code format). Size cap 1 MiB. The parser is pure (`src/shared/mcpimport.ts`) and never executes anything.
- **FR-022** `[IMPLEMENTED]` (test: mcp §9) Mapping to the extra format: `type` `stdio` (or missing with `command`) becomes `stdio` with `command`, `args` (strings only), `cwd` as working directory (must be absolute after `${workspaceFolder}` is resolved, else the entry is not importable), `env` as secret rows (numbers and booleans become text); an optional `tools` list of strings is kept as the tool filter (not a VS Code field, harmless: it only narrows); `type` `http` (or missing with `url`) becomes `http`, `sse` stays `sse`, with `url` and `headers` as secret rows; keys must be valid environment-variable or header names (others are ignored with a note). Entries that would not pass the app's own validation (URL with credentials or not http/https, command with a line break, ...) are shown as not importable with the validation message.
- **FR-023** `[IMPLEMENTED]` (sim: shots-i7) The preview lists each server with name, type, exact command and args or URL, working directory, env/header **keys with masked values**, notes and the reasons for disabled entries; a checkbox per importable server (none ticked), "Select all importable", a count of skipped entries, the file label (`.vscode/mcp.json`), and the sentence that imported servers arrive **off** and ask for trust on first start. Readable at 1280x800 and 1440x900 (no overlap; the list scrolls inside the dialog).
- **FR-024** `[IMPLEMENTED]` (test: mcp §9) Import creates extras **in this folder only**, `enabled: false`, no trust, through the same store function as the add form (so limits, validation, name rules and secret handling are the same). The result says how many were imported and why others failed. Trust: the first switch-on shows the trust dialog (FR-005 of 019, FR-013 above).
- **FR-025** `[IMPLEMENTED]` (test: mcp §9) Secrets as decided above: values never in previews, views, logs or toasts; literal values go to the secret store; `${...}` values are dropped and the key is kept.
- **FR-026** `[IMPLEMENTED]` (test: mcp §9) `inputs` as decided above (never prompted, stored or resolved; ids named in a note; `${input:...}` in command/args/url/cwd blocks the entry).
- **FR-027** `[IMPLEMENTED]` (test: mcp §9) Ignored fields and renamed names are listed per server in the preview.
- **FR-028** `[IMPLEMENTED]` (test: mcp §9, sim) Missing, oversized, unreadable and invalid files and files without servers give the messages above and import nothing.
- **FR-029** `[IMPLEMENTED]` (test: mcp §9) Name clash handling and "already added" as decided above.
- **FR-030** `[IMPLEMENTED]` (test: mcp §9) The main process reads the file; the renderer sends only the folder key and the ids of the ticked entries. Apply re-reads the file and checks the digest. Unknown folder keys are refused (same check as the other folder calls).
- **FR-031** `[IMPLEMENTED]` (test, sim) Unit tests (no credits, in `npm test` via `test:mcp`): comments, trailing commas, BOM, strings with `//`; stdio, http, sse and untyped entries; `inputs` and `${...}` rules; masked previews; bad files; name clashes; import through the store (off, untrusted, folder-scoped, trust prompt on first enable, nothing in another folder, secrets encrypted on disk). ### 2026-10-21: the extras form can also add for all folders (spec 069)

The folder's *+ Add server* form gains *Add to: This folder only (default) / All my folders (global)*. *This folder only* is
unchanged. *All my folders* writes the server into the agent apps' own lists after a per-file review (owner, 2026-10-21), so the Copilot
CLI list is no longer only read by Durbar. See [069](../069-mcp-global-controls/spec.md) FR-001..FR-011.
