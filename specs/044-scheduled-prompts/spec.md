**Input**: Issue #125 (owner's idea, 2026-10-17, with research notes on SDK 1.0.22 / runtime 1.0.98): schedule a prompt on a session, once or at an interval, only while the app is open; no OS scheduler, nothing changed on the user's system.

## Decisions taken from the issue (Phase 1)

- A schedule belongs to a **folder** and sends to that folder's first main agent (the one on its room's first desk). This works whether or not session ids survive a restart (spec 006 T021, open question to the owner), and it is what "every morning, summarize open PRs" means for a folder.
- **Once** (a date and time) or **every N minutes** (5 to 1440). No calendar rules in Phase 1.
- Copilot's own per-session scheduler (`every`/`after`) is not used (research: one session only, needs a live session, no skip-when-missed, no pause-all, no per-run cap).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Schedule a prompt on a folder (Priority: P1)

In **Folders**, each folder has **Schedules**. The dialog lists the folder's schedules (prompt, when, next run, last run and how it went) and adds one: the prompt (up to 10,000 characters, FR-120) and either *once at* a date and time or *every* N minutes. Each schedule can be paused, resumed or deleted.

**Acceptance Scenarios**:
1. **Given** a schedule every 30 minutes, **When** it is due and the agent is idle, **Then** the prompt is sent to the folder's agent as if the user had sent it, and the chat shows a calm note "Scheduled prompt (every 30 min)". *(test:, sim:)*
2. **Given** a once-schedule, **When** it has run, **Then** it is marked done and does not run again. *(test:)*

### User Story 2 - Never pile up, never surprise (Priority: P1)

**Acceptance Scenarios**:
1. **Given** the agent is working or waiting for an approval or an answer when a run is due, **Then** that run is skipped (not queued) and recorded as "skipped: the agent was busy". *(test:)*
2. **Given** the app was closed or the computer asleep at the due time, **When** the app runs again, **Then** a missed once-schedule is marked "missed" and is not sent; an interval schedule continues from now (the missed runs are not caught up). *(test:)*
3. **Given** **Pause all schedules** (in the Folders panel), **Then** nothing is sent until it is switched off; the choice is kept across restarts. *(test:, sim:)*
4. Runs use the session's own credit cap. *(Mode: replaced 2026-10-31, FR-180 and FR-182: a run uses its schedule's mode; it used to be the session's, so a schedule never allowed more than the agent already might.)* *(read: the send path is the user's)*

### Edge Cases

- The folder is removed: its schedules are removed with it.
- The folder is hidden or its floor is off: schedules still run (the agents keep running there, spec 033); the Floors and Folders panels show that a folder has active schedules.
- The prompt text is kept in the app's user-data folder (needed to send it) and never written to logs.

## Requirements *(mandatory)*

- **FR-001** Store: `durbar-schedules.json` in the user-data folder: `pausedAll` and up to 50 schedules (`id`, `folder`, `prompt` ≤ 10,000 characters (FR-120; 2,000 before 2026-10-28), `every` minutes 5-1440 or `at` epoch ms, `paused`, `done`, `last` {`at`, `outcome`: `sent` | `skipped-busy` | `missed` | `failed`}). Tolerant parsing: a bad entry is dropped.
- **FR-002** Scheduler (main process, pure core with an injected clock and sender, unit-tested): computes the next due time; at most one timer; on a due run it checks the folder's agent state (busy = working, thinking, needs-permission, or a question or limit waiting) and either sends or records the skip; missed once-runs at start are marked `missed`; intervals continue from now.
- **FR-003** IPC `schedules:list`, `schedules:save` (validated), `schedules:remove`, `schedules:setPausedAll`; the renderer shows the result.
- **FR-004** UI: **Schedules** per folder in the Folders panel (dialog with list and form), **Pause all schedules** in the panel header, a small clock and the next run in the folder row, and a note in the chat when a scheduled prompt is sent.
- **FR-005** Simulator: the same dialog and runs against simulated agents, no credits.

## Success Criteria *(mandatory)*

- **SC-001**: A user can add an every-30-minutes schedule in under a minute, and can stop all schedules with one switch.
- **SC-002**: No schedule ever sends while the agent is busy, and no run is sent twice.

## Assumptions and dependencies

- Phase 2 (issue #291, built 2026-10-20, see *Changes*): a schedule per session, calendar rules, a per-schedule credit or cost cap, the agent's own schedules (shown read-only).

## Changes

### 2026-10-31: every schedule has its own mode (spec 099 FR-083, FR-084)

**Owner decisions** (Vikram, relayed by his coordinating agent): 18:56 UTC, a scheduled prompt runs in the mode attached to that scheduled prompt; 19:02 UTC, schedules support all modes with a selection on each schedule, and existing schedules get a popup after upgrade asking the user to choose. **Today a schedule has no mode** (`Schedule` in `src/main/schedules.ts`): a run takes the session's mode through `deps.send`. Not built; tasks T140..T143. FR-182's wording needs the three owners (below).

- **FR-180** **A schedule has a mode.** `Schedule.mode?: 'read-only' | 'ask' | 'allow' | 'autopilot'`, with the agent it was chosen for (FR-182), validated in main. A run applies it for that one turn (for Autopilot, that one run) and then the session returns to what it was. The temporary mode is **never written to the folder's or session's saved mode** (not `setModeOp`), so a crash leaves those as they were. The credit cap and the skip rules are unchanged. The agent app's own schedules (FR-016) are not ours and have no mode here. **Choice UI**: reuse the mode choice of the new-session dialog (`#sdPerm`) and its confirmations (`confirmAllow`, spec 099's Autopilot dialog) (AGENTS.md FR-031).
- **FR-181** **No schedule runs without a chosen mode.** A new schedule must have a mode when it is created; the form starts on Read-only (constitution III) and the user can change it. A schedule with no mode, or a value main does not know, **does not send** and shows as *Waiting for a mode*: nothing is deleted and nothing is sent on its own. Each due time it would have used is recorded with a new closed outcome `skipped-mode` (FR-036). **After upgrade**: on the first launch with such schedules, one popup lists them and asks for an explicit choice for each. It never picks for the user; closing it leaves them waiting, and each row keeps a *Choose a mode* action. Choosing does not send at once: an interval or rule schedule waits for its next time, and a once schedule whose time has passed offers *Run missed now* (spec 052 FR-089).
- **FR-182** **Allow all and Autopilot on a schedule: an explicit opt-in for one schedule and one agent.** Draft wording of how this stays within constitution III's "explicit, per-agent opt-in", **for the three owners to confirm in the PR**: the choice is made in the window only (`fromApp`), never from MCP tools or remote control; the confirmation names the schedule and the agent ("Let the schedule *<name>* run *<agent>* (*<app>*) in *<folder>* on Allow all? It will not ask you first, each time it is due, until you change this."); the choice is stored with that agent's identity (the target session and app, or for a folder schedule the app chosen), and a run that would go to any other agent is not sent and returns to *Waiting for a mode*; editing the prompt, target or mode asks again; the row always shows the mode. Read-only stays the default. A schedule may run with more power than its session has: that is this delta's purpose, and the reason for the owners' check. The constitution is not edited here; an amendment, if the owners want one, is proposed in the PR.
- **FR-183** **Organization policy** (spec 076) is checked at save and again at each run. A refusal at a run does not send; it is logged with the closed reason `mode-refused` (FR-036) and visible on the row.
- **FR-184** **Where an adapter lacks a mode** it is not offered for that agent (Autopilot needs `capabilities.autopilot`, spec 099 FR-001). A stored mode that the agent cannot use, or that a live session cannot switch to, is **not sent**: `mode-refused`, a visible reason on the row, `[KNOWN GAP]` per app until checked. Autopilot on a schedule is spec 099 FR-084.
- **Open, proposed**: a loop (spec 072) uses the field per pass for Read-only, Ask first and Allow all, but **Autopilot is not offered on a loop**: a loop is Durbar's timer sending again and Autopilot is the app's own goal loop, so together they would multiply. The owner has not ruled on this.

### 2026-10-31: T140..T143 built: what main proves, gaps and choices made while building (coordinator choices awaiting owner review; none is an owner decision)

Built: `src/main/schedules.ts` (`Schedule.mode`, `modeFor`, `modeSeal`, `modeBlock`, `saveMode`, `applyMode`, `askMode`, `setMode`), `src/main/schedmode.ts` (`RunModes`, `createScheduleWiring`, `modeCheckOp`), `schedules:askMode` and `schedules:setMode`, the form's *Mode* (`fillSchedMode`, on `#sdPerm`'s `modesFor`, `PERM_LABEL` and `markOrgModes`, with `confirmAllow`), the popup `#schedModeDlg`. `test:` `scripts/test-schedmode.ts` (part of `test:schedules`) runs main's wiring (`createScheduleWiring`) with the real Scheduler and a FakeAdapter's events; `sim:` `scripts/check-sched-mode.js` at both sizes runs the simulator's copy of the rules, so it checks the window, not main. `not verified:` a real Copilot, Claude Code or Codex session (no AI credits): each app's switch is `read:` its `setPermMode` (Copilot and Claude Code `live`, Codex `next-message` with its `wantMode`), `[KNOWN GAP]` per app until a real run (FR-184).

**What main can and cannot prove about Allow all (FR-182).** A save or `setMode` that sets Allow all needs a one-time token from `askMode`, valid 5 minutes, memory only, bound to the schedule's id, folder, prompt, target, mode and agent app; `askMode` writes the confirmation's words from main's own records. A mode from a plain save (Pause, Resume), a made-up token, or a token for another prompt or target is refused. **Main can prove**: the call came from the app's own page in its main frame (`fromApp`, in `ipcguard`), that page asked this exact question first, and no other code in `src/` calls these methods (`test-schedmode.ts` scans; MCP tools and remote control have no path). **Main cannot prove**: that a person saw the dialog and pressed the button. Script running in the app's own page could ask and answer by itself; that is the same trust `agents:setMode` gives the page today. A native dialog owned by main would prove more, but FR-180 and FR-031 ask for the shared confirmation; open for the owners.

**`[KNOWN GAP]`**
- **Autopilot** until spec 099 T097: `'autopilot'` is parsed, kept across restarts, Pause, Resume and an edit of the time; a run is not sent and is logged `mode-refused` with a visible reason; no form offers it (no agent has `capabilities.autopilot`) and no save can set it. An edit of the prompt or target of such a schedule is refused until a mode that exists is chosen.
- **The file**: `allow` is sealed by main with the OS's safe storage (`safeStorageCodec`, the MCP secrets' store) over what it was confirmed for (`proofKey`: id, folder, prompt, target, mode, app). A missing, wrong or undecryptable seal reads as no mode: it waits (`skipped-mode`, reason `no-seal`). Where the OS has no safe storage nothing can be sealed: Allow all lasts until the app closes and is asked again at each launch. **This raises the bar and does not close it**: a same-user agent that can reach the keychain, or read this process's memory, can still seal one. `durbar-folders` can already hold `allow` (`folders.ts`, `parseSavedFolders`), so "the file could not raise a session's mode" was true only of this file before this delta, and stays open for that one. Choice awaiting owner review.
- **The seal's limits**: it covers a digest of what was confirmed plus the time and the limit, so an old seal on a changed time or limit reads as no mode. **A whole old copy of the file put back over a choice the user revoked is accepted**: a marker would live in a file the same program can put back too, so none was added. When the OS's safe storage is not available or has changed, the schedule keeps waiting (`modeLost`) with that reason on its row, and asks at each launch until a mode is chosen.
- **Autopilot's seal** (coordinator's ruling on this choice): nothing sets Autopilot in this build, so nothing seals it, and a stored unsealed one stays as a refused value. **T097 seals Autopilot when it sets it, and from then a stored unsealed one reads as no mode.**
- **Remote control during a turn in a lower or the session's own mode**: a raised mode is refused at `apply` while remote control is on (`mode-live`), and remote control cannot be switched on during a raised turn. A lowered turn is no risk.
- **Other sends during a raised turn**: the app's own background work in that turn runs in that mode by design. After the turn, `read:` on Claude Code a CLI launched with Allow all's flags stays up until the next send, which relaunches it; the hook checks the restored mode on every tool call (`hookDecision`), so a background turn is held to the restored mode there, and on Codex a turn only starts from a send, which reopens first. Neither was tried on a real app: `[KNOWN GAP]`.
- **A turn that never ends**: there is no timer. An app that goes silent keeps the session held in the run's mode, shown on the chip, until Stop, a mode chosen in the chip's menu, or End session. Nothing else can start in it.
- **The office's counts**: the top-bar button still counts a waiting schedule as active (FR-028, `activeCount`) and the lobby Postbox still lists its time; its row and the folder's next-run text do not claim a run.
- Under the simulator there is no adapter mode to switch, so the temporary mode, restore and `refusesLive` are tested only on `FakeAdapter`.

**Choices where the spec was open, each the option that fails closed**
1. **Another agent, every mode.** FR-182 says this for Allow all and Autopilot; FR-180 says every mode stores the agent. A run for another agent is not sent and waits for a mode for Read-only and Ask first too (`skipped-mode`, reason `other-agent`). The agent coming back does not bring the choice back.
2. **A save that is not an edit** keeps main's mode; one naming another mode is refused; one that changes the prompt or target (*Use the folder's agent*) drops the choice, so it waits, Autopilot included.
3. **An edit with no `mode` key** keeps the mode under the same re-ask rule; a key with anything else is refused, never read.
4. **An unknown word is not kept**: a mode written by a newer version reads as no mode, and the next write drops the word. Nothing else of the schedule changes.
5. **A mode with no `modeFor` in the file** is no mode (`autopilot` excepted: it needs none until T097).
6. **Once schedules**: a time that passes with no mode finishes it with `skipped-mode` (never retried, so the timer cannot spin), it stays *Waiting for a mode*, and after a choice its row offers *Run missed now*. At start, a time that passed while closed says `skipped-mode` rather than `missed`, so such a run is not in the *Since you were away* card. A `mode-refused` once schedule also offers the choice and the button.
7. **Order at a due run**: over the limit, Pause all, session ended, own limit, then the mode, before a closed door and busy, so a run that may not go is never queued. A held run is checked again at release; one whose prompt is older than an Allow all confirmation stays held.
8. **One gate per session** (`RunModes`, review of a2da7dce): `setup -> sending -> running`. A typed message is refused from the run's reservation until the mode is proven back, whichever way the mode differs (simpler than judging the direction, and a typed message must not end a run's turn). A typed message on its way stops a run: `skipped-busy`. Status is read again right before the switch, and the switch and the send are in one tick. Other schedules count a held session as busy.
9. **Every return path of a run has an end**: a turn's ending status after it began, a send that returned with no status of its own (a sandbox hold: not sent, logged `failed`), a send that threw, Stop, a mode chosen in the menu, End session. A status from before the send never ends it. A read never changes it: a session that is not live while its send is in flight is reopening and stays held; only `running` with no live session may be cleared by a look, as the adapter then keeps nothing. A restore that throws stops the session. A send a person walked away from cannot be called back, so when it returns the mode is set right once more and a turn it delivered is interrupted, unless they typed a message since. Codex reads the wanted mode again after each await of its reopen, and a typed message is refused while the session is closed for it.
10. **The confirmation's name for a schedule** is its prompt cut to 60 characters (schedules have no name), and the whole prompt follows in a scrolling list; the popup's rows open to the whole prompt too. The popup comes once per profile (`durbar.schedModeAsked`) after other dialogs close, and at each launch for a schedule whose seal could not be checked; a later waiting schedule only has its row.
11. **Loops** (open, proposed above): the field is read per pass; no mode or a refusal is not a pass, is logged, and the loop looks again after a pass length; Autopilot on a loop is refused at save and at a pass. Loops stay off in this build (`loopSupport`), so this is tested on the Scheduler only. Spec 072 FR-006 ("passes keep the session's permission mode") is replaced by this if the owner keeps it.
12. **Organization policy at a run** is read fresh after the session is there, and at a save before the check. `blocked` and `fatal` refuse any mode. `doubt` (a reader that threw, a value Durbar does not know), and on Copilot a managed-settings answer that failed, came late or was not readable (`runtimeUnread`: it then read only the fallback file), refuse only a mode above the session's own, since nobody is there to decide; a save before any Copilot runtime has started is not refused, and the run asks again; Read-only and the session's own mode are not refused, and at a start with the person there it stays advice. An app with no policy reader has nothing to refuse.
13. **Folder schedules, for the owners with FR-182**: a folder schedule's Allow all is bound to the app, as FR-182's draft says, not to one session. The folder's first agent can change to another session of the same app and it still runs. The confirmation now says so: "this folder's *app* agent, now *name*". Binding it to one session would be stricter and would make it wait after each new session.
14. **A prompt the app would keep at a spending limit**: in a temporary mode the message is not kept (`noHold`), since it would run after the mode came back, possibly with more power than chosen. See the limits below.

15. **One hung session does not stop the others**: a tick waits at most 30 seconds (`SEND_PATIENCE_MS`) for a send, then goes on; that schedule is not due again until it answers, and its outcome is recorded then. *Run missed now* says so; a door's release treats it as gone out, so it is never released twice.

**Limits on a person's own money or usage (owner principle, Vikram, 2026-10-31 20:52 UTC, relayed: warn and let them override; only organizations may enforce):**

| Limit on a schedule | Kept or changed | Why |
|---|---|---|
| At a session's spending limit, a run in a temporary mode (`noHold`) | **changed, added in this delta** | It first failed silently as "the agent app refused it". Now the app's own notice asks the person with its way to raise the limit, the row says what to do (`mode-refused`, `mode-limit`), the schedule stays active, and its next time goes once raised. Only keeping that one prompt for later is refused: that is the mode's safety, not the money |
| A run in the session's own mode at its limit | kept as it was | Held, and the notice asks; the person chooses |
| The schedule's own limit (FR-015) | kept | Optional, set by the person; it pauses and says so, Resume or an edit overrides |

| 5 to 1440 minutes, 50 schedules, 10,000 characters (FR-001, FR-120) | kept | Not added here. They bound the app's own work and storage, not a person's spend; no way to override them exists today |
| Organization policy (FR-183) | kept | Organizations may enforce |
| The Allow all confirmation (FR-182) | kept | It can always be accepted |
| The mode restore, the gate, the seal, refusing an unknown or another agent's mode | kept | They protect the person's choice; they limit no spend |

### 2026-10-20: Phase 2: calendar rules, per-session schedules, a per-schedule cap, the agent's own schedules (issue #291)

*Decisions:* a schedule whose session has ended **pauses** and says so; it is never sent to another session without the user choosing it (the safe choice, Principle II). A per-schedule cap counts what that schedule's own runs spent; it is checked before a run, never during one (the session's own cap still applies during a turn).

- **FR-012** **Calendar rules.** Next to *Every N minutes* and *Once at*, **On a calendar**: *every day*, *weekdays (Mon-Fri)* or *weekly on* one or more days, **at HH:MM** local time. Stored as `rule` {`kind`: `daily` | `weekdays` | `weekly`, `time` "HH:MM", `days` 0-6 (0 = Sunday), weekly only, at least one}.
  - The next run comes from a pure function, `nextRuleRun(rule, after)` in `src/shared/schedrules.ts`. It builds the next `Date` from the local calendar day and the wall-clock time (Y/M/D h:m), never by adding 24 h, so a run keeps its time of day across a daylight-saving change. This fixes the FR-007 `[KNOWN GAP]` for *every day at*.
  - Daylight saving: in spring a time inside the skipped hour (for example 02:30 in Europe/Zurich) runs once that day at the shifted time (03:30). In autumn a time inside the repeated hour runs once, at its first occurrence.
  - Busy, missed and *Pause all* behave as for intervals: the run is skipped and the next run is the rule's next time. Missed runs are not caught up.
  - The list says "every day at 08:30", "weekdays at 09:00" or "weekly on Mon, Thu at 17:00".
- **FR-013** **Migration.** Existing saved schedules keep working.
  - An old *every day at* (`every: 1440` with `at`) is read as a `daily` rule at the local time of `at`. Its daylight-saving drift goes away without an edit.
  - Other anchored intervals and plain intervals are unchanged.
  - New fields are optional. A missing field means: the folder's agent, no cap, nothing spent. A bad value in a new field is dropped; a bad rule drops that schedule, as for a bad interval.
- **FR-014** **A schedule for one session.** A schedule can target one session (`target` {`session` id, `agent` app id, `name` shown}) instead of the folder's agent.
  - It runs only in that session, and the busy check looks at that session only.
  - When the session is gone (removed, replaced, or not restored after a restart), the schedule **pauses** with `pausedReason: session-ended`. This is checked when the app starts, when a session is removed and when a run is due; a run found due then is recorded as `skipped-ended`.
  - The list shows "Paused: the session has ended", with **Use the folder's agent** (it drops the target and resumes). *Resume* alone is refused while the session is gone.
  - The Schedules dialog opened from a chat (its header button) has **Send to**: *This folder's agent* or *This session (<name>)*. Opened from elsewhere it sends to the folder's agent, as before. The list shows "→ <name>" for a targeted schedule.
- **FR-015** **A limit per schedule.** **Limit** is optional, in the unit of the agent app's cap: AI credits (Copilot) or dollars (Claude's estimate, spec 012 FR-150). The unit is taken from the target's agent app when the schedule is saved. Stored as `cap` {`amount`, `unit`: `aiu` | `usd`}, with `spent` and `spentUnknown`.
  - *Attribution:* from a scheduled send until that session's turn ends (its next `idle`, `error` or `stopped` status), every `usage` event of the session counts toward the schedule. That includes its helpers, which report through their agent. The amount is `nanoAiu / 1e9` for AIU, or `costUsd` for dollars.
  - When a run is due and `spent` ≥ the cap, nothing is sent. The run is recorded as `skipped-cap` and the schedule pauses with `pausedReason: cap`: "Paused: reached its limit". **Resume** starts counting again from zero.
  - The list shows "spent 1.20 of 5 AIU", or "$0.04 of $1.00".
  - *Limits, said honestly:*
    - a message the user sends during a scheduled turn counts too (it over-counts, the safe side);
    - a run that starts under the cap can end over it (the cap stops the next run, not the current one);
    - a usage event without a figure in the cap's unit (a runtime that reports no credits) sets `spentUnknown`, and the list says "the spend was not fully reported";
    - the spend is kept with the schedule, so it survives restarts; a turn in progress when the app quits is no longer attributed after the restart.
- **FR-016** **The agent's own schedules, read-only.**
  - The Copilot SDK reports prompts scheduled inside a session (`session.schedule_created`, `session.schedule_cancelled`, `session.schedule_rearmed`; made with `/every` or `/after`, or by the agent through its `manage_schedule` tool). The Copilot adapter maps them to a normalized `agentSchedule` event: phase, id, prompt, interval, cron expression and time zone, one-off time, next run, and who made it.
  - The Schedules dialog lists a folder's live sessions' own schedules under **Scheduled in the agent app (read-only)**, with a note that Durbar cannot change them.
  - Only schedules reported while Durbar runs are shown. They are not read from a session's history, and they are kept in the window only.
  - `[KNOWN GAP]` Not available from Claude Code or Codex: neither adapter reports such schedules. Not seen on a real Copilot session: the runtime exposes `manage_schedule` only to some accounts ("typically gated to staff users"), and `/every` was not tried through Durbar.
- **FR-017** **Validation.** Everything from the renderer is untrusted and is validated in main: the rule (kind, time, days), the target (the session must exist when saved, ids are limited to `[A-Za-z0-9._:-]` and at most 128 characters, the name is one line of at most 80 characters), and the cap (AIU 0.01 to 1,000,000, dollars 0.01 to 10,000, in the target's unit). `spent`, `spentUnknown` and `pausedReason` are never taken from the renderer; main keeps its own.
- **FR-018** **Simulator.** The simulator has the same rules, targets, caps and pause states. Its simulated usage counts toward a schedule's cap, so the dialog can be checked without credits.

### 2026-10-28: the prompt limit is 10,000 characters and a prompt is never cut silently (owner decision, issue #843)

Owner (Paco, 2026-10-28): a schedule's prompt was limited to 2,000 characters (`MAX_PROMPT`) and **cut without a word** in two places: the textarea had `maxlength="2000"` (a longer paste lost its tail) and the tolerant parser kept `prompt.trim().slice(0, MAX_PROMPT)` (a longer stored prompt lost its tail), so a schedule could send an incomplete prompt unattended.
