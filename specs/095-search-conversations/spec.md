## Why a new spec and not a delta

The title search belongs to spec 006 (FR-023, `src/renderer/sessionsearch.js`) and the List view to spec 052 (FR-100..FR-104, J/K rows). This feature adds things neither owns: **reading the content of every session on disk** (a new privacy surface), a **new main-side scan with its own IPC channels, cancel and progress**, a new top-bar control and shortcut, and a jump to a message. A delta would bury that in 006's 170+ requirements. So it is a new spec, number **095**, as the issue says. Checked 2026-10-29: `specs/` on `origin/main` ends at 094; no remote branch `095-*` (`git ls-remote --heads origin`); no open PR uses 095; 095 is not in `RETIRED` (`scripts/specs-index.js:48`: 023, 026, 031, 042, 046, 047, 053, 055, 067, 071, 078, 079, 082, 086, 088..091). Specs 006 (FR-023) and 052 get a short cross-reference under their `## Changes` when built (T003).

### Owner requirements from the issue (binding)

Reuse `DurbarSessionSearch`, the List view, the readers and Resume, and the palette where it fits; **no parallel path**. Local only: nothing is sent anywhere. Nothing new stored, or the spec says where an index lives, what it holds and how to clear it. Excerpts go through the existing masking (spec 041). ### Decisions taken by this spec (change them under *Open questions*)

- **A1 No stored index in v1.** A streamed scan with cancel (the only thing kept between two searches is the in-memory list of earlier Codex session titles of FR-026, owner answer C). Nothing new is written to disk (the Constitution III default); an index would hold conversation text on disk, which is a bigger privacy decision. The scan is incremental and capped (FR-020..FR-024). An index is a later spec if the scan is too slow (Q6).
- **A2 The text that is searched is the text that is shown.** Matching runs on the **masked** text (FR-030), so a secret cannot be found by its value and the highlighted line is always the matched line. A hit whose only match disappears under the mask is dropped.

## User Scenarios & Testing

### User Story 1 - Find the session where I talked about something (Priority: P1)

I type "invoice export" in the top-bar box. The window switches to the List view and, a moment later, shows the sessions (open or earlier, any folder) whose title or messages contain both words, newest first, each with a line such as "...fix the **invoice** **export** to CSV when the..." and the match marked.

**Why this priority**: it is the whole point of the issue.

**Independent Test**: on the simulator with a fixed corpus of 3 open sessions and 5 previous ones (fake readers), typing a two-word query lists exactly the expected sessions, each with an excerpt containing the words, in newest-first order.

**Acceptance Scenarios**:

1. **Given** the office has sessions A and B and Previous sessions of folder F has C, **When** I type a word that occurs in A's reply, in C's first prompt and in B's tool output only, **Then** A and C are listed, B is not (D2).
2. **Given** a query of two words, **When** one word is in a user message and the other in a reply of the same session, **Then** the session matches (every word, any order, like `filterSessions`); the excerpt is the line with the first word found, and a second excerpt, if the other word is in another message.
3. **Given** "explicacion", **Then** "Explicación" matches (case and accents folded).
4. **Given** a session whose title matches but no message does, **Then** it is listed with the title match marked and no excerpt line (the row itself is the result).
5. **Given** no session matches, **Then** the area says "No conversation matches" with the query, and the box keeps focus.

### User Story 2 - Open a result and land on the message (Priority: P1)

**Independent Test**: simulator, each of the four kinds: click (or Enter on) a result; the right chat opens and, for a content hit, the matching message is in view, marked for a moment (a title hit opens at the end).

**Acceptance Scenarios**:

1. **Given** a result in an open session, **When** I press Enter on it, **Then** that chat opens (as a click on its List row does) and the matching message is scrolled into view and marked (focus ring plus a short background, not animation-only: reduced motion is respected).
2. **Given** a result in a previous session of Claude Code, Codex or Copilot, **When** I press Enter, **Then** it is resumed with the existing Resume (`sessions:resume`, its mode rule, the "already open" refusal, the in-flight guard), and when its history is shown, for a content hit the matching message is scrolled into view; a title hit (earlier Codex and Copilot sessions in v1, US1.4, FR-014) opens at the end.
3. **Given** a VS Code chat result, **Then** it opens in the read-only viewer (View), at the matching block.
4. **Given** the message is older than what the chat shows (the replay cap), **Then** the chat opens at the end and a note says "That message is older than the chat shows" (never a silent miss).
5. **Given** the session is already open or being opened, **Then** the existing refusal text is shown; nothing is resumed twice.

### User Story 3 - Keyboard and screen reader (Priority: P1)

**Acceptance Scenarios**:

1. **Given** any view, **When** I press the shortcut (Q2), **Then** the box is focused and its text selected; it works from text fields except an open dialog.
2. **Given** the box has a query, **When** I press Escape, **Then** the box is cleared, a running scan is cancelled, and the view I came from (Office or List) comes back; a second Escape does nothing special. Focus returns to where it was before the search.
3. **Given** results, **When** I press Down or Tab from the box, **Then** focus goes to the first result; J/K and arrows move between results like the List view; Enter opens; Shift+F10 or the menu key opens the row's menu where the List view has one.
4. **Given** a screen reader, **Then** a polite live region says "Searching, 3 of 12 sessions" (at most every 2 s), then "5 results in 4 sessions" or "No conversation matches", and each result's accessible name is "title, app, folder, open or previous, match: excerpt" with the highlight announced as plain text (a `<mark>` carries no extra speech).

### User Story 4 - Large histories stay calm (Priority: P2)

**Independent Test**: node test with a generated 40 MB corpus of fake sessions: the scan yields to the event loop (longest slice under the budget of FR-022), can be cancelled within one slice, and never holds more than the cap in memory.

**Acceptance Scenarios**:

1. **Given** hundreds of sessions, **When** I type, **Then** the first results show within 1 s on the simulator corpus, the rest arrive progressively, and the state "Searching, N of M sessions" stays visible until done; typing again cancels the old scan.
2. **Given** a session file over the reader's cap, **Then** it is skipped with a count ("2 sessions too large to search"), not read.
3. **Given** the window is in the background, **Then** the scan keeps its pace limits (no busy loop).

### User Story 5 - Sessions I cannot read (Priority: P3)

**Acceptance Scenarios**:

1. **Given** an agent app that is not installed or signed out (its previous sessions cannot be listed), **Then** the scan skips it and the end state says "Not searched: Codex (not installed)" once, with no error dialog.
2. **Given** a Copilot or a Codex previous session (Q4, review question B), **Then** it is searched by title only, and the end state says so.
3. **Given** a hidden previous session, **Then** it is never searched in v1, whatever the panel's Show hidden says (the panel's Show hidden is a per-panel view that resets; main cannot know it; see Q5's note and FR-033). The end state counts them.

## Edge Cases

- **Query**: trimmed; fewer than 3 characters (Q3, FR-033: after trimming and after hidden characters are removed, counted in Unicode code points, spaces not counted) searches nothing, does not switch the view, and says "Type at least 3 characters"; short words inside a longer query are allowed ("a bc" has 3 and is searched, "x y" has 2 and is not); at most 200 characters and 8 words (the rest is cut and said); control characters removed; the query is data (never a regex: plain substring of folded words). A query of only spaces clears the results.
- **Huge or hostile text**: a single message is searched up to 20 000 characters (the reader's `maxTextChars`); an item over that is cut by the reader and a note says so only if the match could lie beyond (not claimed otherwise). The masking step is bounded (FR-031).
- **Masked matches**: a query that matches only inside a masked span (a token, a URL password, a home path user name) finds nothing (A2). The query `~` or `[redacted]` is just text.
- **Same text in many messages**: at most 3 excerpts per session in the row and "+N more" with the count; at most 200 sessions in the result list ("200 shown; narrow your search").
- **Duplicate**: a session open in the office is never also listed as previous (`openIdsOf` already removes it by Durbar id and resume id). `listPreviousOp` works per agent, so two agents of the same app in one folder list the same earlier sessions: the scan lists each once, by (adapter, folder, session id) (FR-020).
- **Scope of "every folder"**: the earlier sessions searched are those of the apps that have an agent in that folder (the plan is built from the open agents' folders). With no session open there is nothing to search yet: the box says "Open a session first; earlier sessions are searched for the apps and folders you have open" and starts no scan.
- **Top-bar folder filter**: it does not limit the search. Every folder is searched and each result shows its folder (FR-016).
- **Helpers and sidechains**: office helper agents (spec 001 FR-089) are not searched as sessions of their own, and Claude sidechain lines (`isSidechain`, which `claudeHistory.ts` filters) are not searched, the same as the chat shows them.
- **Searchable text and folding**: matching uses `fold` from `src/renderer/sessionsearch.js` (NFD, strip combining marks U+0300..U+036F, lower case). It does not unify every spelling: "ß" stays "ß" and does not match "ss"; "İ" becomes "i" and matches "istanbul"; the dotless "ı" stays "ı".
- **Floors off, hidden folders and sessions**: sessions of a floor that is off are not searched (spec 033 FR-008). Folders hidden in the office (a door) are searched. Previous sessions the user hid are not searched (FR-033).
- **A session ends or is deleted during the scan**: its reader returns empty; skipped.
- **Search while an agent writes**: the open session's history is read once per scan; a message that arrives later is found by the next query.
- **Paths**: the window never sends or receives a path; excerpts have home folders masked (`maskHomePaths`, `/home/<user>`, `/Users/<user>`, `C:\Users\<user>`, also `\\`-doubled JSON); readers resolve their stores with `path` and the existing per-OS roots (`claudeConfigDir`, `vscodeUserDirs`, the Copilot/Codex runtimes), no new path code.
- **Layout**: a long title or excerpt ellipsizes in the row (never wraps the row taller than 2 lines), the result list scrolls inside the List area only; the office with 15 agents at 1440x900 and 1280x800 is unchanged when the box is empty (geometry and office checks stay green).
- **Theme**: all themes use the same sizes; no text below 10.5px.
- **Simulator**: `DURBAR_SIM` serves a canned corpus through the faked bridge; no real store is read and no channel is added to `SIM_OPEN_CHANNELS` (T033).

## Requirements

### Functional Requirements

**Box, view and keyboard**

- **FR-001** A search field in the top bar (`#convSearch`, `type="search"`, visible label "Search conversations" via `aria-label`, placeholder "Search conversations", `title` with the shortcut). The box is available in Simple and Expert. With no session open it says there is nothing to search yet (see *Edge Cases*, "Scope of every folder"). `[IMPLEMENTED]` (`#convSearch`, `#convSearchBtn` in `index.html`; `fitTopbar`'s first step `tb-search`; at 1440x900 and 1280x800 with the simulator's labels the bar is already full, so both sizes show the magnifier, which opens the field over the bar; driver: `shots-095`).
- **FR-002** Typing (after a 250 ms pause) switches to the List view (`setView('list')`), remembering the view it came from, and starts a scan (FR-020), **only once the minimum query of FR-033 is met**; below it the view does not change and no scan starts. Clearing the box, or Escape (FR-003), cancels the scan, restores the remembered view and the normal List. `[IMPLEMENTED]` (`csInput`, `csRun` in `app.js`; driver: `shots-095`).
- **FR-003** Escape in the box (or in the result list) clears the query, cancels any scan and goes back to the previous view and focus. With a query empty already, Escape behaves as before (blur). The shortcut that focuses the box is Ctrl+Shift+F (⌘⇧F on a Mac), configurable (Q2 (a)). It is listed in the keyboard sheet (`?`), Settings > Keyboard and the palette's actions as "Search conversations". The palette entry only focuses the box (the palette is not a second search UI). `[IMPLEMENTED]` (`SEARCH_KEY`, `searchClashOf`, `loadSearchCombo` in `navigator.js`; Settings > Keyboard shares the Go to recorder, `wireKeyRec`; tests: `test-navigator.ts`; driver: `shots-095`).
- **FR-004** While a query is active, the List area shows the **results view** in place of the agent rows: the same container (`#list`), list header and styling; the agent rows come back when the query is cleared. Sort headers sort the results by their own columns (name, app, folder, when). `[IMPLEMENTED]` (`renderConvResults`; the sort headers are Session, Agent app, Folder and Active; the other columns of the List keep their place and are not sortable here).

**Results**

- **FR-010** Two groups, in this order: **In the office** (open sessions, each a List row built by the same cell helpers as `renderList()` so the status dot, mode icon and name look identical) and **Earlier sessions** (previous sessions: name or title, app, folder, "last active", and a **Resume** or **View** button as in the Previous sessions panel). Each group header says "N sessions". Within a group, newest first; pinned previous sessions are not moved to the top (a search ranks by recency). While scanning, rows appear per folder as they are found (FR-015); at `search:done` each group is re-sorted newest first. `[IMPLEMENTED]` (office rows by `listRow0`, the List's own row; the office group is ordered by each session's last activity in the window, `csTime`, since main sends no time for it).
- **FR-011** Under each row, one to three **excerpt** lines (D3): about 140 characters, the match centred, cut at word boundaries with "…", every query word found in the line marked with `<mark>` (built from offsets returned by main, text set with `esc()`, never from raw HTML). A marked word has a non-colour cue too (bold plus the background), so it holds in high contrast. Whether it was said by "You" or the agent is shown as a short prefix (`You:`, `Agent:`), text 10.5px or more. A title match is marked in the row's title itself (`titleMarks`), with no `Title:` excerpt line (FR-021, US1.4; changed 2026-11-03). `[IMPLEMENTED]` (`markedHTML`, `excerptHTML` in `convsearch.js`; test: `test-convsearchui.ts`).
- **FR-012** Opening a result: Enter or click on the row. Open sessions: select the agent and open its chat, as a List row click does (`app.js` List click handler). Previous sessions: `sessions:resume(agentId, sessionId, false)` and then show the history, as the Previous sessions Resume button does; VS Code chats: the read-only transcript viewer. No new resume path (Constitution, "look for an existing capability first"). `[IMPLEMENTED]` (`csOpen`: `openPanel`, `resumePrev`, `viewVs`; a resumed result then opens its new chat; driver: `shots-095`).
- **FR-013** **Jump to the message** (D3). Every excerpt carries an **anchor**: `{ n }`, the 0-based ordinal among the text messages (user and agent items, tool items not counted) in the order the reader returns them, plus `head`. **`head` is built only after the full masking of FR-030**, from one normalized comparison used by both main and the window (`anchorKey(text)`, one function in the shared fold module, tested for parity): the masked text, Markdown stripped, then `fold`; `head` is its first 60 characters. After the chat is built, the window applies the same `anchorKey` to the nth message element's text and scrolls to it if it begins with `head` (so a different replay cap or a changed history is detected), marks it for about 2 s (respecting reduced motion: no fade) and moves the focus to the chat log, as Notes' Open source does (innerscroll.js rules, spec 052 FR-176: no bare `scrollIntoView`). If it is not found, the note of US2 scenario 4 is shown. `[IMPLEMENTED]` (phase 1: `anchorKey` and `head` in main; phase 3: `csJump`, `pickAnchor`; T040's answer is in the plan, *Chat messages and the anchor*; driver: `shots-095` for an open chat, a resumed one and the VS Code viewer; test: `test-convsearchui.ts`). Changed in phase 3 (T040): the window looks for the nth bubble first and, when its key does not begin with `head`, for the nearest bubble whose key does (a replay that shows only the last 300 items, or a live chat with more), and compares the page's own masking of the bubble too (the chat may show what main masked); the focus goes to the chat log, as Notes' Open source does, not to the bubble.
- **FR-014** The end state is one line under the group headers: "Searched N sessions in M folders. Not searched: ..." listing only what applies: apps not installed or signed out, sessions too large ("too large, skipped", count, from the 50 MB per-file cap), unreadable (count), Copilot and Codex previous sessions (searched by title only), hidden previous sessions (count, not searched), floors that are off (count of sessions skipped), results capped, folders whose earlier Codex sessions were not listed because their floor is off (count, owner answer C), folders whose earlier sessions were not listed in time (count and apps, FR-022), and, when saved MCP values were locked in the vault during the scan (`notes.mcpValuesLocked`, owner answer D), the note "Some saved MCP values are locked; excerpts may show them." Office helper agents and Claude sidechain lines are not searched, and that is not listed as a gap because the chat does not show them either. `[IMPLEMENTED]` (`notesText` in `convsearch.js`; test: `test-convsearchui.ts`, every note).
- **FR-015** While scanning, the state line says "Searching, N of M sessions" with a **Stop** button (also Escape). The line is a plain `.cs-state` row in the results view, redrawn at most every 250 ms; it is not a live region itself, because it is redrawn so often. What a screen reader hears goes through the app's one live region (`announce()`, `#srAnnounce`, polite): the progress at most every 2 s, then the final line ("N results in M sessions" or "No conversation matches"), and "Stopped." for Stop (changed 2026-11-07, review of PR 1240, R7). **Scan**

- **FR-020** One scan per window at a time. `search:start` cancels the previous scan. The scan is **streamed**: open sessions first (their history as each adapter gives it: Claude Code from its file, an open Codex session through `thread/read` (FR-022, FR-023), Copilot through `getEvents()`), then, folder by folder in the office's order, the previous sessions newest first (the earlier sessions of the apps that have an agent in that folder, listed once each: deduplicated by (adapter, folder, session id), because `listPreviousOp` works per agent and two agents of one app in a folder list the same sessions); each session's text is read, matched and released before the next. No transcript is kept after its session is done (A1). `[IMPLEMENTED]` in the scan core (`orderPlan`, `startScan` in `src/main/convsearch.ts`; test: `test-convsearch.ts`); built from main's state in phase 2.
- **FR-021** Titles first: a session whose title matches is a hit at once, before its messages are read. The title match uses the user's name for the session (spec 059) when there is one, else the title. **Titles are masked before they are matched** (the same masking as FR-030); if masking a title throws, the title is not matched and the session is not a title hit (fail closed). `[IMPLEMENTED]` (test: `test-convsearch.ts`, FR-021 block).
- **FR-022** **Budgets** (constants in one file, tested): the scan yields to the event loop at least every 15 ms of work; reads are one at a time per source (earlier Codex sessions are title only, so no `thread/read` starts for them; an open Codex session's read and a folder's Codex `thread/list`, which starts one short-lived app-server, are one at a time **across scans**, see FR-023); at most 200 listed sessions per folder (the readers' `MAX_FILES` / `MAX_LISTED`); at most 400 sessions per scan; a reader's size cap (Claude 50 MB) applies; at most 20 000 characters per message; a scan stops after 60 s with "Stopped after 60 s; narrow your search". Building the plan has its own limit, `SCOPE_LIST_MS` = 30 s from the start (review N-R2: a hung Codex app-server held the plan up to 70 s per folder, with no progress shown): a listing still running at the limit is given up and the listings not started yet are skipped; those folders are counted per app (`notes.lateLists`, `notes.lateApps`) and the end state says "Not searched: earlier Codex sessions in N folders (no answer in time)". The scan's 60 s starts after the plan. Results are sent in batches of at most 20 hits, at most one batch per 250 ms. `[IMPLEMENTED]` for the scan core (`BUDGET` in `src/main/convsearch.ts`; test: `test-convsearch.ts`, `test-convsearch-corpus.ts` on a fake clock and a real-clock ceiling): the core stops and sets `timedOut`; the "Stopped after 60 s; narrow your search" text is the window's (phase 3).
- **FR-023** **Cancel**: `search:cancel(searchId)`, a new `search:start`, Escape, leaving the List view and closing the window all stop the scan before the next session; a session being read finishes its slice (no process is killed; the Codex probe is the existing short-lived app-server, left to end by itself). "One Codex call at a time" holds **across scans**, through one gate (`createReadGate`): an open Codex session's `thread/read` (over its own live connection; one that is no longer live when its turn comes is skipped) and each folder's Codex `thread/list` (the short-lived app-server that lists its earlier sessions, held up to `CODEX_LIST_GATE_MS`, above the probe's worst case, see FR-022 and FR-025). A new scan waits for, or reuses, a call already in flight and never starts a second one beside it. Earlier Codex sessions are title only in v1, so no `thread/read` is made for them. `[IMPLEMENTED]` for the scan core (`cancel()`, `createReadGate`; test: `test-convsearch.ts`); `search:cancel`, window close and quit in phase 2 (test: `test-convsearchipc.ts`); Escape and leaving the List view are phase 3. **Masking and privacy**

Decisions and differences:

- **T010**: main requires `sessionsearch.js` (and `safetext.js`) from the built tree (`rendererScript`, `<dist>/main/../renderer/`), as `profiles:generate` requires `profileeditor.js`; the build copies both and the package ships `dist/**`. No `src/shared/foldtext.ts` copy, so no parity corpus is needed: main runs the window's file (test: the same module object).
- **Windows (FR-030, review of phase 1, findings 1 and 2)**: a window is ±600 characters around the raw hit, then its left edge goes back to the start of its line and over the line before it (and blank lines), because some `redact` rules read context to the left on the same line or across up to 8 line ends: a `Cookie:` header masks its pairs to the line's end, the JSON `"Cookie": "` form to its quote, `curl ... -u user:pass`, a `.netrc` `machine ... password`, and a `name:` or `Authorization:` whose value is on a later line. A line start more than 1 200 characters back means the whole message is masked. A known secret value across an edge is taken whole (it may hold spaces and line ends); the left edge's rules (line start, value, `BEGIN`) repeat until the edge stops moving, at most 4 rounds, else the whole message is masked (the line rule alone could bring in only the tail of a value over several lines). A private key block opened before the window is masked from its `BEGIN` line; open means `KEY_BLOCK`'s own grammar (`openKeyBlockStart`, review of PR 1098, finding 2: an `-----END CERTIFICATE-----` does not close it); the check reads the text without hidden characters (`-----BEG` + zero-width space + `IN` is a BEGIN to the masks), and when hidden characters are there the whole message is masked. Then the window is widened to whitespace.
- **Edge guard (FR-030)**: an excerpt is cut only at least 200 characters inside a window edge that is not the message's own edge; a message the reader cut at 20 000 characters has no own edge there (review finding 3: a spaced value across the cut left its first word). When the guard fails the window grows (radius 600, then 1 800, then the whole message), and only then; a word missing from the masked window was masked away (A2) and nothing grows.
- **Work budget instead of `MASK_INPUT_MAX` (FR-022, FR-030, review finding 4)**: FR-030 names `MASK_INPUT_MAX` and `REDACT_MAX_CHARS`. `MASK_INPUT_MAX` replaces a whole argument over 12 288 characters by `[redacted]`; on messages it would hide most of every long reply, so it is not used. Instead each mask's cost is estimated before it runs (`maskWork`, in µs measured 2026-11-04 on the VPS for `maskNoteText`: 0.55 a character, 2.5 when a split mark is present; plus 250 per token-like run next to a mark, which `maskNoteText` checks on its own; plus 0.003 a character for each MCP secret value, which every pass looks for: 2 000 values over 20 000 characters took 50-108 ms before this term; doubled for hidden characters). The masks of one message may cost 25 ms (`BUDGET.messageWork`), and one mask as much (`MASK_CALL_WORK`; it was 15 ms, which refused whole masks of mid-size texts the message budget allows). Over it, that message shows no excerpt and counts as `bounded` (fail closed). Measured real time per message under the budget (token-dense or value-heavy, 20 000 characters): typically 15-25 ms, with spikes near 50-60 ms on the VPS under load (another build running); before the budget one such message took 75-260 ms. The estimate is not a real-time guarantee. The end state (FR-014, phase 3) says how many messages were too dense to search (`bounded`) and how many could not be masked (`maskFailed`). `REDACT_MAX_CHARS` (1 MB) is above every window and message, so it never cuts. Pitfall found on the way: a timer that samples the heap cannot run while a synchronous read blocks, so the corpus test also checks `process.resourceUsage().maxRSS` (moved here from agent-notes, which is at its word budget).
- **Scan robustness (review of PR 1098, findings 4, 5 and 7)**: a reader that throws costs its session only (counted as `unreadable`); a mask that fails for another reason than the budget is counted as `maskFailed` (titles too) and shows nothing, so a broken masker never reads as "no results"; the 60 s stop is checked in `halt`, which a reader asks between its lines, so a slow read stops at the limit too.
- **One cap (review of PR 1098, finding 6)**: `SEARCH_MAX_TEXT_CHARS` (`src/adapters/history.ts`) is the readers' cap and the scan's `BUDGET.maxChars`; a text at the cap counts as cut whether or not the reader added `…`.
- **`anchorKey` is linear (review of PR 1098, finding 3)**: a link's text (300) and address (2 000) are bounded and cannot hold the bracket or parenthesis that starts another try, so a run of `[` costs one pass (it took 489 ms at 20 000 characters). A link with a parenthesis in its address or nested brackets is left as written, the same in main and the window.
- **A match longer than an excerpt**: its start, cut on a code point, marked to the cut, then `…` (before, it gave no excerpt at all).
- **Hidden characters**: like `DurbarSafeText` (spec 097 FR-030), the masks also read a copy without default-ignorable and control characters, so a zero-width space cannot hide a token in an excerpt.
- **Title hit (FR-021)**: a session whose masked title holds every word is a hit at once and its messages are not read (no excerpt line, as US1.4 shows a title hit).
- **20 000 characters (FR-022)**: a longer message (the reader cut it) is cut back to the last whitespace before it is matched, so a token split by the cut is not searched half; the end state counts such messages only in sessions that did not match (the *Edge cases* rule).
- **Caps**: the 200 per folder applies to a folder's earlier sessions across apps; the 200-result cap stops the scan.
- **Excerpts**: one per word not yet confirmed in a message (so at most one per query word); the 3 shown are the first that add a word, then the next ones, in message order; `more` counts the rest.
- **FR-011 (review finding 6)**: the `Title:` excerpt prefix is dropped. ## Changes 2026-11-07: a hidden character that cannot hide a token costs only its scan (issue 1234, T065)

After 084 T012 (PR 1236) a message with any hidden character (`HIDDEN_CHARS`: an emoji joiner, a variation selector) was masked in three passes and priced x3 by `maskWork`: 1.65 per character, so a 20,000-character message with one emoji went over `MASK_CALL_WORK` (25,000) and dropped out of search. Change: a hidden character is **inert** when the characters on both sides of its run are non-ASCII, not spaces and not hidden (inside an emoji sequence or a script): every token shape is ASCII, so a token split or glued by a hidden character always has an ASCII neighbour. **Review of PR 1244 (pre-review, 2026-11-07):** that premise fails for a named secret (`password=` then a value): its value may be non-ASCII and its digit look-ahead counts up to 128 characters, hidden ones included, so `password=` + 64 `é` + ZWJ + 64 `é` + `1` was masked by the reference and left readable by the fast path. Chosen fix, the safe one: a text holding a secret name and a separator (`NAMED_HEAD`, built from `SECRET_NAMES`; widened below to `LIVE_HEAD`) is always live, whatever the characters beside the hidden ones; it costs the x3 only for a text that also has a hidden character and a secret name. Not chosen: dropping the ASCII premise whole (every emoji message would be priced x3 again, the issue's cost) and a bare 'non-ASCII follows a name' test (looser, same cost). Also, the plain-ASCII test of a known or environment value is `[\x20-\x7e]`, so a value with a space (`GIT_ASKPASS=/a b/askpass.sh`, set by VS Code on macOS and Windows) no longer changes the rule with the machine; the tests pin the environment. **Independent audit of PR 1244 (2026-11-07), five more families:** the same root cause, a bounded window (`{0,N}`, `{1,N}`) or a 128 loop over a class that admits non-ASCII, in netrc (host, login), `curl -u` (the window before it, the user), URL credentials (user, password), the JSON cookie and the Cookie header (`cookieEnd`'s name loop, a count in code); 4,348 failures in 60,000 seeded texts before the fix, none in 120,000 after. Fix: `NAMED_HEAD` becomes `LIVE_HEAD`, the secret-name head or `cookie` or `machine` + space or `curl` or `://`, tested text-wide (netrc's `\s{1,8}` crosses line breaks). **Trade-off, accepted:** a message with `://` (any link) or the word `cookie` takes the three-pass path when it also has a hidden character, so emoji messages with links lose part of the speed-up; a per-line guard is possible later.
