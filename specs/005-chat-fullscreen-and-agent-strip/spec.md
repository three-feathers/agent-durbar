## User Scenarios & Testing *(mandatory)*

### User Story 1 - Talk to an agent full screen (Priority: P1)

I click an agent; the chat fills the window. I see its status, task line, usage, model chip and folder, a thinking block, tool chips, the answer, and a composer.

**Independent Test**: `DURBAR_SIM=15`, click a desk, at 1440x900 and 1280x800; check for horizontal/page overflow (re-verified 2026-10-16: none).

**Acceptance Scenarios**:

1. **Given** the office, **When** I click a desk or press Enter on it, **Then** the chat opens full screen (top bar, floor and list are hidden) and focus moves to the agent's name. *(re-verified: panel opens; focus read:)*
2. **Given** the chat, **When** I press **Esc** or **Office**, **Then** the office returns and the desk I came from gets focus. *(read:)*
3. **Given** Enter in the message box, **When** the message is non-empty or has attachments, **Then** it sends; **Shift+Enter** adds a line; the box grows up to 110px. *(read:)*

---

### User Story 2 - Keep the overview in a strip (Priority: P1)

A 64px strip at the top shows every other visible agent (avatar, name, status dot and word, a short intent), scrolls horizontally, lists waiting and error agents first and highlights them. Clicking one switches the chat.

**Acceptance Scenarios**:

1. **Given** 15 agents, **When** a chat is open, **Then** the strip lists all 15 (the open one marked current). *(re-verified 2026-10-16: 15 strip items at both sizes)*
2. **Given** an agent starts waiting for me while I chat with another, **When** its status changes, **Then** it moves to the front of the strip and is highlighted. *(sim:)*
3. **Given** I switch agents, **When** the strip re-renders, **Then** its scroll position is kept and the current item is scrolled into view. *(read:)*

---

### User Story 3 - See the work (thinking, tools, approvals) (Priority: P2)

The turn shows a collapsible Thinking block (live counter "Waiting for the model · 4s" until text arrives, auto-collapses when the turn ends unless I touched it), tool chips (icon, name, one-line label, result; click to expand full command and output; latest 6 shown, `+N earlier`), the answer bubble with a caret while streaming, and permission notes inline (feature 003).

**Acceptance Scenarios**:

1. **Given** a turn with no reasoning text, **When** it ends, **Then** the block is replaced with "No reasoning summary was provided for this step." *(read:; real model behavior unverified, feature 013)*
2. **Given** 9 tool calls, **When** shown, **Then** 6 chips show with `+3 earlier`, expandable. *(read:)*

---

### User Story 4 - Stop, End, New session, Open in VS Code (Priority: P2)

Header actions: **Stop** (interrupt the turn; the agent stays ready), **End session** (frees it; sending resumes it), **+ New session** (feature 006), **Open in VS Code** (feature 009), **Copy resume command** (`copilot --resume <id>`).

**Acceptance Scenarios**:

1. **Given** a working agent, **When** I press Stop, **Then** the note "Stopped by you. The agent is ready for your next message." shows and the agent goes to Ready. *(test: broker part; sim:; **not verified on a real running turn**, feature 013)*
2. **Given** an ended agent, **When** I send a message, **Then** its session resumes and the message is delivered. *(read:; not verified on a real session)*

### 2026-10-21: file edits stream into the chat (owner report, Telegram 2026-10-21)

*Symptom (owner):* "Whenever an agent is editing files, nothing is shown in the chat. I have no clue what the agent is doing while I wait; only the number of seconds grows." The chat showed only "Working · 34s" while the model wrote an edit, and after it at best a chip with a bare tool name.

*Root cause (`read:` code, SDK typings and fixtures; no real session run):*
1. **The tool row appears only after the model has written the whole edit.** All three agent apps stream a tool call's arguments while the model writes them, and the adapters dropped that stream: Claude Code's `content_block_start` (`tool_use`) and `input_json_delta` stream events (`claudeMap.ts` read only text and thinking deltas, and emitted the tool `start` from the complete `assistant` message), Copilot's `assistant.tool_call_delta` (not mapped in `map.ts`; `tool.execution_start` comes after the arguments are complete), and Codex's `item/fileChange/patchUpdated` (not mapped in `codexMap.ts`). Writing a large file or a long `old_string`/`new_string` takes the model many seconds, and that is exactly the wait the owner saw.
2. **When the row did appear, it often had no file name.** The chat label takes the first string argument; Copilot's `apply_patch` sends one string (the patch, `real:` tool names and argument key names counted in local Copilot session logs, no content read), and Codex's `fileChange` was mapped to `{files: [...]}`, so both showed a bare `apply_patch`.
3. **No change was ever shown.** The edit's old/new text, patch or file content reached the renderer only as raw `args` (and was dropped for Codex). The only diff view is the permission card's *Show the change* (spec 052 FR-063), which a request in Allow all or a session grant never shows.
4. **The waiting line did not say what is going on.** "Working · Ns" counts the turn, whatever the agent does.

*Corrected (requirements):*

- **FR-018** `[IMPLEMENTED]` `test:` `test:edits`, `test:runtime` fixtures. Normalized edit payload (spec 002 event model, adapter-neutral): a `toolCall` event of a file-changing tool MAY carry `edit: { files: [{ path, kind, diff?, added?, removed?, movedTo? }], partial?, more? }`, where `kind` is `edit | create | write | delete | move`, `diff` is unified-diff text (`@@`, `+`, `-`, ` ` lines), `added`/`removed` are line counts, `partial` marks arguments still being written and `more` counts the files left out after the first 20 (FR-024). The event guard (`src/adapters/eventguard.ts`) rejects an `edit` with no files, a file without a path, an unknown `kind`, a non-string `diff` or `movedTo`, non-number counts or `more`, and a non-boolean `partial` (`test:edits`, negative cases). Each adapter builds it behind the adapter boundary from its own shapes: Claude Code `Edit`, `MultiEdit`, `Write`, `NotebookEdit`; Copilot `edit`, `create`, `str_replace_editor`, `apply_patch` (JSON or raw patch text); Codex `fileChange` changes. No provider type reaches `src/shared` or the renderer. Other tools never carry `edit`.
- **FR-019** `[IMPLEMENTED]` `test:` (fixtures `claude/edit-stream.json`, `codex/file-change-stream.json`, Copilot deltas in `test:edits`); `real:` 2026-10-21 Claude Code and Copilot (T036, below); `[KNOWN GAP]` Codex's `item/fileChange/patchUpdated` branch has no real recording (codex-cli 0.163.0 does not send it by default). Streaming start: the moment an adapter learns from the argument stream that a file-changing tool started **and which file** it touches, it emits the tool's `start` (with the path as `args`), then `update` events with `edit` (`partial: true`) as the arguments grow, and the complete arguments as an `update` (or `complete`/`failed` as usual). The later "whole call" message of the agent app does not add a second row. Adapters that give no argument stream show the row at the app's own start event (as before) and the change at that point. Only file-changing tools start early (other consumers of `start`, such as places and tool usage, keep the arguments they read today).
- **FR-020** `[IMPLEMENTED]` `sim:` `check:edits`, `test:` `test:edits` (editview). The chat shows a file-changing tool as an **edit row**: a verb in the present tense while it runs and the past tense when done ("Editing", "Creating", "Writing", "Deleting", "Moving"; "Edited", ...), the **file name in bold**, its folder in small text **relative to the agent's folder** (absolute only when the file is outside it), and the line counts "+12 −3". - **FR-028** **JSON results are shown formatted.** When the output of a finished tool call (`complete` or `failed`), or the preview of a saved output (FR-032), is a whole JSON object or array (after trimming spaces; it starts with `{` or `[` and `JSON.parse` accepts all of it), the open chip shows it pretty-printed (2-space indent, monospace, the same scrollable block, 20000 characters and "Show all" as spec 052 FR-063) instead of the raw text. A small **Show raw** / **Show formatted** toggle switches to the text as received from main (already masked, FR-030), and **Copy** copies the text of the view that is shown. The closed chip line says `JSON` and the size (for example "JSON · 12 KB", the size from `fmtSize`, FR-033) instead of the first 60 raw characters. Plain text, Markdown and anything that is not a whole JSON value is shown exactly as today. `update` events (streaming output) are never parsed.
- **FR-029** **Nested JSON strings are decoded, within limits.** Inside a parsed result, a string value whose trimmed text is itself a whole JSON object or array is replaced by its parsed value, and so on inside it, **up to 3 levels** of string-in-string. Strings that are not whole JSON, numbers in strings and JSON scalars in strings (`"true"`, `"12"`) stay strings. A line above the block says how many values were decoded ("2 nested values decoded from text"). Limits, all checked before work is done: input at most 1,000,000 characters (the chip's existing keep limit; main already cuts tool text to 50,000, FR-030, so this is a guard); each level only parses strings found by the level above, so the total parse work is at most 4 times the input; at most 50,000 values (objects, arrays and scalars) are visited; the formatted text is cut at 1,000,000 characters. When a limit is reached the chip shows the raw text with the note "Too large to format" (never a half-formatted view). The decoder is linear in its input: no regular expression runs over the whole text, and one long string or deep nesting (200 levels of `[`) does not make it slow or throw. The whole open-chip path (decode, then the page's `redact()` of FR-031) is measured together for linear time.
- **FR-030** **Every tool output is masked in main, raw and formatted (owner Q1 (a), 2026-10-21).** Main masks the text of every tool card before it leaves for the window or the `DURBAR_LOG` sink, in the `outward` hook (`src/main/main.ts:142`): the `output` of every `toolCall` event that carries one, in every phase (`update`, `complete`, `failed`; MCP or not), the `savedOutput.preview` of FR-032, and the `output` of every replayed history tool item (`HistoryItem` `type: 'tool'`, failed or not) in the `agents:wake` and `sessions:resume` replies (Q6). For history it **widens `maskMcpHistory`** (already behind the `maskHistory` dependency of both resume replies) from failed items to every tool item, so there is one path and no new code at the reply sites. Steps 1-2 are linear (about 7 ms per MB measured), so a session value, an env value or a token shape that straddles the cut is already gone and leaves no head; step 4 is the slow one (390-640 ms per MB of worst-case text) and only ever sees the cut text. **The cut** is `MCP_CARD_MAX_CHARS`, 50,000 characters, for every tool card and history item, MCP or not (Q5): one constant, the same as #466's MCP cards, about 46 ms in the worst case and 4 ms on ordinary JSON. One exported helper in `src/shared/redact.ts` (`secretForms(value)`: the value, its JSON-escaped forms 1 to 4 times, each `JSON.stringify(x).slice(1, -1)` of the one before, and its URL-encoded form, without duplicates) is used by `envSecrets` (widened from today's once and twice escaped forms, so the env snapshot gains the 3rd and 4th forms, computed once per env) and by `maskMcpText` for the session values. A value with no `"`, `\` or control character has one form only, so the extra cost is for such values alone. The renderer only formats text that is already masked: the raw view and **Copy** of the raw text show what main sent, and the page adds no masking rule of its own beyond FR-031.
- **FR-031** **The formatted view is masked again after decoding, in the page.** The formatted text passes through the page's `window.DurbarRedact.redact` (the module the live-activity readout uses, spec 001 FR-031) **after** decoding, because a key that was hidden behind escaped quotes (`\"Authorization: Bearer …\"`) only takes a maskable shape once decoded. In the sandboxed page this masks token shapes only; env and session values were already removed by main (FR-030). No masking rule is copied into the renderer. Fail closed: when `DurbarRedact` is missing the formatted view is off and the chip shows the raw text (already masked by main).
- **FR-032** **Invalid or cut JSON falls back to text.** A result that only looks like JSON (cut at 4000 or 2000 characters by an adapter, a 500-character preview cut in the middle, a trailing log line, invalid escapes) is shown as plain text, unchanged, with no error and no partial formatting. ### 2026-10-29: order the chat strip by hand, and favourites that stay first (owner, issue #880)

*Owner request (Paco, issue #880, 2026-10-29):* with a chat open, the strip (`renderStrip` / `stripAgents` in `src/renderer/app.js`) is ordered by `prio` (waiting, then error, then creation order, FR-007 of spec 001). The owner wants to order it himself, and to mark favourites that always show.

*Why a delta here:* the strip is this spec's User Story 2 and FR-002; nothing about it is a new feature area, so no new spec number is taken (096 stays free).

*What exists (read:):* `stripAgents()` (`app.js:5702`, `prio` at `app.js:607`), `renderStrip()` (`app.js:5705`, a keyed `morphHTML` of `button.sitem[data-sw]`), the click that opens a chat (`app.js:3112`), the scroll kept across repaints (`app.js:2340`, `2368`) and the current item revealed (`app.js:2432`), the card menu (`openModeMenu` with `DMK().cardMenuActions`, `Mark as read` of FR-177), `announce()` (`app.js:3373`), `rememberOn()` and the per-window `localStorage` ids (`durbar.chatNo`, `durbar.crew`, `durbar.ui`; `syncChatNos` prunes ids that left the list), the shortcut sheet `openKbdHelp` (`app.js:3636`). **Missing:** any way to reorder, any favourite, any drag-to-reorder code (the only drag code is the file drop, `app.js:2407`). **There is no "+N more" in the strip**: it is a horizontal scroller (`.strip-list`, `overflow-x:auto`, items 196px wide); "+N more" belongs to the office's helper strip. The owner's "never fall into +N more" is read here as "never scroll out of reach behind other sessions" (Q-strip-1).

*Corrected / added (all `[KNOWN GAP]` until built):*

- **FR-178** **Manual order.** The person can move a session in the strip by **dragging** it (mouse, touchpad or pen) or with **Alt+Left / Alt+Right** on the focused item (FR-182). The order is saved and survives a restart (FR-184).
- **FR-179** **A manual order is respected.** Once the person has moved any session, the strip no longer uses `prio`: a session that starts waiting, failing, retrying or in error does not move. It keeps its place and keeps its colour, attention cue, word and badge (FR-002 is unchanged for these); **Needs you** (`N`, the inbox, notifications) still opens it. Until the first move nothing changes: today's `prio` order, then creation order (the "manual" flag is false and no key is written).
- **FR-180** **Favourites.** A session can be marked as a favourite with a star. Favourites come first in the strip (before every non-favourite), in the order the person gave them (starring order until moved), each shows a star mark, and they are never hidden behind others (Q-strip-1). The star exists only in the strip: not in List, the office or the palette, and it is not kept after the session ends (FR-185).
- **FR-181** **The star is a control with a name and state.** A real `button` next to the strip item (never a button inside the item: the item is a `button`), `aria-pressed` true or false, name "Favourite: <session name>", the same toggle in the card menu as **Add to favourites** / **Remove from favourites** (the menu of the strip item, FR-017's menu, opened by right-click, Shift+F10 or the Menu key). Pressing it moves the item to the end of the favourites (starring) or to the start of the non-favourites (unstarring) and announces it (FR-183). The star is 28px high at most, text and glyph at least 10.5px, never colour alone (a filled and an outlined star plus the name).
- **FR-182** **Keyboard.** On a focused strip item: **Alt+Left** moves it one place towards the start, **Alt+Right** one place towards the end, within its group (a favourite among favourites, a non-favourite among non-favourites; at the end of its group nothing moves and the announcement says so). Only with **no** Ctrl, Cmd or Shift (AltGr on Windows layouts reports Ctrl+Alt and is ignored). Focus stays on the moved item and it is scrolled into view (`SCROLL.reveal`). Checked against the existing keys (read:): the chat answer keys are Alt+letter (`keys.js`; Option+Cmd+letter on a Mac), the navigator is Ctrl/Cmd+F, the desk arrows need no modifier (`app.js:3211`), the browser pane ignores any Alt (`browserpane.js:283`), and the app menu (`src/main/appmenu.ts`) has no Alt+arrow accelerator. On a Mac, Option+arrow is "move by word" only inside a text field; the strip has none. `[KNOWN GAP]` not tried with a real screen reader (NVDA, JAWS, VoiceOver) nor on a Linux desktop that grabs Alt+arrows; the plain buttons (FR-181) are the keyboard path for those.
- **FR-183** **Announcements.** Every move, by drag or keys, is announced politely (`announce`): "Moved C12 to position 3 of 9" (the chat number when there is one, else the name; "favourite" is said for a favourite: "Moved C12, a favourite, to position 2 of 4 favourites"); starring: "C12 is now a favourite, position 3 of 3"; unstarring: "C12 is no longer a favourite". The strip is a `navigation` with an accessible description of the shortcut ("Alt+Left and Alt+Right move the focused session"), and the shortcut sheet (`?`) gains the row **Alt+Left / Alt+Right: Move the focused session in the chat strip** (on a Mac: Option).
- **FR-184** **Saved, per window, no secrets.** `localStorage` key `durbar.stripOrder`, JSON `{"v":1,"manual":true,"order":["<id>",...],"favs":["<id>",...]}` (session ids only, like `durbar.chatNo`), written only when `rememberOn()` (not in the simulator or the demo, like the chat numbers and the character map). Missing, unparsable, wrong-typed or oversized data (more than 500 ids, ids longer than 200 characters, duplicates) loads as "no manual order, no favourites", never an error; the key is removed when both lists are empty. No key existed before, so there is no migration; nothing else is read or written.
- **FR-185** **The order rule (pure, `src/renderer/striporder.js`).** Given the strip's agents (main agents on shown floors, as `stripAgents` filters today), the saved `order` and `favs`: (1) drop saved ids that are not among the agents once the real list is loaded (`agentsListed`), like `pruneNumbers`: an **ended** session leaves the order and the favourites and its slot closes, with no gap; before the list is loaded the saved ids are kept; (2) a **new** session (id not in `order`) goes to the **end of the non-favourites**, appended to `order` in `prio` then creation order among several new ones; (3) favourites first (in `favs` order), then the rest in `order`; (4) with `manual` false: favourites first, then today's `prio` order for the rest. Hidden floors: a session on a floor that is off is not drawn but keeps its saved place for when the floor is on again (the saved lists are only pruned by (1)). A helper is never in the strip (unchanged).
- **FR-186** **Drag.** Pointer events on the item (not the HTML5 drag-and-drop, which a touchpad tap-drag and the headless driver handle badly): a press moved more than 6px starts a drag; the dragged item follows the pointer horizontally, the others make room, the drop is where the item's centre is; Esc or a drop outside the strip cancels; the strip scrolls by itself when the pointer is within 40px of its edge (reduced motion: the same, no easing). A drag never opens the chat (the click after a drag is swallowed); a click without movement still opens it. An item cannot be dropped across the favourites boundary: dragging a favourite past the last favourite stops there (starring and unstarring are the star, FR-181). The focus ring and the star stay usable, and the dragged item is not announced as "grabbed" (no live drag state for a screen reader: the keys are the equivalent).
- **FR-187** **Calm and sized.** The strip stays 48px high (spec 052 FR-085 keeps its macOS drag rules: the scroller stays `no-drag`, the grab area at its right end is unchanged); an item is 196px wide, the star adds at most 28px to a favourite's group, so 15 agents still scroll in the strip and the chat, the header and the office are unchanged at 1440x900 and 1280x800. No new animation except the others making room during a drag (`transform`, 120ms; none under `prefers-reduced-motion`). Text at least 10.5px; colours from theme tokens only; the six built-in themes lay it out alike.
- **FR-188** **Needs you is still found.** A manual order can leave a waiting session off screen. The existing ways stay and are checked: `N`, the inbox, the notification and **Needs you** open it, and opening any chat scrolls its item into view. No new cue is added (the owner's answer to Q-strip-2): these ways are enough.
- **FR-189** **Reset.** The strip item's menu has **Reset strip order** (visible only when `manual`): it clears `order` and `manual` (favourites stay) and the strip goes back to `prio`. Announced: "Strip order reset". (Q-strip-3.)

*Edge cases (each has a test, tasks T099..T112):* a single session (move keys do nothing, announced "only session"); the first/last item; a session that needs you while ordered by hand (stays put); a session that ends while dragged (the drag cancels); the same id starred twice (idempotent); a favourite that ends (removed, strip shifts); a new session while a manual order exists (end of non-favourites, not the front, even when it needs you); a floor switched off and on again (place kept); a duplicate or non-string id in storage; storage unavailable (`localStorage` throws: the order works for this run and is not saved); two windows (last write wins; not synchronised, `[KNOWN GAP]`); RTL is not a supported layout (the arrows follow the visual left/right); a rename or title change keeps the place (the id is the key).

*Acceptance (given/when/then):* (1) **Given** 4 sessions and no move, **When** B starts waiting, **Then** B is first (today). (2) **Given** I dragged D to the front, **When** B starts waiting, **Then** D is still first and B has not moved, B shows its waiting colour and word, and `N` opens B. (3) **Given** A,B,C,D, B focused, **When** I press Alt+Right, **Then** the order is A,C,B,D, focus is on B, and the announcement says "Moved ... to position 3 of 4". (4) **Given** C is starred, **Then** C is first with a star; **When** I restart the app, **Then** C is still first (only if C's session is still there). (5) **Given** 15 simulated agents and 4 favourites, **Then** the 4 favourites are the first four items and the strip still fits (FR-187). (6) **Given** a favourite's session ends, **Then** it is gone from `favs` and the saved key. (7) **Given** a new session starts, **Then** it is after the last non-favourite. (8) **Given** the keyboard only, **Then** every action (move, star, reset) is possible and announced.
