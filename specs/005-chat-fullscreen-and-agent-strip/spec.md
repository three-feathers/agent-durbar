# Feature Specification: Full-screen chat and agent strip

**Feature Branch**: `005-chat-fullscreen-and-agent-strip` (reverse-engineered; milestone 6, built on the chat panel of milestones 1-5)
**Created**: 2026-10-16
**Status**: Implemented (reverse-engineered from `src/renderer/app.js`, `styles.css`, README)
**Input**: "Opening an agent replaces the office with the chat; every other agent stays visible in a slim strip so I never lose the overview."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Talk to an agent full screen (Priority: P1)

I click an agent; the chat fills the window. I see its status, task line, usage, model chip and folder, a thinking block, tool chips, the answer, and a composer.

**Independent Test**: `DURBAR_SIM=15`, click a desk, at 1440x900 and 1280x800; check for horizontal/page overflow (re-verified 2026-10-16: none).

**Acceptance Scenarios**:

1. **Given** the office, **When** I click a desk or press Enter on it, **Then** the chat opens full screen (top bar, floor and list are hidden) and focus moves to the agent's name. *(re-verified: panel opens; focus read:)*
2. **Given** the chat, **When** I press **Esc** or **Office**, **Then** the office returns and the desk I came from gets focus. *(read:)*
3. **Given** Enter in the message box, **When** the message is non-empty or has attachments, **Then** it sends; **Shift+Enter** adds a line; the box grows up to 110px. *(read:)*

---

### User Story 2 - Keep the overview in a strip (Priority: P1)

A 64px strip at the top shows every other visible agent (avatar, name, status dot and word, a short intent), scrolls horizontally, lists waiting and error agents first and highlights them. Clicking one switches the chat.

**Acceptance Scenarios**:

1. **Given** 15 agents, **When** a chat is open, **Then** the strip lists all 15 (the open one marked current). *(re-verified 2026-10-16: 15 strip items at both sizes)*
2. **Given** an agent starts waiting for me while I chat with another, **When** its status changes, **Then** it moves to the front of the strip and is highlighted. *(sim:)*
3. **Given** I switch agents, **When** the strip re-renders, **Then** its scroll position is kept and the current item is scrolled into view. *(read:)*

---

### User Story 3 - See the work (thinking, tools, approvals) (Priority: P2)

The turn shows a collapsible Thinking block (live counter "Waiting for the model · 4s" until text arrives, auto-collapses when the turn ends unless I touched it), tool chips (icon, name, one-line label, result; click to expand full command and output; latest 6 shown, `+N earlier`), the answer bubble with a caret while streaming, and permission notes inline (feature 003).

**Acceptance Scenarios**:

1. **Given** a turn with no reasoning text, **When** it ends, **Then** the block is replaced with "No reasoning summary was provided for this step." *(read:; real model behavior unverified, feature 013)*
2. **Given** 9 tool calls, **When** shown, **Then** 6 chips show with `+3 earlier`, expandable. *(read:)*

---

### User Story 4 - Stop, End, New session, Open in VS Code (Priority: P2)

Header actions: **Stop** (interrupt the turn; the agent stays ready), **End session** (frees it; sending resumes it), **+ New session** (feature 006), **Open in VS Code** (feature 009), **Copy resume command** (`copilot --resume <id>`).

**Acceptance Scenarios**:

1. **Given** a working agent, **When** I press Stop, **Then** the note "Stopped by you. The agent is ready for your next message." shows and the agent goes to Ready. *(test: broker part; sim:; **not verified on a real running turn**, feature 013)*
2. **Given** an ended agent, **When** I send a message, **Then** its session resumes and the message is delivered. *(read:; not verified on a real session)*

### 2026-10-21: readable JSON tool results, and outputs the agent app saved to a file (issue #361, tasks T038..T048)

*Numbering:* PR #463 (`005-chat-edit-stream`, open) uses FR-018..FR-027 and T027..T037 in this spec, so this delta starts at FR-028 and T038.

*Found by the owner* (2026-10-20, a Copilot session with an MCP tool that returns JSON): an open tool chip (FR-006, widened by spec 052 FR-063) shows the result as raw text. When the tool returns JSON whose string fields are themselves JSON (`{"rawResponse":"{\"value\":[...`), the text is full of `\"` and hard to read. When the output was larger than the runtime's limit, Copilot wrote it to a temporary file and gave the model only a short preview; the chip does not say so, and in Read-only or Ask first the agent's attempt to read that file (outside the session's folders, spec 003 FR-023) is refused or asks, so the agent can look stuck.

*What exists today* (`read:` the code on `main` at 033caeb, 2026-10-21, and open PR #466 at its head `e0bb4ee`):
- The chip shows `ToolCallEvent.output` as escaped text: `makeChip` in `src/renderer/app.js` (`OUT_SHOWN` 20000 characters shown, "Show all" up to `OUT_KEEP` 1,000,000, `src/renderer/app.js:1055`; closed line `SHORT(output, 60)` from `tTool`). Nothing is parsed as JSON.
- Masking on the way out of main: `outward()` (`src/main/main.ts:142`) is the one copy every path out of main uses (the `agent:event` send and the `DURBAR_LOG` sink, `src/main/main.ts:225`). On `main` it masks `mcp` events only (`maskMcpEvent`, `src/main/mcpmask.ts:36`, spec 019 FR-022). Open PR #466 (spec 058 FR-067, T097) adds `maskMcpText(text, values, max?)` to `src/main/mcpmask.ts` and applies it in `outward` to the `output` of **every MCP `toolCall` after its start** (`update`, `complete` and `failed` events that name an `mcpServer`), cut to `MCP_CARD_MAX_CHARS` (50,000). Its order: (1) the session's MCP secret values and (2) `redact()` (env secret values with their escaped forms, then token shapes), both on the **whole** text; (3) the cut to `max` at a token boundary; (4) only the URL and flag masks (`maskSecretUrl`, `maskFlagValues`) on the shorter text. Not masked before the window gets it: the output of every non-MCP tool (shell, read, edit, any tool without `mcpServer`) in every phase, and a Copilot output whose start event was not seen (#466's FR-067 `[KNOWN GAP]`). `makeChip` only escapes.
- Replayed history: a resumed session's tool items (`HistoryItem` `type: 'tool'`, `output`, `failed?`, `src/adapters/history.ts:114`; no `mcpServer`) go to the window in the `agents:wake` and `sessions:resume` replies (`src/main/ipc/agents.ts:170`, `src/main/ipc/previous.ts:81`). PR #466 passes both through one `maskHistory(id, h)` dependency (wired in `src/main/main.ts`), which calls `maskMcpHistory(h, mcp.secretValuesFor(id))` in `src/main/mcpmask.ts`: it masks the `output` of **failed** tool items only, the same way and with the same 50,000 cut as a live MCP card. Not masked: the output of every tool item that did not fail.
- Env secret values already have escaped forms: `envSecrets` in `src/shared/redact.ts:29-43` adds, for each secret env value, the value once and twice JSON-escaped and URL-encoded (`:36-39`), so `redact()` removes those forms too. Three and four times escaped forms are not covered, and the session's MCP values get no escaped forms at all.
- Cost, measured (`read:` and run on 2026-10-21, `node` on a 4-core Linux VPS, `redact.ts` from `main`, 1,000,000 characters of `?a=&`, the worst case for the URL pass): `redact()` 5-7 ms per MB; `maskSecretUrl` 640 ms per MB (Vikram's agent measured about 390 ms per MB on its machine, review on PR #465), 46 ms on 50,000 characters and 11 ms on 20,000; on ordinary JSON with URLs, 73 ms per MB and 3.6 ms on 50,000. `maskFlagValues` was not timed (unverified).
- The window is sandboxed (`sandbox: true`, `nodeIntegration: false`, `src/main/main.ts:659`), so the page's `window.DurbarRedact` (`src/shared/redact.ts`, spec 001 FR-031, used by the live-activity readout through `liveact.js`) has no `process.env` and no session values: in the page it can mask token **shapes** only.
- Adapters: Copilot takes `result.content` (`contentOf` in `src/adapters/map.ts`), Claude Code keeps the first 4000 characters of the `tool_result` text (`TOOL_OUTPUT_CAP`, `src/adapters/claudeMap.ts`), Codex the first 2000 (`CODEX_OUTPUT_CAP`, `src/adapters/codexMap.ts`). So a long JSON result often reaches the page cut in the middle.
- The attachments code already formats sizes: `fmtSize` (`src/renderer/app.js:1178`) gives "1.2 MB" (one decimal, `.0` dropped) and whole kilobytes ("34 KB", never below "1 KB", never "B").

*Specified* (not built; `[KNOWN GAP]` until T038..T046 and T048 are done; T047 is the real check):

- **FR-028** **JSON results are shown formatted.** When the output of a finished tool call (`complete` or `failed`), or the preview of a saved output (FR-032), is a whole JSON object or array (after trimming spaces; it starts with `{` or `[` and `JSON.parse` accepts all of it), the open chip shows it pretty-printed (2-space indent, monospace, the same scrollable block, 20000 characters and "Show all" as spec 052 FR-063) instead of the raw text. A small **Show raw** / **Show formatted** toggle switches to the text as received from main (already masked, FR-030), and **Copy** copies the text of the view that is shown. The closed chip line says `JSON` and the size (for example "JSON · 12 KB", the size from `fmtSize`, FR-033) instead of the first 60 raw characters. Plain text, Markdown and anything that is not a whole JSON value is shown exactly as today. `update` events (streaming output) are never parsed.
- **FR-029** **Nested JSON strings are decoded, within limits.** Inside a parsed result, a string value whose trimmed text is itself a whole JSON object or array is replaced by its parsed value, and so on inside it, **up to 3 levels** of string-in-string. Strings that are not whole JSON, numbers in strings and JSON scalars in strings (`"true"`, `"12"`) stay strings. A line above the block says how many values were decoded ("2 nested values decoded from text"). Limits, all checked before work is done: input at most 1,000,000 characters (the chip's existing keep limit; main already cuts tool text to 50,000, FR-030, so this is a guard); each level only parses strings found by the level above, so the total parse work is at most 4 times the input; at most 50,000 values (objects, arrays and scalars) are visited; the formatted text is cut at 1,000,000 characters. When a limit is reached the chip shows the raw text with the note "Too large to format" (never a half-formatted view). The decoder is linear in its input: no regular expression runs over the whole text, and one long string or deep nesting (200 levels of `[`) does not make it slow or throw. The whole open-chip path (decode, then the page's `redact()` of FR-031) is measured together for linear time.
- **FR-030** **Every tool output is masked in main, raw and formatted (owner Q1 (a), 2026-10-21).** Main masks the text of every tool card before it leaves for the window or the `DURBAR_LOG` sink, in the `outward` hook (`src/main/main.ts:142`): the `output` of every `toolCall` event that carries one, in every phase (`update`, `complete`, `failed`; MCP or not), the `savedOutput.preview` of FR-032, and the `output` of every replayed history tool item (`HistoryItem` `type: 'tool'`, failed or not) in the `agents:wake` and `sessions:resume` replies (Q6). It reuses `maskMcpText` from `src/main/mcpmask.ts` (spec 058 FR-067, PR #466), generalised from MCP cards after their start to every tool card, with the session's own secret values (`mcp.secretValuesFor(sessionId)`) for every such event, not only MCP ones. For history it **widens `maskMcpHistory`** (already behind the `maskHistory` dependency of both resume replies) from failed items to every tool item, so there is one path and no new code at the reply sites. No second masker is written. **Order** (#466's, unchanged): (1) the session values, in all their forms below, are removed from the **whole** text; (2) `redact()` runs on the whole text (env secret values in all their forms, then token shapes; `redact()`'s own 1,000,000 cut sits between the two); (3) the text is cut at a token boundary (`cut()`, `src/shared/redact.ts:49`); (4) only the URL and flag masks run on the shorter text. Steps 1-2 are linear (about 7 ms per MB measured), so a session value, an env value or a token shape that straddles the cut is already gone and leaves no head; step 4 is the slow one (390-640 ms per MB of worst-case text) and only ever sees the cut text. **The cut** is `MCP_CARD_MAX_CHARS`, 50,000 characters, for every tool card and history item, MCP or not (Q5): one constant, the same as #466's MCP cards, about 46 ms in the worst case and 4 ms on ordinary JSON. The chip still shows 20,000 characters and "Show all" now reaches at most 50,000; a longer output ends in `cut()`'s ` [truncated]` mark, and a cut JSON result falls back to text (FR-032). **Escaped forms.** A secret value can hide in nested JSON, where each level of string-in-string escapes it once more; FR-029 decodes 3 levels inside the JSON document, so the value can appear escaped up to 4 times. One exported helper in `src/shared/redact.ts` (`secretForms(value)`: the value, its JSON-escaped forms 1 to 4 times, each `JSON.stringify(x).slice(1, -1)` of the one before, and its URL-encoded form, without duplicates) is used by `envSecrets` (widened from today's once and twice escaped forms, so the env snapshot gains the 3rd and 4th forms, computed once per env) and by `maskMcpText` for the session values. A value with no `"`, `\` or control character has one form only, so the extra cost is for such values alone. The renderer only formats text that is already masked: the raw view and **Copy** of the raw text show what main sent, and the page adds no masking rule of its own beyond FR-031.
- **FR-031** **The formatted view is masked again after decoding, in the page.** The formatted text passes through the page's `window.DurbarRedact.redact` (the module the live-activity readout uses, spec 001 FR-031) **after** decoding, because a key that was hidden behind escaped quotes (`\"Authorization: Bearer …\"`) only takes a maskable shape once decoded. In the sandboxed page this masks token shapes only; env and session values were already removed by main (FR-030). No masking rule is copied into the renderer. Fail closed: when `DurbarRedact` is missing the formatted view is off and the chip shows the raw text (already masked by main).
- **FR-032** **Invalid or cut JSON falls back to text.** A result that only looks like JSON (cut at 4000 or 2000 characters by an adapter, a 500-character preview cut in the middle, a trailing log line, invalid escapes) is shown as plain text, unchanged, with no error and no partial formatting. A value nested in a string that fails to parse stays the string it was.
- **FR-033** **Normalized "saved to a file" flag.** `ToolCallEvent` gets an optional `savedOutput?: { bytes?: number; place: 'temp' | 'app'; preview?: string }` (`src/adapters/types.ts`), set by an adapter on the `complete` or `failed` event when its agent app reports that the full output was written to a file and the model got only part of it. `bytes` is the full size when the app states it (parsed from "33.8 KB", "49.4KB", "1.2 MB"); `place` is `temp` for a temporary folder (Copilot) and `app` for the agent app's own folder (Claude Code); `preview` is the part the app showed the model (the text after its "Preview" line), cut at the adapter's output cap, and masked in main with the output (FR-030). The **file path is never put in the flag**, and Durbar **never opens, reads, copies or lists the file**. Detection lives only in the adapter's mapper: Copilot (`src/adapters/map.ts`) from the "too large to read at once … Saved to:" text whose path's file name matches the runtime's own `copilot-tool-output` pattern, or from a `largeOutputWrittenToFile` telemetry flag if it is present; Claude Code (`src/adapters/claudeMap.ts`) from the `<persisted-output>` wrapper, read before the 4000-character cap; Codex sets nothing. The detection accepts both `/` and `\` separators (a Windows path such as `C:\Users\me\AppData\Local\Temp\…-copilot-tool-output-….txt`). The event guard (`src/adapters/eventguard.ts`, spec 010 FR-021) checks the field's shape. A tool whose own output imitates the marker only changes this one display line (it grants nothing and opens nothing).
- **FR-034** **One plain line for a saved output.** When `savedOutput` is set, the open chip starts with one line: "The full output (34 KB) was saved to a temporary file; the agent may ask to read it." (`place: 'app'`: "…was saved to a file in the agent app's own folder; …"; no size known: "The full output was saved to …"). The size is formatted by the renderer from `bytes` with the existing `fmtSize` (`src/renderer/app.js:1178`, the attachments' formatter), so the chat and the attachments use one rule: one decimal for megabytes, whole kilobytes, at least "1 KB". The closed chip line says "Saved to a file (34 KB)". Below the line the chip shows the `preview` (formatted per FR-028 when it is whole JSON, else as text). In **Simple** mode the raw text with the app's instructions and the full path is not shown; in **Expert** the **Show raw** toggle shows the output as the model received it, after main's masking (path included, because that is what the agent saw). No string of any one agent app is matched in `src/renderer`; the renderer reads only the normalized field.
- **FR-035** **Hint on the permission card (optional).** `PermissionInfo` gets an optional `savedOutput?: true`, set by the adapter on a `read` request (or a shell request whose command names the file) for a file it flagged under FR-033 in the same session. The match uses only the base names the adapter kept in memory (never sent to the page): a `read` path's base name (split on `/` and `\`) must equal a remembered name exactly; a shell command matches when it contains a remembered name as a plain substring (`includes`), never through a regular expression built from or run over the command. The pending card, the Needs you inbox row and the Read-only refusal note then add one muted line: "This is the file where the agent app saved a large tool output earlier."
