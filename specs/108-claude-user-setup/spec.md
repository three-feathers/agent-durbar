## Summary

A Claude Code session started from Durbar does not behave like the same person's `claude` in a terminal, because Durbar launches Claude with `--setting-sources ""` (spec 012 Q8). The folder's `CLAUDE.md` is passed, but the person's own `~/.claude/CLAUDE.md` is not, and the person's agent files are offered only as the one profile a session starts with (spec 043 FR-008), never as sub-agents the session can hand work to. A "coordinator" way of working (the main session plans and delegates to named agents such as `analyst`, `implementer`, `reviewer`) cannot run in Durbar.

This feature adds **one switch in Settings, off by default**: *Use my Claude Code instructions and agents*. While it is on, each Claude session launch also gets:

1. the person's `CLAUDE.md` from their Claude folder, with its `@` imports **inside that folder only**, as instructions (beside the folder's `CLAUDE.md`, through the same reader and budget);
2. the person's agent files (`<Claude folder>/agents/*.md`) as **sub-agents**: one `--agents` definition with several entries, **without** `--agent`, so the main session can delegate to them. A folder's own agent files are **not** offered as sub-agents in this version (Q7; the owner's decision names "your own" agents).

Only the items the person ticked in Settings' checklist are sent (section L): nothing is sent until something is ticked.

Nothing else from the Claude folder is read, and nothing the person did not tick is sent. Settings files stay off, Durbar's mode still decides every permission, and nothing read is stored, logged or shown unmasked.

## User scenarios

- **US1 (P1) Turn it on knowingly.** *Given* Settings > Agent apps > Claude Code, *Then* I see the switch **Use my Claude Code instructions and agents**, off, and under it one plain sentence of what it loads and what it never loads. *When* I press **Check what loads**, *Then* I see the file names, sizes and counts it would use (no file text), and what it would skip and why. *When* I turn it on, *Then* the row says "On. Applies to Claude sessions that start or restart from now on." and nothing is read until a session launches.
  - *Given* the switch on and my `CLAUDE.md` saying "Answer in Spanish", *When* I start a Claude session in any folder and send a message, *Then* the CLI got my `CLAUDE.md` text (with its imports from my Claude folder) as appended instructions, and no other launch flag changed except the ones this spec names.
- **US2 (P1) A coordinator delegates to my named agents.** *Given* the switch on, `analyst.md` and `reviewer.md` in my agents folder, and the session in Ask first, *When* the main session hands a task to `analyst`, *Then* the office shows a helper named *Helper · analyst*, its tool calls ask through the same permission cards as the main session, and it can do nothing the mode does not allow.
- **US3 (P1) Off means today's behaviour.** *Given* the switch off (the default), *Then* no file in my Claude folder is read for instructions or sub-agents (the profile list of spec 043 keeps working as today), and the launch flags are byte-for-byte today's.
- **US4 (P2) A folder's agents are not helpers.** *Given* the switch on and a folder with `.claude/agents/deploy.md`, *Then* `deploy` is not offered as a sub-agent (Q7, default); it stays available as a session profile through spec 043's confirmation, as today.
- **US7 (P1) Pick what loads, easily.** *Given* I turn the switch on, *Then* Settings lists what it found in my Claude folder in plain words: *Your instructions (CLAUDE.md)*, each file it imports, and each agent by name, each with its size, its masked first line and one sentence of what Claude will see, and **nothing is ticked**. *When* I press **Pick for me**, *Then* CLAUDE.md, its allowed imports and every agent are ticked; **Select all** and **Select none** do the same in one click; I never type a path. *When* I add a new agent file later and press **Check what loads**, *Then* it appears unticked with *New*, and it is not sent until I tick it.
- **US5 (P2) Nothing leaks.** *Given* the switch on and a token-shaped string in an agent's name or in my `CLAUDE.md`, *Then* Settings, the helper name, the debug log, Diagnostics, saved settings and screenshots never show it unmasked; Durbar's saved files hold only the switch.
- **US6 (P3) Keyboard and screen reader.** *Given* keyboard only, *Then* Tab reaches the switch and **Check what loads**, Space toggles, and the result is read by the row's polite status region; the switch has a name and a description that says what it loads.

## Edge cases

- No Claude folder, no `CLAUDE.md`, an empty one, or no `agents` folder: nothing is added for that part; the session starts as today; **Check what loads** says "No CLAUDE.md found" / "No agents found".
- `CLAUDE_CONFIG_DIR` set: that folder is the Claude folder everywhere (FR-003), and Settings names it (home part masked).
- The Claude folder itself is a symlink (common with dotfiles): its `realpath` is the root; files inside it are fine. A file or import whose `realpath` leaves the root is skipped and **counted** as "points outside your Claude folder" (no path shown, FR-020). An `agents` folder or a `CLAUDE.md` that is itself a link to outside the root: FR-043 and Q8.
- An import names `.credentials.json`, `settings.json`, a session file, history, memory (`projects/*/memory/*.md` included) or any other file outside the allow-list (FR-004, FR-005): skipped and counted as "not offered", left as plain text; never listed in the checklist.
- A ticked item disappears or changes kind (a file becomes a link, a folder): it is not read at launch, the checklist shows it as *Missing* or *Not allowed now*, and the session starts without it.
- Durbar crashed or was killed while a session ran: its private launch folder may hold a copy of the person's instructions until the next start, which sweeps it (FR-038).
- Import cycles, the same file twice, depth over 4, `@` inside code fences or inline code, URLs and e-mail-like tokens: as `claudeMdPrompt` handles them today.
- A huge, binary, NUL-holding, invalid UTF-8, BOM or CRLF file; a front matter that never closes; 10,000 front matter lines; a name `__proto__`, `constructor` or `prototype`; a `tools:` list of 10,000 entries; a name clash between a user agent, a folder agent and the chosen profile (FR-012, FR-013).
- More than 50 agent files in total: the first 50 by the existing order (folders first, then the user's, each sorted by file name) are read; the rest are counted as "not read: over 50 files".
- The person also chose a profile for the session (spec 043): the profile stays the session's own agent (`--agent`), and the sub-agents are offered beside it (FR-011).
- The switch or the ticks change while sessions run: running CLI processes keep what they got; the next launch of each session (first message, resume, relaunch after a mode or model change) uses the new value, except that a resumed session may keep its earlier `--agents` set (FR-027, FR-039).
- Read-only: the instructions apply; delegation is refused as today (Q3, answered (a) 2026-11-09). The row says so.
- The installed Claude Code is older than the version these flags were checked on, or its version cannot be read: see FR-016.
- The Claude folder is on a slow or network drive: reads are bounded (FR-008) and never block the window.

## Requirements

### A. The switch

- **FR-001** **One global switch, off by default.** `AppSettings.claudeUserSetup?: true`: only `true` is written, absent means off; any stored value other than `true` reads off (fail closed). Setter `SettingsStore.setClaudeUserSetup(v)` accepts only a boolean (*Diagnostics*' pattern, issue #1094's `Saved`); IPC `settings:setClaudeUserSetup` through the existing `setting()` helper; `settings:get` returns `claudeUserSetup: boolean`. No per-folder or per-session value exists (owner 2026-11-09).
- **FR-002** **Plain words.** The row sits in Settings > Agent apps under Claude Code (it reaches the section list of spec 052 FR-226 through its heading). Label: **Use my Claude Code instructions and agents**. Description, always visible: "Claude Code sessions here also get the files you tick below: your CLAUDE.md (and the files it imports from your Claude folder) as instructions, and agents from your Claude folder's agents folder as helpers they can hand work to. Read when a session starts. A folder's own agent files are not used as helpers. Your settings, hooks, plugins, MCP servers, memory, history and sign-in are never read. Durbar's mode still decides what every agent may do." The Claude folder is named under it, home masked (`~/.claude`, or the `CLAUDE_CONFIG_DIR` folder). When on: "Applies to Claude sessions that start or restart from now on." The switch is offered only when the Claude Code adapter is registered; it does not appear for Copilot or Codex.

### B. What is read, and when

- **FR-003** **The Claude folder.** One function decides it: `claudeConfigDir(env)` (`claudeHistory.ts`), already used by the agent reader and the session list: `CLAUDE_CONFIG_DIR` when set and non-empty, else `path.join(os.homedir(), '.claude')`. Windows: `%USERPROFILE%\.claude` through `os.homedir()`; macOS and Linux: `$HOME/.claude`. No second rule is added. The root for every containment check is `realpath(claudeConfigDir())`; if it cannot be resolved, nothing is read.
- **FR-004** **The allow-list** (Q2, owner 2026-11-09 07:40 UTC). Two lists, both closed:
  - **Offered** (what the checklist may list, FR-030): `<root>/CLAUDE.md`; a `.md` file `CLAUDE.md` imports that sits in `<root>` itself or one folder below it (`<root>/<folder>/<file>.md`), where `<folder>` is not `agents` and not one of `projects`, `todos`, `plugins`, `shell-snapshots`, `statsig`, `ide`, `logs`, `cache`, `session-env`, `file-history`, and does not start with `.` (those are never offered, even when imported); and `<root>/agents/*.md`, one level, regular files only.
  - **Sent** (what a launch reads): only the offered items the person **ticked** (FR-031), each checked again at launch by FR-005 and FR-041. Nothing else is read at launch.
  Never read for this feature: `settings.json`, `settings.local.json`, `.credentials.json`, `.claude.json`, `projects/` (sessions and auto-memory), `todos/`, `history.jsonl`, `shell-snapshots/`, `statsig/`, `plugins/`, hooks, MCP configs, `ide/`, logs, caches, and any other file not in the list above. (Other existing features that read the Claude folder, such as the session list of spec 012 FR-125 and the slash entries of spec 073, are unchanged and not widened.)
- **FR-005** **Imports: text first, then the real path, then the ticks** (review 1, 2). The person's `CLAUDE.md` goes through `claudeMdPrompt` with the Claude folder as its root (the same function, a root and a heading parameter added; FR-018). An import is followed only when every step holds, in this order:
  1. **By text, before any file-system call**: the token does not start with `\\` or `//`, holds no `:` (drive letters, Windows streams), no NUL and no control character; `~/` is replaced by the home folder (Q1, answered (a)); the result, joined to the importing file's folder and normalised with the platform's `path`, is inside the root by text (`path.relative` has no `..` part and is not absolute).
  2. **`realpath`**: if it fails, the import is skipped (never used unresolved). The real path must again be inside `realpath(root)`.
  3. **On the real path, not the token**: relative to the real root, it is an **offered** item of FR-004 (`.md`, top level or one allowed folder down). Names are compared case-folded; on Windows each segment is refused if it ends with a dot or space or looks like an 8.3 short name (`~` followed by a digit), so `PROJEC~1` cannot stand for `projects`. A link `rules.md -> .credentials.json` fails here because its real path is not `.md`.
  4. **Ticked**: the item is in the person's ticks (FR-031).
  Anything else stays as the literal `@token` text and is counted by reason. URLs stay refused. Tests: `test:claudemd` cases for each refusal in both path flavours, with a recording `io` asserting that steps 1's refusals make **no** fs call; mutants: check containment only after `realpath`, apply the `.md` rule to the token, use an unresolved path when `realpath` fails, drop the short-name rule.
- **FR-006** **When.** Reads happen only (a) in `ClaudeAdapter.launch`, once per CLI launch of a session while the switch is on (the same moment the folder `CLAUDE.md` is read today), and (b) when the person presses **Check what loads** in Settings (FR-020). Never at app start, never on opening Settings, never in the background, never for Copilot or Codex sessions, never for the simulator's fake agents beyond the fixture folder of FR-026.
- **FR-007** **Switch off = no read.** With the switch off, `launch` calls neither the user branch of `claudeMdPrompt` nor the sub-agent builder, and `claudeArgs` output equals today's for the same session (a test compares them).
- **FR-008** **Bounded.** Every read is synchronous on the adapter's existing launch path today; this feature adds no unbounded work: at most 1 + imports (each file once, depth 4, 64 KB total, FR-009) and at most 50 agent files of 64 KB each. A read error on any file skips that file only; the session still starts.

### C. Caps

- **FR-009** **One CLAUDE.md budget.** The folder's and the person's `CLAUDE.md` share the existing `CLAUDE_MD_MAX_CHARS` (64 KB). The folder's file is read first with the whole budget, exactly as today, so turning the switch on never cuts the folder's instructions; the person's file gets what is left (Q4, answered (a) 2026-11-09: one shared budget). In the prompt the person's block comes first, headed "Your own CLAUDE.md (user instructions; Agent Durbar passes it because user settings are not loaded):", then the folder's block with today's heading. When the person's text is cut or left out for budget, the prompt says "[cut: CLAUDE.md budget]" at the cut, and **Check what loads** shows it.
- **FR-010** **Agent caps, unchanged.** `MAX_AGENT_FILES` 50 across folders and user, `MAX_AGENT_BYTES` 64 KB per file (larger: skipped, counted "too big"), `MAX_AGENT_PROMPT` 16 KB (longer: cut, counted "cut"). No new cap is added; the `--agents` data goes through a private file (FR-015), so command-line length limits (Windows' 32,767 characters, Linux's per-argument limit) do not apply to it.

### D. Sub-agents

- **FR-011** **Several agents, no `--agent`.** While the switch is on, the launch passes ONE `--agents` definition holding every **ticked** `user` agent read under FR-004 (folder agents are not included, FR-014, Q7). Without a chosen profile, no `--agent` flag is passed, so the main session is Claude's default agent and the others are available to its `Task`/`Agent` tool. With a profile chosen (spec 043 FR-008), the profile is in the same definition and `--agent <profile>` is passed as today. With the switch off, today's single-agent behaviour is unchanged.
- **FR-012** **Names and clashes.** The existing name rule `[A-Za-z0-9._-]{1,64}` applies, and `__proto__`, `constructor` and `prototype` (any case) are refused. The definition is built on a null-prototype object (or a `Map` serialised in order), never by assigning into `{}`. On a clash the chosen profile (spec 043, which may be a folder's agent) wins over the person's agent of the same name; the loser is shown as "same name as your session profile" in the session line (FR-039).
- **FR-013** **Only four keys pass.** Each entry carries `description`, `prompt`, `tools` and `model` only, as `agentsArg` does today; every other front matter key in the file (whatever it is called, for example a key that would name hooks, MCP servers, a permission mode or skills) is dropped. `parseFrontMatter`'s result maps become null-prototype so a key `__proto__` or `constructor` cannot reach a prototype or throw (today such a list key throws and the file is skipped, which stays the outcome for a file that cannot be parsed).
- **FR-014** **Folder agents are not sub-agents in this version** (review 5, Q7). The owner's decisions name "your own" agents; a folder's `.claude/agents/*.md` is outside text until confirmed, and spec 043's confirmation was given for choosing a profile, not for being a helper in every session of that folder. So the sub-agent definition holds only the person's ticked agents; a folder's agents stay available only as the session profile (spec 043 FR-008, unchanged). If Q7 is answered (B), a folder agent is offered only when `AgentTrustStore.isTrusted(folderKey, id, sha)` holds for the SHA-256 of the same bytes parsed, and only after a separate per-agent tick in the Agent menu. The person's own files under their Claude folder need no confirmation beyond their tick (issue #840, owner decision 2026-11-02). Test: `test:claudeagents` with a confirmed folder agent: it is never in the sub-agent definition; mutant: include confirmed folder agents.
- **FR-015** **No widening.** Sub-agents run in the session's own CLI process: the same `--permission-mode`, `--allowedTools`, `--disallowedTools` (mode and spec 069 FR-062), `--strict-mcp-config` with Durbar's MCP list only, the same OS sandbox block (spec 087), the same `PreToolUse` hook and `canUseTool` broker, the same dollar cap (`--max-budget-usd`). An agent's `tools` list can only narrow what it may call (review 7). The reference set is the session's own: the tools its mode allows after `--allowedTools`, `--disallowedTools`, the sandbox and the broker. A `tools` list keeps only names in that set; an absent list, an empty list or `*` means exactly that set, never more; Durbar adds nothing from it to any allow list, and a name the mode disallows stays disallowed. **Model rule**: an agent's `model` is passed only when `claudeModelFlag` (`claude.ts:307`) accepts it; otherwise it is dropped and the helper uses the session's model. Test: launch tests with `tools: ["*"]`, `tools: ["Bash"]` in Read-only and an absent list: `--allowedTools`/`--disallowedTools` equal with the switch off; mutant: copy an agent's tools into `--allowedTools`. `--setting-sources ""` stays in every launch. No hook, permission rule, plugin, MCP server, environment value or `--settings` content comes from any file this feature reads. A helper's cost counts against the session's cap like any helper.

### E. How it reaches Claude, and the version gate

- **FR-016** **Private files, version gated.** The person's instructions and the `--agents` definition go to Claude through private files, never as command-line text, because a process's command line is readable by other local accounts (on Linux through `/proc/<pid>/cmdline` unless `/proc` is mounted with `hidepid`) and is length-limited (Windows: 32,767 characters): `--append-system-prompt-file <file>` and `--agents <file>` (both listed by `claude --help`, `read:` Claude Code 2.1.319, 2026-11-09, which says `--agents` takes "JSON … or with --print the path to a file"), written with the `privateMcpConfig` pattern (`makePrivateDir`, mode `0600`, flag `wx`, removed at CLI exit, swept at quit). When the installed Claude Code is older than the first version known to have both (a constant like `CLAUDE_FORWARD_SUBAGENT_MIN_VERSION`; Q5, answered (a) 2026-11-09) or its version is unknown, the switch's content is **not sent at all** (no fallback to the command line); the session starts as with the switch off, and the row says "Needs Claude Code <version> or later". `[KNOWN GAP]` until the plan's research task confirms the first version and the file forms on a real install (free `--help` probes only).
- **FR-017** **The folder's CLAUDE.md, unchanged unless both go together.** When the switch's instructions are sent (FR-016), the folder's block travels in the same private file (one `--append-system-prompt-file`, FR-009's order). When they are not, the folder's `CLAUDE.md` goes exactly as today. Today that is on the command line (`claude.ts:366-370`, with the profile agent JSON and the `--settings` JSON): that exposure for every session, whatever this switch says, is **issue #1379** (Paco's side), not this spec; this spec adds nothing to the command line.
- **FR-042** **The SDK transport too** (review 3). Under the SDK transport (`claudeSdk.ts:93` passes `appendSystemPrompt` as `systemPrompt.append`), the switch's content never goes through `systemPrompt.append` or any other in-memory option: it goes only through the same private files passed as `extraArgs` (`append-system-prompt-file`, `agents`), and when the SDK's pass-through of those flags is not confirmed for the installed SDK version, **nothing is sent** (the gate of FR-016, its own constant). Test: SDK options test: with the switch on, `systemPrompt.append` holds no user text and `extraArgs` names only file paths, or neither is set; mutant: put the user text into `systemPrompt.append`.

### F. Code shape

- **FR-018** **One loader each.** `claudeMdPrompt` gains a root kind (folder or user Claude folder) and the FR-005 import filter for the user kind, keeping one budget counter across both calls (FR-009); `claudeAgents.ts` gains `subAgentsArg(defs)` beside `agentsArg` and a read path that returns the parsed definition with the SHA-256 of the bytes read. No other module reads the Claude folder for this feature.
- **FR-019** **Adapter-neutral options.** `StartOptions` gains `userSetup?: { on: true; items: string[] }` (the ticked names of FR-031 only; no Claude type, no file text, no absolute path from the window). Main fills it from `SettingsStore` when a Claude session starts or relaunches; other adapters ignore it. The adapter re-checks every name by FR-004, FR-005 and FR-041 before reading. The window never sends file paths, names or content for this feature.

### G. Check what loads (Settings preview)

- **FR-020** **On request, the checklist's items and counts.** **Check what loads** calls `settings:claudeUserSetupPreview` (main, `fromAppFrame`, no arguments accepted). ## Safety (constitution III)

- **Default off; one explicit choice** that says what it loads (FR-001, FR-002). Off is byte-for-byte today (FR-007).
- **Allow-list, not deny-list, for the files** (FR-004, Q2 as changed 2026-11-09 07:40): only offered items, and only those the person ticked (FR-031, FR-032: nothing by default); imports checked by text before any fs call, then by real path, `.md` only, top level or one allowed folder down, no symlink escape, no data folders (FR-005); one open per file, checked on the handle, capped (FR-041); links to outside not followed (FR-043). Credentials, settings, sessions, memory, history, plugins, hooks and MCP files are never read by this feature.
- **Read at launch or on request only** (FR-006); bounded (FR-008, FR-009, FR-010); hostile files skipped, never crash the launch (FR-012, FR-013, edge cases).
