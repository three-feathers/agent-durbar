## Summary

A Claude Code session started from Durbar does not behave like the same person's `claude` in a terminal, because Durbar launches Claude with `--setting-sources ""` (spec 012 Q8). The folder's `CLAUDE.md` is passed, but the person's own `~/.claude/CLAUDE.md` is not, and the person's agent files are offered only as the one profile a session starts with (spec 043 FR-008), never as sub-agents the session can hand work to. A "coordinator" way of working (the main session plans and delegates to named agents such as `analyst`, `implementer`, `reviewer`) cannot run in Durbar.

This feature adds **one switch in Settings, off by default**: *Use my Claude Code instructions and agents*. While it is on, each Claude session launch also gets:

1. the person's `CLAUDE.md` from their Claude folder, with its `@` imports **inside that folder only**, as instructions (beside the folder's `CLAUDE.md`, through the same reader and budget);
2. the person's agent files (`<Claude folder>/agents/*.md`) as **sub-agents**: one `--agents` definition with several entries, **without** `--agent`, so the main session can delegate to them. A project folder's own agent files (`.claude/agents/*.md`) can be helpers too, but only when spec 043's per-file confirmation holds **and** the person ticked that agent as a helper (Q7 B, FR-014); they are someone else's text and are marked "from a folder".

Only the items the person ticked in Settings' checklist are sent (section L): nothing is sent until something is ticked.

Nothing else from the Claude folder is read, and nothing the person did not tick is sent. Settings files stay off, Durbar's mode still decides every permission, and nothing read is stored, logged or shown unmasked.

## User scenarios

- **US1 (P1) Turn it on knowingly.** *Given* Settings > Agent apps > Claude Code, *Then* I see the switch **Use my Claude Code instructions and agents**, off, and under it one plain sentence of what it loads and what it never loads. *When* I press **Check what loads**, *Then* I see the file names, sizes and counts it would use (no file text), and what it would skip and why. *When* I turn it on, *Then* the row says "On. Applies to Claude sessions that start or restart from now on." and nothing is read until a session launches.
  - *Given* the switch on and my `CLAUDE.md` saying "Answer in Spanish", *When* I start a Claude session in any folder and send a message, *Then* the CLI got my `CLAUDE.md` text (with its imports from my Claude folder) as appended instructions, and no other launch flag changed except the ones this spec names.
- **US2 (P1) A coordinator delegates to my named agents.** *Given* the switch on, `analyst.md` and `reviewer.md` in my agents folder, and the session in Ask first, *When* the main session hands a task to `analyst`, *Then* the office shows a helper named *Helper · analyst*, its tool calls ask through the same permission cards as the main session, and it can do nothing the mode does not allow.
- **US3 (P1) Off means today's behaviour.** *Given* the switch off (the default), *Then* no file in my Claude folder is read for instructions or sub-agents (the profile list of spec 043 keeps working as today), and the launch flags are byte-for-byte today's.
- **US4 (P2) A folder's agent as a helper, knowingly.** *Given* the switch on and a folder `web` with `.claude/agents/deploy.md`, *Then* the Agent menu and the *What Claude gets* checklist list `deploy` **unticked**, marked "from a folder: web", with its masked first line. *When* I tick it, *Then* spec 043's confirmation shows the file's masked text and says "This file comes from the folder web, not from you. Once ticked, Claude sessions in web can hand work to it; it works under the session's mode. Its text can steer Claude to anything this session's mode allows. It uses the session's model." *After* I confirm, *Then* it is offered as a helper from the next launch of sessions in `web` only. *If* its file changes, *Then* it is not offered until I confirm it again (its tick stays and shows "Waits for confirmation").
- **US7 (P1) Pick what loads, easily.** *Given* I turn the switch on, *Then* Settings lists what it found in my Claude folder in plain words: *Your instructions (CLAUDE.md)*, each file it imports, and each agent by name, each with its size, its masked first line and one sentence of what Claude will see, and **nothing is ticked**. *When* I press **Pick for me**, *Then* CLAUDE.md, its allowed imports and every agent are ticked; **Select all** and **Select none** do the same in one click; I never type a path. *When* I add a new agent file later and press **Check what loads**, *Then* it appears unticked with *New*, and it is not sent until I tick it.
- **US5 (P2) Nothing leaks.** *Given* the switch on and a token-shaped string in an agent's name or in my `CLAUDE.md`, *Then* Settings, the helper name, the debug log, Diagnostics, saved settings and screenshots never show it unmasked; Durbar's saved files hold only the switch.
- **US6 (P3) Keyboard and screen reader.** *Given* keyboard only, *Then* Tab reaches the switch and **Check what loads**, Space toggles, and the result is read by the row's polite status region; the switch has a name and a description that says what it loads.

## Edge cases

- No Claude folder, no `CLAUDE.md`, an empty one, or no `agents` folder: nothing is added for that part; the session starts as today; **Check what loads** says "No CLAUDE.md found" / "No agents found".
- `CLAUDE_CONFIG_DIR` set: that folder is the Claude folder everywhere (FR-003), and Settings names it (home part masked).
- The Claude folder itself is a symlink (common with dotfiles): its `realpath` is the root; files inside it are fine. A file or import whose `realpath` leaves the root (and is not a link FR-043 accepts) is skipped and **counted** as "points outside your Claude folder" (no path shown, FR-020). An `agents` folder or a `CLAUDE.md` that is itself a link: FR-043 (Q8 B).
- An import names `.credentials.json`, `settings.json`, a session file, history, memory (`projects/*/memory/*.md` included) or any other file outside the allow-list (FR-004, FR-005): skipped and counted as "not offered", left as plain text; never listed in the checklist.
- A ticked item disappears or changes kind (a file becomes a link, a folder): it is not read at launch, the checklist shows it as *Missing* or *Not allowed now*, and the session starts without it.
- Durbar crashed or was killed while a session ran: its private launch folder may hold a copy of the person's instructions until the next start, which sweeps it (FR-038).
- Import cycles, the same file twice, depth over 4, `@` inside code fences or inline code, URLs and e-mail-like tokens: as `claudeMdPrompt` handles them today.
- A huge, binary, NUL-holding, invalid UTF-8, BOM or CRLF file; a front matter that never closes; 10,000 front matter lines; a name `__proto__`, `constructor` or `prototype`; a `tools:` list of 10,000 entries; a name clash between a user agent, a folder agent and the chosen profile (FR-012, FR-013).
- More than 50 agent files in total: the first 50 by the existing order (folders first, then the user's, each sorted by file name) are read; the rest are counted as "not read: over 50 files".
- The person also chose a profile for the session (spec 043): the profile stays the session's own agent (`--agent`), and the sub-agents are offered beside it (FR-011).
- The switch or the ticks change while sessions run: running CLI processes keep what they got; the next launch of each session (first message, resume, relaunch after a mode or model change) uses the new value, except that a resumed session may keep its earlier `--agents` set (FR-027, FR-039).
- Read-only: the instructions apply; delegation is refused as today (Q3, answered (a) 2026-11-09). The row says so.
- The installed Claude Code is older than the version these flags were checked on, or its version cannot be read: see FR-016.
- The Claude folder is on a slow or network drive: reads are bounded (FR-008) and never block the window.

## Requirements

### A. The switch

- **FR-001** **One global switch, off by default.** `AppSettings.claudeUserSetup?: true`: only `true` is written, absent means off; any stored value other than `true` reads off (fail closed). Setter `SettingsStore.setClaudeUserSetup(v)` accepts only a boolean (*Diagnostics*' pattern, issue #1094's `Saved`); IPC `settings:setClaudeUserSetup` through the existing `setting()` helper; `settings:get` returns `claudeUserSetup: boolean`. No per-folder or per-session value exists (owner 2026-11-09).
- **FR-002** **Plain words.** The row sits in Settings > Agent apps under Claude Code (it reaches the section list of spec 052 FR-226 through its heading). Label: **Use my Claude Code instructions and agents**. Description, always visible: "Claude Code sessions here also get the files you tick below: your CLAUDE.md (and the files it imports from your Claude folder) as instructions, and agents from your Claude folder's agents folder as helpers they can hand work to. A project folder's own agents are helpers only when you confirm and tick them. Read when a session starts. Your settings, hooks, plugins, MCP servers, memory, history and sign-in are never read. Durbar's mode still decides what every agent may do." The Claude folder is named under it, home masked (`~/.claude`, or the `CLAUDE_CONFIG_DIR` folder). When on: "Applies to Claude sessions that start or restart from now on." The switch is offered only when the Claude Code adapter is registered; it does not appear for Copilot or Codex.

### B. What is read, and when

- **FR-003** **The Claude folder.** One function decides it: `claudeConfigDir(env)` (`claudeHistory.ts`), already used by the agent reader and the session list: `CLAUDE_CONFIG_DIR` when set and non-empty, else `path.join(os.homedir(), '.claude')`. Windows: `%USERPROFILE%\.claude` through `os.homedir()`; macOS and Linux: `$HOME/.claude`. No second rule is added. The root for every containment check is `realpath(claudeConfigDir())`; if it cannot be resolved, nothing is read.
- **FR-004** **The allow-list** (Q2, owner 2026-11-09 07:40 UTC). Two lists, both closed:
  - **Offered** (what the checklist may list, FR-030): `<root>/CLAUDE.md`; a `.md` file `CLAUDE.md` imports that sits in `<root>` itself or one folder below it (`<root>/<folder>/<file>.md`), where `<folder>` is not `agents` and not one of `projects`, `todos`, `plugins`, `shell-snapshots`, `statsig`, `ide`, `logs`, `cache`, `session-env`, `file-history`, and does not start with `.` (those are never offered, even when imported); and `<root>/agents/*.md`, one level, regular files only.
  - **Sent** (what a launch reads): only the offered items the person **ticked** (FR-031), each checked again at launch by FR-005 and FR-041. Nothing else is read at launch.
  Never read for this feature: `settings.json`, `settings.local.json`, `.credentials.json`, `.claude.json`, `projects/` (sessions and auto-memory), `todos/`, `history.jsonl`, `shell-snapshots/`, `statsig/`, `plugins/`, hooks, MCP configs, `ide/`, logs, caches, and any other file not in the list above. (Other existing features that read the Claude folder, such as the session list of spec 012 FR-125 and the slash entries of spec 073, are unchanged and not widened.)
- **FR-005** **Imports: text first, then the real path, then the ticks** (review 1, 2). The person's `CLAUDE.md` goes through `claudeMdPrompt` with the Claude folder as its root (the same function, a root and a heading parameter added; FR-018). An import is followed only when every step holds, in this order. **Both root kinds** (Paco's round-2 B): steps 1 and 2 apply to the folder's `CLAUDE.md` too, with `realpath(<session folder>)` as its root, whether the switch is on or off (one rule in the one loader, so the folder's reader is never the weaker path); steps 3 and 4 apply to the person's file only, and the folder's file keeps today's other rules (any file type inside the folder, no ticks).
  1. **By text, before any file-system call**: the token does not start with `\\` or `//`, holds no `:` (drive letters, Windows streams), no NUL and no control character; `~/` is replaced by the home folder for the person's file only (Q1, answered (a); the folder's file keeps leaving `@~/` as text, as today); the result, joined to the importing file's folder and normalised with the platform's `path`, is inside the root by text (`path.relative` has no `..` part and is not absolute).
  2. **`realpath`**: if it fails, the import is skipped (never used unresolved). The real path must again be inside `realpath(root)`.
  3. **On the real path, not the token**: relative to the real root, it is an **offered** item of FR-004 (`.md`, top level or one allowed folder down). Names are compared case-folded; on Windows each segment is refused if it ends with a dot or space or looks like an 8.3 short name (`~` followed by a digit), so `PROJEC~1` cannot stand for `projects`. A link `rules.md -> .credentials.json` fails here because its real path is not `.md`.
  4. **Ticked**: the item is in the person's ticks (FR-031).
  Anything else stays as the literal `@token` text and is counted by reason. URLs stay refused. Tests: `test:claudemd` cases for each refusal in both path flavours and **both root kinds** (a folder `CLAUDE.md` importing `\\server\x.md`, `//server/x.md`, `C:x.md` and `../outside.md` is refused by step 1 with no fs call; a folder import whose `realpath` fails is left as text), with a recording `io` asserting that steps 1's refusals make **no** fs call; mutants: apply steps 1 and 2 to the person's root only, check containment only after `realpath`, apply the `.md` rule to the token, use an unresolved path when `realpath` fails, drop the short-name rule.
- **FR-006** **When.** Reads happen only (a) in `ClaudeAdapter.launch`, once per CLI launch of a session while the switch is on (the same moment the folder `CLAUDE.md` is read today), and (b) when the person presses **Check what loads** in Settings (FR-020). Never at app start, never on opening Settings, never in the background, never for Copilot or Codex sessions, never for the simulator's fake agents beyond the fixture folder of FR-026.
- **FR-007** **Switch off = no read.** With the switch off, `launch` calls neither the user branch of `claudeMdPrompt` nor the sub-agent builder, and `claudeArgs` output equals today's for the same session (a test compares them).
- **FR-008** **Bounded.** Every read is synchronous on the adapter's existing launch path today; this feature adds no unbounded work: at most 1 + imports (each file once, depth 4, 64 KB total, FR-009) and at most 50 agent files of 64 KB each. A read error on any file skips that file only; the session still starts.

### C. Caps

- **FR-009** **One CLAUDE.md budget.** The folder's and the person's `CLAUDE.md` share the existing `CLAUDE_MD_MAX_CHARS` (64 KB). The folder's file is read first with the whole budget, exactly as today, so turning the switch on never cuts the folder's instructions; the person's file gets what is left (Q4, answered (a) 2026-11-09: one shared budget). In the prompt the person's block comes first, headed "Your own CLAUDE.md (user instructions; Agent Durbar passes it because user settings are not loaded):", then the folder's block with today's heading. When the person's text is cut or left out for budget, the prompt says "[cut: CLAUDE.md budget]" at the cut, and **Check what loads** shows it.
- **FR-010** **Agent caps, unchanged.** `MAX_AGENT_FILES` 50 across folders and user, `MAX_AGENT_BYTES` 64 KB per file (larger: skipped, counted "too big"), `MAX_AGENT_PROMPT` 16 KB (longer: cut, counted "cut"). No new cap is added; the `--agents` data goes through a private file (FR-015), so command-line length limits (Windows' 32,767 characters, Linux's per-argument limit) do not apply to it.

### D. Sub-agents

- **FR-011** **Several agents, no `--agent`.** While the switch is on, the launch passes ONE `--agents` definition holding every **ticked** `user` agent read under FR-004 and every ticked and confirmed `repo` agent of the session's folders (FR-014, Q7 B). Without a chosen profile, no `--agent` flag is passed, so the main session is Claude's default agent and the others are available to its `Task`/`Agent` tool. With a profile chosen (spec 043 FR-008), the profile is in the same definition and `--agent <profile>` is passed as today. With the switch off, today's single-agent behaviour is unchanged.
- **FR-012** **Names and clashes.** The existing name rule `[A-Za-z0-9._-]{1,64}` applies, and `__proto__`, `constructor` and `prototype` (any case) are refused. The definition is built on a null-prototype object (or a `Map` serialised in order), never by assigning into `{}`. On a clash the chosen profile wins, then a folder's agent, then the person's (today's order in `listClaudeAgents`); the loser is shown as "same name as your session profile" in the session line (FR-039).
- **FR-013** **Only four keys pass, three for a folder agent.** Each entry carries `description`, `prompt`, `tools` and `model` only, as `agentsArg` does today, and a folder agent offered as a helper carries `description`, `prompt` and `tools` only (its `model` is ignored, FR-014, Paco's E); every other front matter key in the file (whatever it is called, for example a key that would name hooks, MCP servers, a permission mode or skills) is dropped. `parseFrontMatter`'s result maps become null-prototype so a key `__proto__` or `constructor` cannot reach a prototype or throw (today such a list key throws and the file is skipped, which stays the outcome for a file that cannot be parsed).
- **FR-014** **Folder agents as helpers: confirmed, ticked, and named as someone else's text** (Q7 B, owner 2026-11-09 07:49 UTC; review 5). A `repo` agent (`<session folder>/.claude/agents/*.md`) is put in the sub-agent definition only when **all** hold: (1) the switch is on; (2) the person ticked it as a helper for that folder (FR-045); (3) `AgentTrustStore.isTrusted(folderKey, id, sha)` holds for the SHA-256 of **the same bytes the adapter parsed** (one read, FR-041: hash and parse from one buffer, so a file swapped between check and use is never offered), and that trust was itself recorded for the bytes the confirmation dialog showed (FR-047); (4) it passes the same reader rules as the person's agents (FR-012, FR-013, FR-041; a link in a folder's `.claude/agents` is never followed: FR-043's home-folder rule is for the person's own Claude folder only). It is offered **only to sessions of that folder**: a session whose folder list (the folders it was started with, spec 043's `folders`) includes that folder; a session with several folders gets the ticked, confirmed helpers of each of its folders and of no other (Paco's round-2 F: this is FR-019's "this session's folders"; the session can already work in each of those folders, so this adds no reach). Main passes the ticked, confirmed (folder key, id, SHA-256) triples in `StartOptions.userSetup` (FR-019); the adapter never reads the trust file.
  - **What a folder agent can do**: what any helper can, under FR-015: work inside the session's process, mode, allow and deny lists, sandbox, hook, broker and dollar cap; its `tools` list only narrows that set; only `description`, `prompt` and `tools` pass from its file. **Its `model` is never passed** (Paco, issue owner, 2026-11-09, round-2 E): a folder agent always uses the session's model, so a repository cannot pick a pricier model; the confirmation and the checklist do not show a model for it. **What it cannot do**: add a tool, permission, hook, MCP server, setting, environment value or `--settings` content, change the mode, or reach another folder's sessions.
  - **Someone else's text** (a prompt-injection surface): a folder agent's prompt is written by whoever wrote the repository and can tell Claude to do anything the mode allows. So it is unticked by default (never ticked by *Pick for me* or *Select all*, which act on the person's own items only), marked "from a folder: <folder name>" in the Agent menu and the checklist with its masked first line, and spec 043's confirmation dialog shows its masked text (rendered as text only, FR-049) and names the role: "This file comes from the folder <name>, not from you. Once ticked, Claude sessions in <name> can hand work to it; it works under the session's mode. Its text can steer Claude to anything this session's mode allows. It uses the session's model." A changed file loses its confirmation (spec 043) and is not offered until confirmed again; its tick stays and reads "Waits for confirmation". The prompt-injection risk that remains after all this is FR-048's `[KNOWN GAP]`.

### E. How it reaches Claude, and the version gate

- **FR-016** **Private files, version gated.** The person's instructions and the `--agents` definition go to Claude through private files, never as command-line text, because a process's command line is readable by other local accounts (on Linux through `/proc/<pid>/cmdline` unless `/proc` is mounted with `hidepid`) and is length-limited (Windows: 32,767 characters): `--append-system-prompt-file <file>` and `--agents <file>` (both listed by `claude --help`, `read:` Claude Code 2.1.319, 2026-11-09, which says `--agents` takes "JSON … or with --print the path to a file"), written with the `privateMcpConfig` pattern (`makePrivateDir`, mode `0600`, flag `wx`, removed at CLI exit, swept at quit). When the installed Claude Code is older than the first version known to have both (a constant like `CLAUDE_FORWARD_SUBAGENT_MIN_VERSION`; Q5, answered (a) 2026-11-09) or its version is unknown, the switch's content is **not sent at all** (no fallback to the command line); the session starts as with the switch off, and the row says "Needs Claude Code <version> or later". `[KNOWN GAP]` until the plan's research task confirms the first version and the file forms on a real install (free `--help` probes only).

- **FR-043** **Links in your Claude folder** (Q8 B, owner 2026-11-09 07:49 UTC; review 4; Paco's round-2 C and D, which are conditions of his acceptance of B). `<root>/agents` and `<root>/CLAUDE.md` may be symlinks or junctions (dotfiles setups). Such a link is followed only when every rule holds, in this order:
  1. **Link text before `realpath`** (round-2 D): each hop of the chain is read with `readlink` (at most 8 hops; a longer chain is refused) and checked by text before anything resolves it: a target that starts with `\\` or `//` (UNC, `\\?\`, `\\.\` device and network forms), or names a drive other than the home folder's drive, is refused, so a link to a network share or a mapped drive is never resolved or opened; a relative target is joined to the link's own folder and must be inside the home folder by text (`path.relative`, as FR-005 step 1).
  2. **Inside home**: the resolved target (`realpath`, so a chain counts as its end) is inside `realpath(os.homedir())`.
  3. **No dot folder, no app data**: no segment of the target relative to the home folder starts with `.`, except the Claude folder's own real path (so `~/.ssh`, `~/.aws`, `~/.config`, `~/.gnupg` are refused even though they are inside home), and no segment is `Library` or `AppData` (case-folded; round-2 C: macOS and Windows keep application data and credentials there without a dot). A user-made link to an ordinary folder such as `~/Documents/claude/agents` is allowed: its items start unticked.
  4. **Inside the Claude folder, only an offered place** (round-2 C): when the resolved target is inside `realpath(root)`, it must pass FR-004 relative to the root for its role: a `CLAUDE.md` link must land on an offered `.md` file (top level, or one folder down where the folder is not one FR-004 excludes), and an `agents` link must land on a top-level folder of the root that FR-004 does not exclude (never `projects`, `todos`, `plugins`, `shell-snapshots`, `statsig`, `ide`, `logs`, `cache`, `session-env`, `file-history`, or a dot folder). So `agents -> ~/.claude/projects/<p>/memory` is refused, and none of its memory files is listed or previewed.
  5. **The role**: the resolved name still fits FR-004's allow-list: `CLAUDE.md` resolves to a `.md` regular file, `agents` to a folder whose entries are read as `*.md` regular files; names are case-folded and Windows segments with a trailing dot or space or an 8.3 short name are refused (FR-005 step 3).
  6. **Checked on the open handle, not the path** (round-2 D): each file, and the linked `agents` folder itself, is opened **once** at its resolved path with `O_NOFOLLOW` (the folder with `O_DIRECTORY` as well, where the platform has them) and every check is made on that handle: `fstat` shows a regular file (or a folder) within the cap and, on POSIX, owned by the user running Durbar (`fstat().uid === process.getuid()`; Windows has no owner in Node's `stat`, so there the target must be inside the user's profile folder, and ownership is FR-046's `[KNOWN GAP]`); on Linux the handle's own path (`readlink('/proc/self/fd/<fd>')`) must equal the resolved path, so a parent folder swapped after `realpath` is caught (`O_NOFOLLOW` guards only the last part of the path); on macOS and Windows Node has no call for a handle's path, which is FR-051's `[KNOWN GAP]`. Then at most cap + 1 bytes are read, and the bytes must be text: valid UTF-8 with no NUL (FR-041).
  A followed link is shown in the checklist with its masked target (`maskHomePaths`, for example "agents → ~/dotfiles/claude/agents", rendered as text only, FR-049) and its items start **unticked**; *Pick for me* does not tick them (each needs its own tick). A link that fails any rule is shown once as "points outside" with nothing to tick and is never read. Durbar never creates, changes or deletes a link or its target. Imports of a followed `CLAUDE.md` resolve inside that target's own folder under the same six rules, one folder down at most. Links inside `agents` (a single agent file that is a link) and links in a project folder's `.claude/agents` are never followed. Test: `test:claudeagents` and `test:claudemd` with fixtures: `agents -> ~/dotfiles/agents` (followed, unticked, masked target shown); `agents -> ~/Documents/claude-agents` (followed, unticked); `agents/x.md -> ~/.ssh/id_rsa` and `agents -> ~/.ssh` (refused: dot folder, not `.md`); `agents -> ~/.claude/projects/p/memory` and `CLAUDE.md -> ~/.claude/projects/p/memory/MEMORY.md` (refused by rule 4, nothing previewed); `agents -> ~/Library/x` and `agents -> ~/AppData/Roaming/x` (refused by rule 3); `CLAUDE.md -> /etc/passwd` (outside home); a link whose text is `\\server\share\agents`, `//server/share` or another drive (refused by rule 1 with a recording `io` showing no `realpath` or open call); a chain of nine links (refused); a target owned by another uid (refused on the handle's `fstat`, with the path's `stat` faked to say this user); a parent folder swapped for a link to `~/.ssh` between `realpath` and open (refused on Linux by the `/proc/self/fd` check); a target swapped for a link between `realpath` and open (refused by `O_NOFOLLOW`); `PROJEC~1`-style and `agents.` names on win32.
