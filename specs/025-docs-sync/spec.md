## What was wrong

- `[KNOWN GAP]` (fixed here) No rule said that a PR must update README, docs, spec tasks, CHANGELOG and screenshots. Several merged PRs (#15 Allow all, #16, #17 usage totals) left the README status block, the CHANGELOG, the roadmap, spec statuses and the Development section behind `main`.
- `[KNOWN GAP]` (fixed here) The PR template had no docs box and CI had no docs reminder.

## Requirements

- **FR-001** `[IMPLEMENTED]` `AGENTS.md` has a **Keep docs in sync** section: when a PR changes user-visible behaviour, scripts, permissions, settings, MCP/tool behaviour, release status or contributors, it updates in the same PR the README, `CHANGELOG.md`, the relevant `docs/` pages, the spec's `tasks.md` (and spec status and index), and the screenshots, with the exact list of files to check. An agent that cannot do it opens an issue (label `area:docs`), assigns it, and links it from the PR. `CLAUDE.md` imports `AGENTS.md`; `.github/copilot-instructions.md`, `docs/collaboration.md` and `CONTRIBUTING.md` point to it.
- **FR-002** `[IMPLEMENTED]` The PR template has a **Docs** section: a *Docs updated* box, a *no docs impact* box with a `Docs: n/a <reason>` line (in an HTML comment, like `Spec-Exempt`), and a screenshots line in Verification.
- **FR-003** `[IMPLEMENTED]` `test:` A non-blocking **Docs check (warning only)** job in `.github/workflows/spec-kit.yml` runs `.github/scripts/docs-check.sh`. It warns (annotation and step summary) when (a) `src/` changed and none of `README.md`, `CHANGELOG.md`, `docs/` changed, or (b) `package.json` scripts changed and `README.md` did not. Switched off by a `Docs: n/a <reason>` line (reason of 4+ characters, not the template placeholder, not inside a comment) or a `docs-n/a` or `spec-exempt` label. The script always exits 0; the job has `continue-on-error: true`; it is **not** in `.github/ruleset-main.json` required checks. `.github/scripts/test-docs-check.sh` (20 cases, throwaway repos) runs in the same job.
- **FR-004** `[IMPLEMENTED]` Catch-up audit against `main` after PRs #1, #11-#17: README status block, release status (v0.1.0-alpha.2 draft pre-release, unsigned), permission names (Read-only / Ask first / Allow all), usage totals, roadmap, known limits, Development scripts, links (repo, board), contributors and credits; CHANGELOG *Unreleased* (and the *Allow edits* wording in the alpha.2 entry); CONTRIBUTING, SECURITY, `specs/README.md` and stale task ticks in specs 021 and 023.

### 2026-10-22: fewer merge conflicts (changelog fragments, generated specs index)

**Input**: Vikram (team chat, 2026-10-22 05:59 UTC, "yes" to the proposal): remove the main source of merge conflicts. 8 of the 9 PRs that conflicted that night clashed only in `CHANGELOG.md` *Unreleased*, README status lines and `specs/README.md` rows. This delta lifts "Auto-generating docs" out of *Out of scope* for exactly these two files.

- **FR-007** `[IMPLEMENTED]` `test:` **Changelog fragments.** A PR adds its changelog line(s) as one file `changelog.d/<branch-or-topic>.md` instead of editing `CHANGELOG.md`. Format: one or more top-level Markdown bullets (`- ...`), an indented line continues the bullet above it; no headings, no HTML comments, no unindented prose; the file name is lower case (`[a-z0-9][a-z0-9._-]*.md`, so names never clash on a case-insensitive disk); `changelog.d/README.md` explains the folder and is not a fragment. No categories: the CHANGELOG has none.
- **FR-008** `[IMPLEMENTED]` `test:` `npm run changelog:check` (in `npm test` through `test:changelog`) fails on a bad fragment name or format and on an entry that is already in another fragment or in `CHANGELOG.md` (spacing ignored). A bullet under *Unreleased* in `CHANGELOG.md` is a **warning** until the cut-over marker (`<!-- changelog.d: fragments only ... -->`) is in the *Unreleased* section, then an **error** (`--strict` makes it an error at once).
- **FR-009** `[IMPLEMENTED]` `test:` `npm run changelog:build -- --release "<heading>"` (release PR) adds `## <heading>` right under *Unreleased* with every fragment (sorted by file name), then every bullet still under *Unreleased* (the transition: lines added the old way are folded too, not lost), deletes the folded fragments, keeps *Unreleased* with a one-line pointer to `changelog.d/` and the cut-over marker, and moves "after the alpha.N tag" in the *Unreleased* heading to the new tag. The rest of the file is kept byte for byte. It refuses invalid fragments, a missing heading and a heading that already exists; with nothing to fold it changes nothing (idempotent); `--dry-run` prints the result. `npm run changelog:preview` prints what the next release gets.
- **FR-010** `[IMPLEMENTED]` No separate migration command (review on #518: after alpha.11 *Unreleased* was empty, so it had nothing to move). Lines that still land under *Unreleased* the old way are folded by `changelog:build` (FR-009). `changelog:build` also refuses a second section for a version that is already in the file, comparing the `v...` token, not the whole heading: a different date or link must not slip through.
- **FR-011** `[IMPLEMENTED]` `test:` **Generated specs index, rows not committed.** Each `specs/NNN-*/spec.md` keeps its index row in a comment block right under its title: `<!-- specs-index (...)`, then `group:` (which table), `title:` and `status:` (one line each, Markdown, no unescaped `|`, no `-->` or `--!>`), then a line that is only `-->`. The block is invisible on GitHub and needs no YAML escaping. `specs/README.md` keeps only its hand-written text, plus a `<!-- specs-index group=ID -->` line where each table goes. **The rows are not committed** (review on #518: committed generated rows still conflicted when two PRs changed neighbouring specs, 063 and 064 tested). Two PRs therefore never share a line, and a status change touches only that spec's own `spec.md`. The website (spec 050) builds the full index from the blocks: the docs page has a *Specs index* section, the feature grid uses it, and the landing page links to it. `npm run specs:index` writes `specs/INDEX.md` (git-ignored) for local reading; `--print` prints it. Rows are sorted by spec number within a group.
- **FR-012** `[IMPLEMENTED]` `test:` `npm run specs:check` (in `npm test` through `test:specsindex`) reports any of these: a spec with no block or a bad block, a group that has no marker or is marked twice, and table lines committed under a marker (an old-style hand edit). Until `specs/README.md` has the line `<!-- specs-index: strict -->` (or `--strict` is given), the check only warns. A small PR adds that line once no open PR edits the rows any more (#520). There is **no clock**: the same commit always gives the same result. `npm run specs:index -- --import` reads the hand tables into the blocks and removes their rows; it refuses a duplicated row or a value with a comment end and writes nothing then. `npm run specs:index -- --add specs/NNN-name` gives a new spec a `Draft` block, using the newest spec's group and the title of its `# ` line. A spec made from the Spec Kit template and given a block with `--add` passes `--check --strict`. The template itself is not changed: `.specify/integrations/speckit.manifest.json` pins its hash, so an edit would show as drift in `specify integration status`.
- **FR-013** `[IMPLEMENTED]` Backfill: all 63 spec folders on `main` (after alpha.11) got their block from the table. The index generated from the blocks equals that table except for the new intro sentence and three rows put in number order (055/054, 057/056, 061/060). At merge time `--import` runs again on the then-current table, so rows changed by PRs that landed first are kept (#520). Two status fields: the block's `status` is what the index shows and the one to keep current. The `**Status**:` line in a spec's header comes from the Spec Kit template and records the stage when the spec was written; it is not checked and may lag. Removing it from 63 specs and from the template (whose hash is pinned) is not worth the churn.
- **FR-014** `[IMPLEMENTED]` README status block: generating it is not worth it (it is prose about releases and real-machine runs, not spec status). Rule instead: feature PRs do not edit it; the release PR does. The other README hot spots (feature list, *Build from source* commands) are real per-feature content and stay hand-edited.
- **FR-015** `[IMPLEMENTED]` `test:` The *Docs check* (FR-003) accepts a `changelog.d/` fragment as a docs change, and warns (still never blocks) when a PR that adds no `## v` release heading adds a bullet to `CHANGELOG.md`, or adds a spec row (`| [NNN](...)`) to `specs/README.md` (the rows are generated from the spec blocks and not committed). `test-docs-check.sh` has 25 cases.
- **FR-016** `[IMPLEMENTED]` Rules and docs: `AGENTS.md` (*Where things are*, *Keep docs in sync*), `CLAUDE.md`, `.github/copilot-instructions.md`, `.github/pull_request_template.md`, `CONTRIBUTING.md`, `docs/collaboration.md` (workflow, Docs check, the release step), `docs/agent-notes.md`, README *Build from source*, the `specs/README.md` intro and `changelog.d/README.md`. `.gitattributes` keeps `CHANGELOG.md merge=union` as a fallback for the transition. `specs/README.md` has no rows left to conflict in.
- `[KNOWN GAP]` The fold order inside a release is by file name, not by merge time; the release manager reorders by hand if it matters. Checked on Linux only; the scripts are plain Node with `path.join` and CRLF-tolerant reads (the Windows and macOS CI runs `npm test`). Follow-ups: the merge-time step, the strict marker and the first release with `changelog:build` are tracked in #520.
