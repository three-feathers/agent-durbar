## User Scenarios & Testing *(mandatory)*

### User Story 1 - Install a build for my OS (Priority: P1)

From the GitHub Releases page I download a file for my system and run it; the README explains the OS warnings for unsigned apps.

**Acceptance Scenarios**:

1. **Given** macOS Apple Silicon / Intel, **When** I download the `.dmg` or `.zip`, **Then** I get `Agent-Durbar-<version>-arm64|x64.<ext>`. *(read:; the draft release exists, CI run succeeded 2026-10-16 per `gh run list`; **never installed on a Mac**)*
2. **Given** Windows 10/11 x64, **When** I download, **Then** I get an NSIS installer (`Agent-Durbar-Setup-<v>.exe`, per-user, choose folder) or `Agent-Durbar-<v>-portable.exe`. *(read:; never installed on Windows)*
3. **Given** Linux x64, **When** I download the AppImage and `chmod +x`, **Then** it runs (maybe with `--no-sandbox`). *(sim: built here; launching the packaged app was not recorded)*

### User Story 2 - The packaged app can actually start Copilot (Priority: P1)

The bundled Copilot runtime must be reachable at run time: it is unpacked from the asar and located by path. A build without it fails.

**Acceptance Scenarios**:

1. **Given** `npm run pack:dir` on Linux, **When** it finishes, **Then** `afterPack` has verified `app.asar.unpacked/node_modules/@github/copilot-sdk-linux-x64/prebuilds/linux-x64/copilot-runtime` and `runtime.node` exist and no other platform's runtime is bundled. *(re-verified 2026-10-16: exit 0)*
2. **Given** a packaged app, **When** the adapter starts, **Then** it passes that unpacked path to the SDK. *(test: path logic; real start of a packaged app not recorded)*

---

### User Story 3 - A tag makes a draft release; I publish by hand (Priority: P2)

Pushing a tag `v*` that matches `package.json` builds all platforms on GitHub Actions, uploads artifacts and creates or updates a **draft** (pre-)release with `SHA256SUMS.txt`. Nothing is published automatically.

**Acceptance Scenarios**:

1. **Given** tag `v0.1.0-alpha.1`, **When** pushed, **Then** the workflow builds macOS (arm64, then x64), Windows and Linux and creates a draft pre-release. *(real: run 38908947850 succeeded; draft "Agent Durbar v0.1.0-alpha.1" exists)*
2. **Given** a tag that differs from `package.json` version, **When** pushed, **Then** the workflow fails before building. *(read:)*

---

### User Story 4 - CI on every push and PR (Priority: P2)

Typecheck, build and `npm test` run on Ubuntu, macOS and Windows; a Linux job also packs the app and checks the runtime is unpacked.

**Acceptance Scenarios**:

1. **Given** a push to `main` or any pull request, **When** CI runs, **Then** the 3-OS matrix and the packaging smoke run. *(real: last run on main, success)*

## Changes

### 2026-11-09: no duplicate typecheck step before build in CI (FR-193, T150; owner decision, team-reviewed on #1352)

Owner (Vikram, 2026-11-08) asked for CI optimisation; the agents of Paco and Ruben agreed on the #1352 comments. `npm run build` is `tsc -p tsconfig.json && node scripts/copy-assets.js`, and `npm run typecheck` is the same `tsc -p tsconfig.json --noEmit`, so running both compiles twice for nothing. FR-192's measurement (about 290 runner minutes a week, #1352) is the basis; this is a separate, smaller change that does not wait for that proposal.

- **FR-193** `[IMPLEMENTED]` (T150) `test:` **CI type-checks once, in the build.** The `Build and test` job in `ci.yml` and `macos-pr.yml` no longer run `npm run typecheck` before `npm run build`; a type error still fails the build step. `release.yml` keeps `npm run typecheck` because no build step runs before its tests. `AGENTS.md`'s local check line keeps `npm run typecheck`. `scripts/test-ci-typecheck.js` (`npm run test:citypecheck`) asserts that the `typecheck` and `build` scripts use the same `tsc -p` project and that both workflows still run `npm run build` and not both steps. Mutants (build on another tsconfig; build step removed; typecheck step re-added) each fail it with its own message.

### 2026-11-08: the slow UI drivers wait for the page's own word, not for a guess (owner: "speed up the slow checks, starting with the top 15", then "all drivers")

*Why:* on green CI run 42476923350 the slowest drivers took 288 s (check-office-fill), 245 s (check-auto-follow), 132 s (check-crew); profiling them locally (a wrapper counting every `ctx.sleep`, `until` poll and `waitFor`) showed where the time goes: (a) `H.load` found "the frozen simulator is steady" by sampling the page twice 200 ms apart, 2 to 4 times per load, while the page itself knows (`__durbarSimReplayed`, `visitsSettled()`, `settleNow()`); (b) a load whose `ready` expression can never hold (the default is "15 desks": a chat opened by `open=`, 2 agents, the Real office) waits its whole 15 s and goes on, silently (shots-017: 4 loads, 60 s of 79 s; check-auto-follow: 3 loads, 45 s of 250 s); (c) a fixed 800 ms "a visit may start a moment after the load" and fixed gaps of 250 + 150 ms after it (check-office-fill: 107 loads); (d) the lobby's own timers (a visit starts after 600 ms, a walk takes 1 s, an ended visit stays 2 s) and a simulated reply's four 650 ms thinking pauses, which drivers that look at neither only wait for. No assert, tolerance, size or world changes.

- **FR-190** `[IMPLEMENTED]` (T143) **A driver waits on a condition the page states.** (1) `helpers(ctx).load` with the frozen simulator (`simfreeze=1`, no custom `index`, settling not turned off) waits, at most 4 s, for `__durbarSimReplayed && visitsSettled() && settleNow() && no .scene-out` before its usual `settle`, which still runs; it never throws (`until`), so the driver's own asserts report what is wrong. No driver opts out: check-office-ops used a `steady: false` opt-out while its arcade row `statusNodes@retro15`/`@retro40` was a race with the screen painter; PR #1318 fixed that caret flake at its cause, the opt-out was removed (and the option with it), and check-office-ops passed 10 of 10 local runs under xvfb on the merge with `main`. (2) `load` prints `[waits] load: the ready expression never held ...` when `ready` times out, so a wait that is always spent is visible; the drivers it found pass a real `ready` (shots-017 two `open` loads: the new-session button; check-auto-follow: 2 desks, and the Real office's plate). (3) check-office-fill waits for the simulator's steady state and no walking figure (then two painted frames) instead of 800 ms + 250 ms + 150 ms; its Settings toggle waits for the setting's own effect (the stored `durbar.shutters` value flips, the screen closes, two frames are drawn), not for the screen alone (that failed 1 run in 3 at 1440x900 with the old state read); check-crew waits for every portrait to decode (then two painted frames) instead of a fixed 250 ms and 200 ms. A `simreply=fast` switch was tried for check-notes-source (it failed once on CI with `Message shown. is announced`), the driver was put back as it was, and the switch was dropped because no driver used it. Per-driver before and after seconds, and the mutants, are in the PR description (local runs under xvfb; CI times differ).

### 2026-10-22: `npm test -- --bail`, an opt-in fail-fast run for local iteration (issue #563, T102)

*Why:* an implementer iterating locally waits 3-6 minutes for the first failure because `npm test` always runs every suite. Team proposal (Paco, agreed with Vikram's agent, 2026-10-22).

- **FR-115** `[IMPLEMENTED]` (T102) **Opt-in fail-fast.** `npm test -- --bail` or `TEST_BAIL=1` (anything but empty, `0`, `false`) stops at the first failing suite: no new suite or step starts, the suites still running are stopped, that suite's output is printed, the exit code is 1, and a last line names the suite and says the run was cut short (not complete). Without the flag nothing changes: every suite runs and every failure is listed. It combines with the name filter (`npm test -- folders --bail`). Stopping reaches the whole tree of each running suite and only those this runner started: on POSIX, only when bailing, each step is spawned `detached` (its own process group) and stopped with `SIGTERM` to the group, then `SIGKILL` to the group after a 5 s grace period or as soon as the step's pipes close (a grandchild that ignores TERM keeps them open, so the runner must not wait for it); on Windows with `taskkill /PID <pid> /T /F`, which already forces, spawned without a shell. Without `--bail` the suites are spawned exactly as before. Ctrl-C, SIGHUP or SIGTERM of a bailing runner takes the same path and exits 128 plus the signal number (SIGINT 130, SIGTERM 143; SIGHUP is 129, so 129 is not SIGTERM), not 1 (the signal is recorded and wins over the bail's exit code; `runMain` in `scripts/run-tests.js`). `test:runtestsreal` also starts the real wiring on a slow suite, sends it SIGTERM, SIGINT and SIGHUP in turn, and asserts exit 143, 130 and 129 and the suite gone (POSIX only; skipped on Windows, which has no POSIX signals); dropping the recorded signal makes it fail. **Under CI** (`CI` set, not empty, `0` or `false`) `--bail` and `TEST_BAIL` are ignored with the line `--bail ignored under CI: running every suite` (decision on review of PR #565). The pieces are injectable (`runSuites`, `stopChild`, `parseArgs`, `loadSuites` in `scripts/run-tests.js`). `test:` `scripts/test-run-tests.ts` (`test:runtests`) with fake spawn and kill: default runs all after a failure and is not detached, `--bail` starts nothing after the first failure (one at a time and in parallel), running suites get a group TERM then KILL (POSIX) or a `taskkill /T /F` (Windows), the grace timer, flag, env var, CI and the filter. `test:` `scripts/test-run-tests-real.ts` (`test:runtestsreal`, runs on every CI OS) spawns real fixture suites, one failing and one whose process and grandchild both ignore SIGTERM and hold the pipes, and asserts the runner returns in time and the grandchild pid is gone (fixture code is constant text, paths pass through the environment); dropping the SIGKILL escalation makes it fail (mutation run on Linux). `[KNOWN GAP]` The Windows branch (`taskkill`) and macOS were not run by hand; they run only in CI via the real test. Real Electron or Xvfb children were not used (fixtures are plain node processes). SIGTERM (143), SIGINT (130) and SIGHUP (129) are each tested on POSIX.

### 2026-11-08: pull requests skip the CI parts their change cannot affect (FR-191, T144; owner decision)

**Owner decision** (Vikram, maintainer and CODEOWNER of `.github/`, Telegram 2026-11-08 22:36 UTC): "Ok go" to stop running the three-OS UI workflow on pull requests that cannot affect the UI, and (22:37 UTC) "Include common sense optimization of other such things as well". The rule that bounds it: **`main`, the merge queue and the nightly run everything they ran before**; only pull requests skip, so the checks before a release are the same as before. (Precisely: pushes to `main`, the nightly and by-hand runs run every workflow in full; the merge queue runs `ci.yml` in full; `ui-platforms.yml` has never had a `merge_group` trigger and still has none, review of PR #1349: adding it would put 8 UI shards on every queue entry for a check that is not required, so the docs were corrected instead) (AGENTS.md *Fast checks, same quality*: nothing is dropped, work a change cannot affect is not repeated on its PR).

*Why:* `ui-platforms.yml` ran 8 UI shards (Linux and Windows, 4 each) on any pull request touching `src/**`, `scripts/**`, `package.json` or the lock, so a report script (`scripts/usage-lib.js`), a unit-test script, a new npm script line or the release's version bump ran the whole UI suite; `macos-pr.yml` ran the real macOS build and test for a version bump; `ci.yml`'s office layout and package smoke ran for any non-docs change.
