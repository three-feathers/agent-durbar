## Summary

Agent Durbar has no own update today: a person learns of a new version from GitHub or the team. This spec adds, in phases:

1. **Phase 1, all three OSes, unsigned builds (recommended first):** Durbar checks the GitHub releases of the repository **its build came from** (a fork checks the fork), once a day, and only that. A newer stable release shows an **Update available** card with every release in between (notes as plain text), a **breaking changes** card when one of them is breaking, *Remind me in 7 days* and *Skip this version*. **Download** fetches the installer for this OS and install type, checks it against the release's `SHA256SUMS.txt` (which only catches a broken or wrong download, not a forged release), marks it as downloaded from the internet (Windows zone mark, macOS quarantine flag) so the OS's own checks run, and offers *Open installer* and *Show in folder*. Nothing installs by itself; the person runs the installer. The daily check is **on by default** (owner decision D2 = A), with a Settings switch that makes zero network calls when off (FR-004).
2. **Phase 2, in-place apply, every time with consent, and only with a signature checked against a key built into the app (FR-014):** Windows NSIS install (run the installer, quit, restart) and Linux AppImage (replace the AppImage file, keep the old one for a rollback). Without a built-in key and a valid signature there is no in-place apply, whatever the source or policy.
3. **Phase 3, macOS in place: only after Developer ID signing and notarization** (spec 014, a purchase, owner approval). Until then macOS stays at phase 1.

Every phase: a pre-update backup of Durbar's own settings and session index (never secrets), the organization policy keys reserved by spec 076 FR-174 (`updates.mode`, `updates.feedUrl`), a Settings switch that makes zero network calls when off, the simulator with a canned feed, and tests that run offline.

- **D1 Signing (money). - **D3 Signature scheme and where the key lives.** The checksum alone never allows phase 2 (FR-014). Options for the signature: A none: phase 1 only, for ever; B **GitHub build provenance attestations** (already made by `release.yml`, spec 008 FR-132): a sigstore verifier dependency and a bundled trust root, the app pins the signing workflow identity of its own repository; C **one Ed25519 key per repository** in the format of FR-014, verified with Node's `crypto.verify` (no dependency). For C the private key lives in a **GitHub Environment `update-signing`** (owner settings): required reviewers = the owners, **Prevent self-review** on (the person who pushed the tag cannot approve the run), deployment branches and tags limited to `v*` tags, and a tag ruleset that lets only owners create `v*` tags. Only with all four does *a pushed tag or a write token alone cannot sign* hold: an owner other than the tagger approves each signing run. The **next** key (rotation) is generated and kept offline by an owner (an encrypted file on that owner's own machine and a backup they choose), never in the Environment, the repository or any agent's reach; no agent ever handles a real private key. `[KNOWN GAP]` a compromised owner account (or two colluding owners) can still approve a signing run and sign a malicious release. Rotation and leaks as in FR-014. *Proposed*: A for phase 1, then C. Creating the environment, its reviewers and the secret are repo settings = owner approval.
- **D4 Fork source rules.** A the built-in source only (no override); B override in Settings with a trust warning and a native confirmation (FR-003), GitHub `owner/name` only; C B plus any HTTPS feed URL. *Proposed*: B; an organization may still set `updates.feedUrl` (FR-005). Whatever is chosen, an override never enables phase 2 unless the new source's signature checks against a key built into this build (FR-014), so a switched source can at most offer a download the person opens.
- **D5 Cadence.** A at every start; B at start when the last check is older than 24 h, and every 24 h while Durbar stays open; C once a week. *Proposed*: B (spec 081 chose start-only for agent apps; Durbar itself often runs for days).
- **D6 Breaking marker.** A a new `Breaking:` line in changelog fragments (spec 008 FR-173 style) that puts a `### Breaking` section into the release notes, plus a minor bump on `0.x` or a major bump counts as breaking; B a `releases.json`-style file in the repository read from the tag (as Duniya); C an extra release asset. *Proposed*: A (one notes source, as today).
- **D7 Where the download goes.** A the Downloads folder (never overwriting a file: a numbered name); B a private folder in userData, removed after the install. *Proposed*: A, so the person keeps the installer.

### Open questions (not owner decisions; for review)

- **Q1** Version scheme of forks: a fork that keeps upstream version numbers and pulls upstream tags will compare equal or lower; the check compares only versions of the configured source, so it works, but a fork must bump its own versions. Documented in `docs/install.md` (FR-022).
- **Q2** GitHub's unauthenticated API limit is 60 requests per hour per IP address; a company behind one NAT address with many Durbar copies checking at start could hit it. The check then says *GitHub is busy, will try tomorrow*; no retry loop (FR-004).

### User Story 1: I hear about a new version, calmly (Priority: P1)

Ana runs v0.1.27. The day v0.1.29 is published, the top bar's More menu (⋯) and Settings > About show a small *Update available: v0.1.29* line, and one toast says so once. The toast shows once per version (spec 081 `announceRule`). 3. The office, a session start and Settings are never delayed (the check runs after the office is shown, in the background).

### User Story 2: a breaking release is never a surprise (Priority: P1)

v0.2.0 renames floors. The Update dialog starts with a **Breaking changes** card: what changes, what to do, and *Download* is only enabled after *I have read the breaking changes* is ticked. *Skip this version* hides it until a newer release.

**Acceptance**: 1. A fake release with a `### Breaking` section, or a `0.1.x → 0.2.0` jump, shows the card. 2. *Download* stays disabled until the box is ticked. 3. Skip, then a fake v0.2.1: shown again.

### User Story 3: the download is checked before I can open it (Priority: P1)

Ana clicks *Download*. Durbar fetches the Windows NSIS installer (her install type) and `SHA256SUMS.txt` from the same release, checks the hash, marks the file as an internet download, and offers *Open installer* / *Show in folder*. The dialog says *Checked against the release's checksum list*.

**Acceptance**: 1. Matching hash: offered, and the file carries the zone mark (Windows) or quarantine flag (macOS). 2. Wrong hash, missing line, two lines for one file, a missing `SHA256SUMS.txt`: the file is deleted, the dialog says *The download does not match the release's checksum; nothing was kept*, no *Open*. 3. A redirect to a host off the allow-list, a body over the cap, a timeout: refused, nothing kept.

### User Story 4: a fork checks the fork (Priority: P1)

Ravi forks the repository to `ravi/durbar` and builds releases with the same workflow. His users' copies check `ravi/durbar`, never `three-feathers/agent-durbar`, and the reverse.

**Acceptance**: 1. A build with `GITHUB_REPOSITORY=ravi/durbar` bakes `ravi/durbar`; Settings > About shows *Updates from ravi/durbar (built in)*. 2. A release answer whose `html_url` or asset URL names another repository is refused. 3. A redirect from a renamed repository is not followed: *The update source moved; change it in Settings*.

### User Story 5: I can change the source, with a warning (Priority: P2)

Ravi's user wants upstream releases. Settings > Updates > *Update source*: type `owner/name`; Durbar reads that repository's releases first (nothing changes on failure), then a native confirmation: *Updates from three-feathers/agent-durbar replace this build (built from ravi/durbar)*. The card then always shows *Updates from three-feathers/agent-durbar (changed by you)* and *Use the built-in source*.

### User Story 6: off means off (Priority: P1)

*Check for Durbar updates once a day* off: no request is made, not at start, not on a timer; *Check now* still works when pressed (spec 081 FR-022 pattern). `updates.mode: "off"` from the organization: the whole section is hidden with *Turned off by your organization* and *Check now* is gone too.

### User Story 7: in place, with consent (Priority: P3, phase 2)

On Windows NSIS and Linux AppImage, after a checked download and a valid signature against a key built into this build (never without one): *Install and restart* → native confirmation listing the open sessions (they are ended, as spec 081 FR-013 does for agent apps) → pre-update backup → apply → restart. A failure leaves the old version running and says what happened.

### Edge cases

- No network, DNS failure, proxy refusal, TLS error: card *Could not check: <masked reason>*; no toast; next try at the next cadence (FR-004).
- A release list with HTML, `javascript:` links, bidi or control characters, 10 MB of text, 500 releases: notes shown as text, clipped (FR-010); list capped (FR-007).
- Running version newer than the latest release (a dev or fork build): *Up to date (this build is newer than the latest release)*.
- No asset for this OS/arch/type in the release: *No download for this system in v0.1.29*, *Open the release page*.
- Portable Windows build, extracted AppImage, dev run: install type detected (FR-012); dev runs (`npm start`, unpackaged) never check (FR-004).
- The simulator: canned feed, canned download, never the network (FR-020).

## Requirements *(mandatory)*

### Source

- **FR-001** **Built-in update source.** At package time the source is fixed into the build as a GitHub `owner/name`: `DURBAR_UPDATE_REPO` when set, else `GITHUB_REPOSITORY` (the repository whose workflow builds it, so a fork's release builds name the fork), else `package.json` `repository.url`. Parsed with one strict pure parser (Duniya `repo.js` rules: `owner/name`, `github:owner/name`, `https://github.com/owner/name[.git][/]`; owner `[A-Za-z0-9][A-Za-z0-9-]{0,38}`, name `[A-Za-z0-9._-]{1,100}`, not `.`/`..`; nothing else). An unparseable value fails the build. The parsed slug, its origin (`env`, `ci`, `local`) and, with D3 C, the public keys are written by `scripts/copy-assets.js` (which already writes `appversion.js` at build time, spec 008 FR-179) into `dist/main/updatesource.json`, inside the asar (covered by the asar integrity fuse, spec 008 FR-037); a missing or invalid file means no source and no check. **At run time the app reads only that file**: `DURBAR_UPDATE_REPO`, `GITHUB_REPOSITORY` and `package.json` are ignored (a test sets them at run time and sees no change). Origin `ci` means *built by any GitHub Actions run of that repository* (a release tag or any other workflow run), not *an official release*; only the signature (FR-014) says that. A build with origin `local` (no release workflow) has the check off by default and Settings says *This build was made outside a release workflow; updates from <owner/name>*, so a fork built by hand never follows upstream unnoticed. `release.yml`'s summary prints the baked source and warns (does not fail) when it differs from `package.json` `repository`. No owner/name is written in `src/`.
- **FR-002** **The source is always visible.** Settings > About and the Update dialog say *Updates from <owner/name> (built in)* or *(changed by you)* or *(set by your organization)*.
- **FR-003** **Override (D4 B).** Settings > Updates > *Update source*: `owner/name` or `https://github.com/owner/name` only (FR-001 parser). The window sends only the typed text; **main** parses it, reads that source's release list (FR-007) and on any failure changes nothing and says why; then main shows a native confirmation with a trust warning: *Updates from <new> are made by whoever controls that GitHub repository, not by the makers of this build (<built-in>). Durbar can only check that a download matches that repository's own list. Only switch to a repository you trust.* Saved in settings as the slug only; *Use the built-in source* removes it. Comparison is case-insensitive. `[KNOWN GAP]` a person (or a program running as that person) who edits the settings file directly skips the confirmation; Settings then still shows *(changed by you)* and the source, and phase 2 stays barred unless the signature checks (FR-014).
- **FR-004** **When Durbar contacts the source** (D5 B). Only in a packaged build, never in a dev run or the simulator: at start, after the office is shown and startup detection has finished, when the last check is older than 24 h; every 24 h while open; and when the person presses *Check now*. One request at a time, 10 s limit. Failures are silent apart from the card (*Could not check: ...*), no retry loop. The last check time and result (versions only) are kept in settings. **Default: on** (owner decision D2 = A, 2026-11-22); it takes effect with the code PR that builds this check (T010), not before. With the switch off or `updates.mode: "off"`, no timer is armed and no request object is created (a test counts both). Turning the switch or the policy off **while a check runs** aborts that request, discards its result and disarms the timer: no further call (a test turns it off between the request and the answer).
- **FR-005** **Organization policy** (spec 076 FR-174). `updates.mode: "off"` hides the feature and makes no request; `notify` allows phase 1 only; `auto` allows phase 2 apply but never without the person's confirmation (this spec has no silent install; 076's `auto` wording gets a delta). `updates.feedUrl`: accepted only when it is `https://github.com/<owner>/<name>` (FR-001 parser), then it is the source and the override is locked (*set by your organization*); any other value fails closed (no check, *Your organization's update address is not supported by this version*). An unreadable policy fails closed (spec 081 FR-022). Read through `updatePolicy()` (today `none`, issue #1125).
- **FR-006** **What the check sends and reveals.** One HTTPS GET to the allow-listed URL (FR-007) with `User-Agent: AgentDurbar`, `Accept: application/vnd.github+json`, `Accept-Language: en`, no cookies, no credentials, no query beyond `per_page`, no version, machine or user identifier; Chromium's network stack adds its own transport headers (such as `Accept-Encoding`; the exact set is recorded by a test against the fake request layer and listed in `docs/safety.md`). What is revealed: GitHub sees the IP address, the time and the repository slug (so which fork this copy follows); a configured proxy (spec 076) sees the host `api.github.com` and the time; the timing shows roughly when Durbar starts. A download additionally reveals the OS, architecture and install type (the asset name) to GitHub and its asset host. The README *Safety model*, `docs/safety.md` and the Settings note say all of this in plain words.

### Feed

- **FR-007** **Exact allow-list.** The list request is `https://api.github.com/repos/<owner>/<name>/releases?per_page=30` for the configured slug and nothing else. `redirect: 'manual'`: any 3xx is refused (a renamed repository says so, User Story 4). 200 only, `content-type` `application/json`, body at most 2 MiB (counted while reading; the request is aborted past it), then FR-008's schema; anything else is *Could not check*.
- **FR-008** **Feed schema** (pure, strict). The body must be a JSON array of at most 30 objects; anything else refuses the whole feed. Per entry, only these fields are read and each must have its type, else the entry is dropped: `tag_name` string matching strict `vMAJOR.MINOR.PATCH[-pre]` (at most 64 characters, spec 081 FR-005 rules); `draft`, `prerelease` booleans; `published_at` an ISO 8601 string that `Date.parse` accepts; `html_url` string; `body` string or `null` (at most 1 MiB, else the entry is dropped); `assets` an array of at most 40 objects with `name` string matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,199}$` and not containing `..`, `size` an integer with 0 < size <= 600 MiB, `browser_download_url` string. Unknown fields are ignored, never used. Two entries with the same `tag_name` refuse the whole feed. Drafts and pre-releases are ignored. URLs are parsed with `new URL()` and must have protocol `https:`, host exactly `github.com`, no username, password, port, query or fragment, and a pathname equal (slug case-insensitive, the rest exact) to `/<slug>/releases/tag/<tag>` (`html_url`) or `/<slug>/releases/download/<tag>/<name>` (assets).
- **FR-009** **Breaking** (D6 A). A release is breaking when its notes contain a `### Breaking` heading (written by `scripts/release-notes.js` from a new `Breaking: <text>` fragment field, spec 008 delta), or the jump grows the major version, or, on `0.x`, the minor version. The update is breaking when any release between running and target is. **When the list cannot show the whole way** (the running version is older than the oldest stable entry on the page, or the page is full and the running version is not on it), the update counts as breaking and the card says *Some releases between vA and vB are not listed; read the release notes on GitHub before you update*.
- **FR-010** **Notes are untrusted text.** Rendered with `textContent` only, never `innerHTML` or a Markdown renderer; control and bidi characters removed; `redact()` and `maskHomePaths()` applied; each release body clipped to 8 KiB, the whole dialog to 64 KiB, with *Open the release page* for the rest. Links are shown as text and never followed; *Open the release page* opens only the validated `html_url` through the existing external-open path.

### Update card, decision, download

- **FR-011** **Update card and dialog.** A line in the More menu (⋯) and Settings > About: *Up to date · v0.1.27 · checked 2 h ago*, or *Update available: vX* (one toast per version, spec 081 `announceRule`). The dialog: *You are running vA. N releases come with it*, the breaking card first (FR-009, with the tick box of User Story 2), then each release (version, date, notes), newest first, older ones folded; buttons *Download*, *Remind me in 7 days*, *Skip this version*, *Close*. Text at least 10.5 px; fits 1280x800; keyboard and screen-reader operable.
- **FR-012** **Install type** (pure, injected environment). `win32` + `process.env.PORTABLE_EXECUTABLE_FILE` = portable; `win32` packaged otherwise = NSIS; `linux` + `process.env.APPIMAGE` = AppImage; `darwin` packaged = dmg; anything else = *unknown* (notes only). Arch from `process.arch`. The asset name is built from spec 008's `artifactName` patterns (`Agent-Durbar-Setup-<v>.exe`, `Agent-Durbar-<v>-portable.exe`, `Agent-Durbar-<v>-x86_64.AppImage`, `Agent-Durbar-<v>-<arch>.dmg`) and must be in the release's asset list.
- **FR-013** **Checked download.** On *Download* only. The window sends the target version string only; **main** resolves the asset from its own last validated feed (FR-024). The file name is the **expected** name built by FR-012 from the version; the feed's asset with exactly that name must exist, and the feed's name is never used as a path. Fetch `SHA256SUMS.txt` (at most 64 KiB) and the asset from their FR-008 URLs; redirect hops allowed only to `objects.githubusercontent.com` and `release-assets.githubusercontent.com` over HTTPS (at most 3 hops, each checked with `new URL()` as in FR-008); size at most the feed's `size` and at most 600 MiB; 10 min limit; progress and *Cancel*. The redirect URLs carry signed query tokens: they are never shown, logged, saved or put in an error text (FR-025). Writing: into a private folder `userData/updates/` (0700/0600 on macOS and Linux; on Windows the per-user profile ACL is the protection, `[KNOWN GAP]` no extra ACL is set), the file is created exclusively (`wx`), a symlink or existing file at the path refuses, SHA-256 is computed while streaming. Exactly one `SHA256SUMS.txt` line (`<64 hex>  <expected name>`) must name it; mismatch, no line or two lines = delete and refuse (User Story 3). Then the zone mark / quarantine flag is set (FR-015) and the file is copied to its destination (D7 A: the Downloads folder) with an exclusive create (never overwriting; a numbered name), and the copy is hashed again; only a copy that matches is offered. Failures: full disk, missing or unwritable Downloads folder, a move across file systems (a copy, never a rename across volumes), a cancel: the partial file is deleted, the private copy stays and *Show in folder* opens the private folder. Partial files left by a crash are deleted at the next start. **Right before *Open installer* and before any apply, main hashes the file again** and refuses on a change; phase 2 applies only from the private folder copy, never from Downloads.
- **FR-014** **Signature** (D3). Phase 1 has no signature, and every user text says *checked against the release's checksum list*, never *verified* or *signed*. **Phase 2 (in-place apply) is never offered without a signature checked against a public key built into this build (FR-001)**, whatever the source, override or policy; a build without a key says *In-place update is not set up for this build* and stays at phase 1. Format (D3 C, one format): the release carries `SHA256SUMS.txt.sig`, one ASCII line `durbar-sig-v1 <key-id> <base64 Ed25519 signature>` where the signature is over the exact bytes of `SHA256SUMS.txt`, `key-id` is the first 16 hex characters of SHA-256 of the raw 32-byte public key; the app accepts only a key-id it has built in and checks with `crypto.verify(null, sums, publicKey, sig)`. Not minisign. Key home: the GitHub Environment `update-signing` with required reviewers, *Prevent self-review* and `v*`-only deployments (D3); `[KNOWN GAP]` a compromised owner account can still sign. Rotation: a build carries the current and the next public key; the next private key is generated and kept offline by an owner (D3), not in the Environment; a planned rotation: that owner puts the next key into the Environment, generates a new offline next key, and ships a release signed by the current key that bakes both new public keys, then signs with the former next key. **Replay**: `SHA256SUMS.txt` names files that carry the version (`Agent-Durbar-Setup-<v>.exe`), so a list signed for another version cannot vouch for this version's expected file name; the app also requires that every file name in the signed list carries the target version and that the list names the expected file (FR-013), so an old, validly signed list served with another release is refused. Leak: the owners remove the key from the environment, publish a release signed with the next key that drops the leaked one, and say so in the release notes and `SECURITY.md`; `[KNOWN GAP]` builds that never take that release keep trusting the leaked key, so phase 2 still asks for consent every time and shows the key-id.
- **FR-015** **Open, as an internet download.** Before a file is offered, main marks it as downloaded from the internet: on Windows it writes the `Zone.Identifier` alternate data stream (`[ZoneTransfer]`, `ZoneId=3`, `HostUrl` = the release page) so SmartScreen and Office-style checks see an internet file; on macOS it sets the `com.apple.quarantine` attribute (by `execFile('/usr/bin/xattr', ['-w', 'com.apple.quarantine', <value>, <path>])`, fixed absolute binary, no shell, the path from main's own state) so Gatekeeper checks it; on Linux nothing exists to set. Durbar never removes either mark. If the mark cannot be set (a FAT/exFAT drive, a failing `xattr`), *Open installer* is not offered: only *Show in folder*, with *Durbar could not mark this file as downloaded from the internet, so your system may not check it. Open it yourself only if you trust it.* *Open installer* (`shell.openPath`) for NSIS and dmg; *Show in folder* (`shell.showItemInFolder`) for every type; the AppImage file gets mode `0755`. Phase 1 never runs a file and never passes arguments. `[KNOWN GAP]` both marks are platform knowledge, not checked on a real PC or Mac (T020).
- **FR-016** **Snooze and skip.** *Remind me in 7 days*: no toast and no menu badge until then (the Settings line still shows it). *Skip this version*: hidden until a newer release (a newer breaking release always shows). Both saved as version + time in settings.
- **FR-017** **Pre-update backup.** Before *Open installer* (phase 1, offered and ticked by default) and before every apply (phase 2, required: no backup, no apply): copy Durbar's settings file and session index (names, folders, times: the files spec 109 exports) to `userData/backups/pre-update-<from>-<to>/`, 0700/0600, keep the last 3. Never tokens, `.env`, agent-app config folders (`~/.copilot`, `~/.claude`, `~/.codex`) or session transcripts. Once spec 109's writer exists, it is used instead of a copy (same exclusions).
- **FR-018** **After the update.** The first start of the new version shows spec 107's What's new strip; this spec adds nothing beside it. **Links follow the built-in source**: spec 107's links (`<REPO_URL>/releases`, `<REPO_URL>/releases/tag/v<version>`) and its bug-form base use the slug of `dist/main/updatesource.json` (FR-001), not the fixed `REPO_URL` of `src/shared/about.ts`: `about.ts` gets a `repoUrl(slug)` that returns `https://github.com/<slug>` for a valid slug and `REPO_URL` otherwise, and a build test fails when the baked slug and the URL spec 107 uses disagree. A dated delta in spec 107 says so (T027). An override (FR-003) does not move these links: they name the repository the build came from.

### Phase 2 and 3

- **FR-019** **Apply only with consent, every time, and only signed.** Phase 2 needs FR-013's checks, FR-014's signature against a built-in key, and FR-017's backup. Windows NSIS: a native confirmation (version, key-id, every open session to be ended: a whole-app gate, not spec 081's one-app `UpdateGate`), then the installer from the private folder is started with fixed argv (the NSIS silent switch `/S` and electron-builder's `--updated` and `--force-run`, plan D4; `[KNOWN GAP]` until checked on a real Windows PC) via `spawn` without a shell, and Durbar quits. Linux AppImage: `$APPIMAGE` is checked first and phase 2 is refused (phase 1 stays) unless it is an absolute path to a regular file (`lstat`, not a link, and no link in its parent folder's real path differs from the path), owned by the current user, ending in `.AppImage`, whose folder is writable by the user, and whose file is the one this process runs from (same device and inode as at start); then the new file is written beside it with an exclusive create, hashed again, renamed over it (the old one kept as `<name>.old`), Durbar restarts it. Failure: the old copy stays and runs. No automatic apply in any mode.
- **FR-020** **Simulator.** `DURBAR_SIM`: a canned feed (one up to date, one update, one breaking, one checksum mismatch) and a canned download; never the network; the apply step is a canned success.
- **FR-021** **Settings.** `updates.selfCheck` (boolean; absent = the FR-004 default), `updates.source` (slug or absent), `updates.snooze` (`{version, until}`), `updates.skip` (version), `updates.lastCheck` (`{at, latest}`), validated on read; a bad value is ignored (treated as absent). No token, URL or file path is ever saved.
- **FR-022** **Docs.** `docs/install.md` *Updates* (per OS table above, the honest limits), *For forks* (FR-001, version numbers Q1, D3 key setup); README *Safety model* (the one request); `docs/safety.md`; `docs/features.md` and `docs/feature-inventory.md` rows. `docs/install.md` and `docs/safety.md` carry this text (or a plainer version of it): *Durbar checks a download against `SHA256SUMS.txt` from the same GitHub release. That catches a broken or wrong download. It does not prove who made the release: someone who can publish releases in that repository can publish matching files and a matching list. Install only from a repository you trust.* User text never calls the checksum check *verified*.
- **FR-023** **macOS in place** (phase 3) only after spec 014 signing (D1). Not built here.
- **FR-024** **Main decides every URL, path and source.** The new IPC channels take only a version string (or nothing) from the window: `selfupdate:get`, `selfupdate:check`, `selfupdate:snooze(version)`, `selfupdate:skip(version)`, `selfupdate:download(version)`, `selfupdate:cancel`, `selfupdate:open(version)`, `selfupdate:reveal(version)`, `selfupdate:openReleasePage(version)`, `selfupdate:setSource(text)`, `selfupdate:useBuiltInSource`. A version must be one main has in its last validated feed, else the call is refused. Main opens only its own validated `html_url`, the file it wrote and re-hashed, and does the read-first check and native confirmation of FR-003 itself. Tests call each channel with forged arguments (a URL, a path, `../`, an object, a version not in the feed, a slug in `selfupdate:open`) and see a refusal and no request, open or file change.
- **FR-025** **No tokens.** Durbar never reads `GITHUB_TOKEN`, `GH_TOKEN` or any credential for this feature, never sends an `Authorization` header, and never stores a token; the rate limit is handled as Q2 says. Redirect URLs (signed query tokens) and their query strings never reach a log, a setting, an error text, the window or a crash report; error texts name the host only.

## Success Criteria *(mandatory)*

- **SC-001** With the switch off (and with `updates.mode: "off"`), a 24 h simulated clock run makes zero requests (fake request layer counts 0).
- **SC-002** Every refusal case of FR-007, FR-008, FR-013, FR-014, FR-015, FR-024 and FR-025 has an offline test, and each has a planted mutant that the test catches (tasks.md).
- **SC-003** A fork build (`GITHUB_REPOSITORY=ravi/durbar`) checks only `ravi/durbar`; an upstream build only `three-feathers/agent-durbar` (test with both baked values against a fake feed of each).
- **SC-004** A release body with `<img src=x onerror=...>`, `<script>`, `[x](javascript:...)`, bidi and control characters shows as plain text in the dialog (UI driver reads `innerHTML` contains no element from it).
- **SC-005** No test or CI step contacts GitHub; the simulator never does.

## Assumptions

- Releases stay on GitHub with `SHA256SUMS.txt` and spec 008's asset names; a renamed asset pattern needs an FR-012 update in the same PR.
- The existing per-user NSIS install (`perMachine: false`) lets the installer replace the app without admin rights.
- GitHub's REST release list stays available unauthenticated.

## Out of scope

- Pre-release channel (alpha, test builds), rollback to an older version, delta updates, `.deb`/`.rpm`, a feed host other than GitHub (FR-005 fails closed), Windows portable in place, any silent or scheduled install.
