**Input**: Overnight owner request (2026-10-20): "research what could come as natural evolution and autonomously implement new features which make sense the way we are evolving without making app messy or clumsy". Research: `evolution.md` idea 1, "what did my agent change, and on which branch?" is the first question after a turn, and Durbar does not answer it today.

## User Scenarios

### Story 1 - See the branch and the changes at a glance (P1)
In a chat, the folder chip in the header also shows the git branch and how many files have uncommitted changes, for example `~/work/api · main · 3 changed`. Nothing changes for a folder that is not a git repository, or when git is not installed.

### Story 2 - See which files changed (P1)
Clicking the folder chip, when it shows changes, opens a small dialog: the branch (and ahead/behind of its upstream), then each changed file with its state (modified, added, deleted, renamed, untracked) and its +/− line counts. Buttons: **Open in VS Code** (the existing action) and **Done**.

### Story 3 - It stays current without noise (P2)
The status is read when the chat opens and again when the agent finishes a turn (it goes idle), at most once every 5 seconds per folder. There is no polling while nothing happens.

## Requirements

- **FR-001** Main reads the status only for a folder Durbar already knows (the agent's own `cwd`; the renderer passes an agent id, never a path). It runs `git` with argv only (no shell):
  - `git -C <dir> status --porcelain=v1 --branch -z --untracked-files=all`;
  - `git -C <dir> diff HEAD --numstat -z` for the line counts.

  Limits: 4 s per command, 512 KB of output, 200 files listed (with "and N more"). Read-only: no git command that writes (no `fetch`, no lock-taking commands; `--no-optional-locks` is passed).
- **FR-002** The result is `{ repo: false }`, or `{ repo: true, branch, detached?, ahead?, behind?, files: [{ path, state, added?, removed? }], more }`. Paths are relative to the repository, at most 300 characters, with control characters removed. On any error, `{ repo: false }`: the chip simply shows nothing extra.
- **FR-003** The folder chip shows ` · <branch>` (or ` · detached`) and, when files changed, ` · N changed`. The chip becomes a button only when there is something to show; its accessible name says the same. The text is at least 10.5px and the chip still fits (it truncates the path first, as today).
- **FR-004** The dialog uses the shared dialog (`askDialog`). Lines are text only (never HTML):
  - `M  src/app.ts  +12 −3`, using A/D/R/? for added, deleted, renamed and untracked;
  - binary files say "binary";
  - the body says the branch and ahead/behind.
- **FR-005** Refresh: on chat open and on each turn end, debounced to 5 s per agent. One request in flight per agent. Nothing runs for a sub-agent's helper chat (it uses its parent's folder).
- **FR-006** Simulator: agents report a fixed status (branch `main` or `feature/login`, 0–4 changed files), so the driver and screenshots need no git repo.
- **FR-007** Windows, macOS and Linux: `git` is found on PATH with the existing detection (no hard-coded path); `-z` output avoids quoting differences.

## Out of scope
Committing, staging, discarding or diffs inside Durbar (VS Code does this). Status of folders without an open chat.

### 2026-10-25: git never runs a command from the folder's own config (security, #719)
Finding: Ruben's agent, review of #718 (`real:`, 2026-10-25): git honours the folder's own `.git/config`, so a `core.fsmonitor` command set there ran 8 times during the status/diff calls; `-c core.fsmonitor=false` made it 0. Issue #719 tracks the related missing `--no-ext-diff --no-textconv`. A clone does not bring a `.git/config`, but a folder someone else prepared (an archive, a shared drive) can.

- **FR-008** Every git call in `src/main` goes through the one runner, `nodeGitExec` in `src/main/gitstatus.ts`, and the runner (not each caller) makes it safe:
  - **only read-only subcommands**: `status`, `diff`, `rev-parse`, `rev-list` (and its own `config` read, below); anything else is refused without running git. So an alias (`alias.*`) can never run: git never lets an alias replace a built-in command, and no other command is run;
  - **global options** before every call: `--no-pager`, `--no-optional-locks`, and `-c` overrides that beat the repository's config: `core.fsmonitor=false` and `core.useBuiltinFSMonitor=false` (no fsmonitor hook, also not in a submodule, since `-c` is passed down to the git that runs there), `protocol.allow=never` and `protocol.<file|git|ssh|http|https|ext>.allow=never` (no transport, so a lazy fetch of a partial clone cannot start `core.sshCommand`, an `uploadpack` command or a credential helper), `log.showSignature=false` (no `gpg.program`), `credential.helper=` (an empty value clears every listed helper), `diff.submodule=short` and `status.submoduleSummary=false` (no git started inside a submodule);
  - **environment**: built from Durbar's own **without any `GIT_*` variable** (compared in upper case for Windows) or `SSH_ASKPASS`: a `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG*`, `GIT_EXTERNAL_DIFF`, `GIT_PAGER` or `GIT_ASKPASS` in Durbar's environment would point git at another repository or start a helper (review on #722: a set `GIT_DIR` made the status list another repository's files). Then `GIT_NO_LAZY_FETCH=1` (a git that knows it refuses the lazy fetch itself; 2.43 does), `GIT_ALLOW_PROTOCOL=` (empty: no transport, and it replaces every `protocol.*` setting, so a folder's own `protocol.<name>.allow=always` for ftp or a `git-remote-<x>` helper cannot bring one back, review on #722), `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`;
  - **caller options are an allow-list** per subcommand (review on #722): a caller's flag comes after the overrides, so `--textconv`, `--ext-diff`, `--submodule=diff` or `--ignore-submodules=none` would undo them. Only `status --porcelain=v1 --branch -z --untracked-files=all|normal`, `diff --numstat --shortstat -z --no-ext-diff --no-textconv`, `rev-parse --verify -q` and `rev-list --count` pass (what spec 063 and spec 085 use; the real-git test makes #718's calls exactly as its `sessionsummary.ts` does); any other argument that starts with `-` before `--` is refused before git starts. Revisions (`HEAD`, `<sha>..HEAD`) and paths after `--` pass;
  - **filter drivers** (`filter.<name>.clean/smudge/process`, chosen by `.gitattributes`): git has no switch for them, and `status` runs a clean filter whenever a file's timestamps do not match the index (every file of an unpacked archive). The runner first reads the names of every driver that has a command, from any config file (`git config -z --name-only --get-regexp '^filter\..*\.(clean|smudge|process)$'`; reading config runs nothing), then blanks `clean`, `smudge` and `process` and sets `required=false` for **each of them, the user's own included**. A driver from the user's `~/.gitconfig` is not safe either: git-lfs runs `lfs.extension.<name>.clean` from the folder's own `.git/config` as a command (review on #722, round 3; `read:` git-lfs-config(5); a stand-in filter that does the same ran the folder's command in the test until every driver was off). **Limit (the price of never running a filter from a folder):** a file stored through a clean filter (git-lfs, git-crypt, any other) that has been touched can show as "changed" in Durbar's folder status while plain `git status` says it is clean. A driver name that `-c` cannot express (it contains `=`) makes the call fail, so the folder shows `{ repo: false }`;
  - **after `diff`**: `--no-ext-diff --no-textconv` (`diff.external`, `diff.<name>.command`, `diff.<name>.textconv`; #719), `--ignore-submodules=dirty` and `--submodule=short` (with the folder's `diff.submodule=diff`, a patch diff of a moved submodule commit started `git diff` inside the submodule, where its own diff command ran; review on #722); **after `status`**: `--ignore-submodules=dirty`, so git does not start a `git status` inside each submodule (whose own filter drivers the runner did not read). A submodule whose commit moved still shows as changed; only "has uncommitted changes inside" is no longer reported.
  - Still `execFile` with an argv array and `shell: false` (pinned by a test with the time and size bounds); `safe.directory` and the ownership check are unchanged (nothing sets them).
- Cannot fire for these read-only commands, so no override is added (the real-git test plants them anyway and checks they did not run): `core.pager`/`pager.*` (stdout is a pipe, and `--no-pager`), `core.editor`/`sequence.editor` (only commit, rebase and edit commands open an editor), `core.hooksPath` and hooks (no hook runs for status, diff, rev-parse or rev-list; `--no-optional-locks` means the index is not written, so no `post-index-change`), `core.sshCommand` (only a transport, refused above).
- `test:` `scripts/test-gitstatus.ts`: the runner's argv and env (fake run), one assertion per override, the refused subcommands (`commit`, `fetch`, an alias name, a caller's own `-c`) and the refused driver name; the exact file, argv and `execFile` options of a real call through a fake `execFile` (`shell: false`, 4 s, 512 KB, `windowsHide`, the env), and a source check that `nodeGitExec` is exactly that runner over Node's `execFile` with no other process call in the file. A planted mutation of each of 50 overrides (plus the round-3 "keep the user's drivers" mutants), options and checks (`shell: true` behind a cast, another time or size bound, a second raw `execFile`, each env rule, the option allow-list) fails it; a plain `shell: true` fails `npm run typecheck` (the option's type is `false`).
- `real:` 2026-10-25, Linux, git 2.43.0, and Windows CI (the same test, in `npm test`; skipped with a note when git is absent, except under CI, where a missing git fails it, so a green *Build and test (windows-latest)* means it ran there; on pull requests the macOS job is the FR-106 stub, so **not verified on macOS** before merge, checked on `main` and nightly): a scratch repository plants in its own config `core.fsmonitor`, `filter.*.clean/smudge/process/required`, `diff.*.textconv`, `diff.*.command`, `diff.external`, `core.pager`, `pager.status`, `pager.diff`, `core.editor`, `sequence.editor`, `core.hooksPath` (with hook scripts), `core.sshCommand`, `gpg.program` with `log.showSignature`, `alias.st` and `alias.status`, `diff.submodule=diff`, `status.submoduleSummary`, `credential.helper`; an embedded repository with its own fsmonitor, filter, diff command, textconv and `diff.external`, whose commit moved; a partial clone whose missing blob needs a lazy fetch over ssh; a second one over a fake `git-remote-testhelper` that the folder allows itself (`protocol.testhelper.allow=always`), run with `GIT_NO_LAZY_FETCH` removed to stand for an older git; and a `GIT_DIR` set in Durbar's environment, pointing at another repository. A second repository has a file stored through a git-lfs-like filter from the user's own global config (in a temporary `HOME`) that runs the folder's `lfs.extension.x.clean`, which the folder sets, and a file with a filter from its own config: neither filter nor the extension runs, and the first file shows as changed (the limit above). A mutant that keeps the user's drivers makes the stand-in run the folder's `lfs.extension` command. A positive control runs the fake-helper fetch without `GIT_ALLOW_PROTOCOL` and must see the helper start, so a pass on a platform proves the empty value works there. #718's calls are made exactly as its `sessionsummary.ts` makes them (`status --porcelain=v1 -z --untracked-files=normal|all`, `rev-parse --verify -q HEAD`, `diff --no-ext-diff --no-textconv --shortstat|--numstat <sha> --`, `rev-list --count <sha>..HEAD|HEAD`). The caller flags `--textconv`, `--ext-diff`, `--submodule=diff` and `--ignore-submodules=none` are refused. Every call the app makes (spec 063 status and numstat, spec 085 rev-parse, rev-list, shortstat) plus a full patch diff ran through `nodeGitExec`: no planted command ran, and the status is still right. Before the fix the same repository ran fsmonitor, clean, process, the submodule's fsmonitor and clean, and the lazy-fetch ssh command. Mutations checked against the real-git part alone: dropping `core.fsmonitor=false`, the filter overrides, `--ignore-submodules=dirty` on status, `--no-ext-diff`, `--no-textconv`, all of the transport refusals, `GIT_ALLOW_PROTOCOL`, or both submodule diff settings each makes a planted command run; passing Durbar's environment through makes the status list the other repository; dropping the option allow-list lets `--textconv` through.
- `[KNOWN GAP]`: run by hand on Linux only; on Windows only through CI (the planted commands are `sh` lines, which Git for Windows runs through its own `sh`); **not verified on macOS** before merge (PR CI runs the FR-106 stub there), checked on `main` and nightly. A git that does not know `GIT_NO_LAZY_FETCH` (older Git for Windows, Apple git) relies on `GIT_ALLOW_PROTOCOL=` and the `protocol.*` overrides; the test stands for it by removing the variable, not by running an old git. A git that does not know `GIT_ALLOW_PROTOCOL` (before 2.12) is not covered. A git release that adds a new command-running setting is not covered until it is added here. A new caller flag needs adding to the allow-list after checking what it can run.
