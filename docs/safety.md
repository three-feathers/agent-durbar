# Safety model and costs

Permission modes (Read-only, Ask first, Allow all) and spending limits, in detail. Moved out of the [README](../README.md) on 2026-10-31 so the README stays short (spec 021 FR-065); the text is unchanged except for its links.

## Safety model

Agents run **locally, on your machine, as you**, in the folders you add. Every agent has a permission mode. The names are the same for every harness, and Durbar maps them to each tool's own controls.

- **Read-only** (the default): reads inside the session's folders only; everything else is denied. On Copilot, an MCP tool that its server marks read-only still runs without asking (the runtime does not ask Durbar); any other MCP tool is denied (both checked on 2026-10-20). **The runtime trusts the server's own mark:** a server that marks a writing tool read-only gets it run in Read-only, and Durbar never sees a permission request for it (the call still shows in the chat). Add only MCP servers you trust. Claude Code and Codex were not checked for this. Read-only governs agents: a write you ask Durbar itself to make, such as the optional `.durbar/notes.md` of a folder's notes (below), still happens.
  When Read-only stops an edit or a command, the chat says so and offers **Switch to Ask first…**: it opens the mode menu (Read-only, Ask first, Allow all; Allow all still asks you to confirm). Afterwards, ask the agent again; nothing is resent for you ([screenshot](screenshots/003-ro-ask-menu-1440x900.png)).
  On Codex, Read-only and Ask first rely on Codex's own sandbox: checked on Linux (reads limited to the session's folders, writes blocked; 2026-10-21). On macOS and Windows that sandbox depends on the system; if it cannot start, the session does not start and Durbar says why.
- **Ask first**: writes, shell commands, URLs and tools wait for *Allow once*, *Allow “…” for this session* or *Deny* (the same words in Simple and Expert).
  - **How far *for this session* reaches** ([spec 003](../specs/003-permissions-and-approvals/spec.md) FR-013, FR-108): for a **write** it covers every file in that folder, not only the one asked about; *Allow for this session: any arguments* covers every simple command of that name (`git` also means `git push`). The approval card says so in a line above its buttons. A shell command's normal session button allows that exact command only.
- **Allow all**: no prompts. Use it only in folders you trust; it asks once to confirm.

Change the mode any time from the mode chip under the message box or the agent's card menu.

**Why was this allowed?** A tool card that ran without asking you carries a small tag saying why, only when Durbar itself decided it: **Allowed: session rule** (you chose *Allow “…” for this session*), **Allowed: Allow all**, **Allowed: folder read** (a path Durbar checked to be inside the session's folders) or **Allowed: attached file**. Open the card for the full sentence; for a session rule it also has **Undo this rule**, the same removal as the x on the grant chip: the next matching request asks again. A call you answered yourself has no tag. If the agent app allowed something on its own rule (a Claude Code settings rule, a hook, Codex or Copilot's own approvals, an auto-mode classifier), the card shows no tag rather than a guessed reason: none of the agent apps' own reasons is read yet. Not run against a real Copilot, Claude Code or Codex session ([screenshot](screenshots/003-why-allowed-1440x900.png)).

**The agent app's own OS sandbox underneath** ([spec 087](../specs/087-os-sandbox-floor/spec.md)). In **Read-only** and **Ask first** Durbar also turns on each agent app's own OS sandbox, as a second lock under its own checks: Durbar asks the app's sandbox to stop a shell command that gets past them (for example through a folder allow rule you accepted) from writing outside the folder or reaching the network. That is requested, not yet verified on a real session.
- **Claude Code:** its bash sandbox (macOS sandbox; on Linux bubblewrap and socat; Claude Code 2.1.309 or later; an older one runs without the floor and the chip says to update). Read-only: no writes; Ask first: writes only in the session's folders; in your home folder only the session's folders can be read, and credential folders (`~/.ssh`, `~/.aws`, `~/.config/gh` and others) are denied even when a session folder is your home folder (a link there is denied at its target too; per Claude Code's docs the narrower read rule wins and a write deny holds inside an allowed folder; not yet run on a real session); network off; never an unsandboxed retry, and every command still asks you in Ask first. MCP servers, hooks (also a folder's own accepted hooks), the status line and Claude's own file tools are not in it: Durbar's checks cover what they can. **Windows has no Claude Code sandbox** (WSL2 only).
- **Copilot:** its local sandbox (macOS sandbox; Linux bubblewrap 0.5.0+ and slirp4netns; Windows 11 25H2 or 26H1 with ProcessContainer). Shell commands and local MCP servers run in it, with your `PATH` folders readable (resolved through links; never your home folder or a parent of it); network off; no credentials passed in. A session folder that is your home folder (or a parent of it) is opened to the sandbox only where Copilot can deny the credential folders inside it; otherwise commands there are refused by the sandbox. A session whose own folder is a credential folder (or, for Copilot without that support, holds one, such as `~/.config`) is not started in Read-only or Ask first: the chat says why and offers *Change mode…*. Any other folder of a workspace that is (or, for Copilot without that support, holds) a credential folder is left out of the sandbox, and the mode menu names it. Copilot's own file tools are checked by Durbar, not the OS. In Ask first a Copilot command card says *If you approve, Copilot’s sandbox may still let this write outside the folder (seen on Linux, 2026-10-25).*, and the chip tooltip says it too.
- **Codex:** unchanged: its read-limited profile already is the sandbox, and an approval card in Ask first says *If you approve, Codex may run this outside its sandbox.*

The mode chip says it after the mode: *Read-only · Sandboxed*, *Sandbox: checking* (until the app confirms it at its start), *Not sandboxed* (the tooltip says why), *Allow all · Sandboxed (managed)* or *(until a new session)*, and, for Copilot in Ask first, *Sandboxed (partial)* (an approved command may write outside the folder). Allow all keeps the app's default. **Switching a Copilot session from Read-only or Ask first to Allow all also turns its sandbox off in that session** ([#806](https://github.com/three-feathers/agent-durbar/issues/806)): the Allow all confirmation says *Copilot’s OS sandbox is also turned off for this session.*, and switching back re-sends it. This was checked on one real session on Linux (Copilot CLI 1.0.98: cleared in place, then back on), not on macOS or Windows. If Copilot refuses or does not answer within 15 seconds, a short message says so and Durbar treats the sandbox as still on (if a late answer turns it off, the chip follows; if you switch back first, nothing is sent until that answer comes and the sandbox has been sent again): its shell commands still cannot write outside the folder or reach the network, and *Allow all · Sandboxed (until a new session)* on the chip becomes a button. That button, or **Restart without the sandbox** in the mode menu, asks first in its own dialog (grants are cleared, remote control turns off, waiting requests are denied, MCP servers start again with your next message, no AI credits) and then continues the same conversation in a new Allow all session; nothing is re-sent. A Durbar restart, a sign-in refresh, or *End session* followed by your next message also resumes an Allow all session without it (the session you ended takes its kept sandbox with it). Claude Code and Codex need none of this: their next message already uses the new mode's settings. When the sandbox cannot start, **nothing is sent**: the chat says why and offers *Continue without the OS sandbox* (this session; Durbar's own checks still apply) or *Change mode…*; only on native Windows, where Claude Code can never be sandboxed, also *Always continue on this computer* (undo it in Settings > Agent apps, which also shows each app's sandbox line) ([screenshot](screenshots/087-sandbox-note-1440x900.png)). **Not verified on a real session yet:** built and tested on the simulator and with fakes only; every tooltip says *Requested; not verified on a real session.* until a real check per app and system is recorded.
**Your company's own agent-app policy** ([spec 076](../specs/076-managed-config/spec.md) section O). When your organization has set the agent app's own machine policy (Claude Code `managed-settings.json`, Copilot `managed-settings.json`, Codex `requirements.toml`), Durbar reads it, read-only, and greys out what it blocks before anything starts: a permission mode (for example Allow all), a model, an MCP server or an MCP tool, with *Blocked by your organization's <app> policy* as the reason. Each key is read the way the vendor documents it, and Durbar refuses only what the agent app itself would refuse. What Durbar cannot read the vendor's way is shown as advice (*may be blocked by your organization*) and stays selectable. Copilot's policy comes from the Copilot runtime itself, which includes MDM, the registry and the enterprise's server-managed settings. For Claude Code and Codex, Durbar does not read MDM profiles, the Windows registry or server-managed settings; there the app still refuses the way it did before. Checked on fixture files only, not on a real managed machine ([mode menu](screenshots/076-orgpolicy-mode-1440x900.png), [MCP server](screenshots/076-orgpolicy-server-1440x900.png)).

**Coming back to a session.** Each session keeps the mode you last chose for it. After a restart, and when you resume it from *Previous sessions*, it comes back in that mode, also when it was Allow all and the session you opened the list from is in Read-only. Its chat then says which mode it is in and why ("Permissions: Allow all, the mode you last chose for this session"), and an Allow all that came back shows *restored* on the mode chip. A session Durbar has no mode for (one from before this change, or started outside Durbar) gets the folder's mode after a restart, or the mode of the session you resumed it from; the chat says that too. A resumed session that comes back in another mode than the session you opened it from is also written to the activity log. Grants from *Allow for this session* are never kept.

Rules that always apply:
- **The session browser** (spec 080) asks once per app profile before it opens (*Not now* / *Open the browser*). The page never gets Durbar's preload, Node or IPC: the browser view has no preload, a sandbox, no permissions (camera, location, notifications, fullscreen, devices) and no client certificates, and downloads are cancelled. The window gets only the page's address (without a user name or password), its title, loading, history and sound state, and a network error name; while a Durbar menu, dialog or toast covers the page, it also gets a still picture of the page, kept in memory only and never written to disk. A page's own dialogs (`alert`, `confirm`) are the system's boxes. A dialog in a session whose chat is not showing raises a toast naming the session (page text, masked) and brings that chat forward, once per session until you open it yourself, and marks it *Dialog open*. A page that asks before it is left opens Durbar's *Leave this page?* box, with *Stay* focused. A link in a chat is classified in Durbar's main process, not by the window: a web link opens in the session's own browser, a mail link only offers *Open* and waits for your click, and every other kind of link is refused with no button. Page tabs (spec 080 FR-120..FR-133) are decided in main as well: main makes every tab and its id, and refuses a tab id that is not that session's; a page can never open a window, and its *new tab* requests become tabs only for `http`/`https` addresses of the page's own site, only while that session's browser is shown, at most 5 per page load and 10 per session; any other scheme opens nothing and reaches no other app. The tab keys pressed inside a page are kept from the page.
- **Durbar deletes no files of yours, with one exception you ask for** (the project notes file, below). Its own data it deletes only when you ask: *Delete all…* of a folder's notes and *Also delete its notes* when you remove a folder each ask once more in a system dialog the page cannot answer; the second deletes only that folder's file in `<userData>/notes/`, never anything in the project. *Delete…* in Previous sessions goes only through the agent app's own API (Copilot `deleteSession`, Codex `thread/delete`), only from Durbar's own window (not from MCP tools, remote control or schedules), never for a session still in the office, never for VS Code chats, and not for Claude Code. Not yet run against a real session.
- **Notes are private, masked and local** (spec 083). A note is saved on this computer only, in `<userData>/notes/<fingerprint>.json` (the folder 0700, the file 0600, no folder path inside), after Durbar has masked it: token shapes, the secret values Durbar already holds for the folder's MCP extras and the session, and anything split by Markdown marks or control characters. The raw text is never stored or logged. A secret you saved on purpose is therefore lost (only `[redacted]` is kept), and a secret that is neither a known value nor a known shape is stored as written, so do not keep passwords in notes. A notes file Durbar cannot read is never overwritten. There is no notes tool for agents. Nothing is written into your project unless you turn on a folder's *Also keep these notes as `.durbar/notes.md` in the project* (off by default): that file may get committed and pushed with your code (secrets are masked, private ideas are not), anyone or any agent that can write the folder can add notes through it (marked *From the project file*), and Durbar never adds it to git or runs git; the only git-related write is the optional `.durbar/` line in the clone's local `.git/info/exclude`, which you opt into in the dialog and which stays when you turn the switch off. *Delete the file* removes only a `notes.md` holding exactly what Durbar would write, and an empty `.durbar`, except under an attack by a process that can read another folder and swap `.durbar` twice in a tiny window (the other folder's file may then be deleted, or left renamed there). A folder deleted and cloned again at the same path is recognised by its creation time and not written into where the file system records one; where it does not (and on a drive that was remounted) Durbar may not tell, or may ask you to turn the switch off and on. The same folder whose content changes (another branch shipping its own `notes.md`) gets the notes written into that file. Writing that file is Durbar's own write, your own action: the permission mode governs agents and does not stop it, also in Read-only. *Export…* writes the folder's notes, masked again with the secret values known at that moment and without session ids, to a file you pick in the system save dialog (Durbar shows it; the window never chooses a path), readable only by you (0600); it refuses a link, a hard link, a folder or a device at the chosen name and replaces an existing file only after the dialog asked you; it waits while a secret value is still locked. Turning it on and *Delete the file* each ask once more in a system dialog the page cannot answer; while a secret value is still locked in the system key store, the file is not updated, and a file that disappeared (for example another clone at the same path) is not written again until you turn the switch off and on.
- **Creating a folder** ([spec 093](../specs/093-create-folder/spec.md)) writes only the one folder you named, in the place you picked in the system picker: the window never sends a path (Durbar's main process keeps the place behind a one-use token) and the name is checked there. *New repository* runs `git init` through Durbar's one git module (a separate runner from the read-only folder-status runner), with an argument list (no shell), your environment's `GIT_*` variables dropped, a private empty hooks folder (so none of your own git hooks run during it), fsmonitor off and every transport off. None of these settings is written into the new repository, so your hooks apply again to later commits, as after a terminal `git init`. If anything fails, Durbar removes the folder it made, without following links inside it; if it cannot, the message names the folder to remove by hand.
- **Cloning** ([spec 093](../specs/093-create-folder/spec.md) phase 2) runs `git clone --progress --no-recurse-submodules -- <address> .` inside the new folder, through the same git module, with an argument list (no shell). Only `https` and `ssh` can be used, by two layers that each stop the other transports git ships even when your own git config allows them or rewrites the address with `url.<x>.insteadOf`: `GIT_ALLOW_PROTOCOL=https:ssh` (which also stops a remote helper of any other name) and `protocol.<name>.allow=never` for every other transport. Submodules are not cloned. A remote cannot bring git hooks; the private empty hooks folder also keeps your own global or template hooks from running during the clone (they apply again afterwards). fsmonitor is off, git's checks against `.git` look-alike names stay on (`core.protectNTFS`, `core.protectHFS`), `transfer.bundleURI=false`, and `transfer.credentialsInUrl=die` backs up the refusal of a password in the address. **Credentials:** git uses your own credential helper (Git Credential Manager, the macOS keychain, libsecret, a cache) and your ssh agent, as in a terminal; Durbar never sees what they return, and nothing can prompt (`GIT_TERMINAL_PROMPT=0`, no terminal, ssh with `-o BatchMode=yes`; if your `core.sshCommand` is plain `ssh` or `ssh.exe`, `-o BatchMode=yes` is added to it, and any other program, such as plink, is used as it is). If a helper of yours opens its own window, the progress dialog says after 30 s that it is waiting, and Cancel always works; a clone has no time limit. Your environment's `GIT_*` variables do not reach git (`GIT_SSL_NO_VERIFY`, `GIT_PROXY_COMMAND`, `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_CONFIG_*`, ...), except `GIT_SSL_CAINFO` and `GIT_SSL_CAPATH` when they are absolute paths; the usual proxy variables and `SSH_AUTH_SOCK` do pass. If a clone works in your terminal but not in Durbar, put the setting in your git config instead (`http.sslCAInfo`, `http.proxy`, `core.sshCommand`). **Several ssh keys or accounts:** use `Host` blocks in `~/.ssh/config` (or an unconditional `core.sshCommand`); a `core.sshCommand` under `includeIf "hasconfig:remote.*.url:…"` is honoured, but one under `includeIf "gitdir:…"` is not (the new folder is not a repository yet when Durbar reads it), so Durbar's own `ssh -o BatchMode=yes` would be used instead. An address whose user name is a token (`https://ghp_…@github.com/…`) is refused, like a password: git would store it in the new repository's config. Your own filter drivers (Git LFS) stay on, so LFS files download as in a terminal; note that git-lfs reads the repository's own `.lfsconfig` and downloads with its own client, outside the https/ssh limits above. Keep git and git-lfs up to date: Durbar checks no version of either, and a clone of an untrusted repository relies on their own fixes. **The clone writes files the remote chose:** keep git up to date; Durbar checks no minimum git version (distributions fix git without changing the version it prints). Git's output is masked (credentials, tokens, home paths) before the window or the log sees it. Cancel ends only the git that Durbar started and what it started, then removes the folder after git has exited, without following links; quitting Durbar during a clone does the same (it waits at most 5 s).
- **Add project folders, not your home folder or a drive root.** Everything under an added folder counts as the agent's own; Durbar warns calmly when you add one of those.
- **Answering a question** an agent asks is allowed in every mode; it is not an action.
- **A profile (custom agent) from a folder's repository** asks once before it is used and never changes your mode. After you edit it, it asks again (the confirmation is for the file's exact content). Profile files are read and written only by the app's main process, only inside the agent folders (`.github/agents`, `.claude/agents`, `~/.copilot/agents`, `~/.claude/agents`), never through a link that leads out of them, at most 256 KB (64 KB for Claude Code, its own limit), with an atomic write; a new profile cannot take a Windows device name (`CON`, `NUL`, `COM1`...).
- **A folder's own agent setup** (spec 061). The folder's hooks, permission rules and MCP servers (`.claude/settings*.json`, `.mcp.json`, `.codex/config.toml`, `.github/hooks/`, `.github/copilot/settings.json`) are listed in full the first time the folder is added, and again when a file changes, before anything of it runs:
  - each item shows its exact command or rule; only text shaped like a token (GitHub, OpenAI/Anthropic, bearer, JWT, AWS keys, Slack tokens and webhooks, Discord webhooks, Telegram bot tokens) is hidden, MCP env values are shown as `NAME=value` before the command, except where the name looks secret (`DB_PASSWORD=[hidden]`; header values by name only), and arguments with spaces or shell characters are quoted. An item with something hidden, an MCP server that hands env values to a shell or an inline-code interpreter (also behind `env -S`, `timeout`, `nice`, `sudo` and similar), or one whose env sets a code-loading variable (`NODE_OPTIONS`, `BASH_ENV`, `LD_PRELOAD`, `PYTHONPATH`, `BASH_FUNC_*`, `MAKEFLAGS`, ...) starts unticked and says why;
  - a broad allow rule is marked: a whole tool, a wildcard-only pattern, a file tool on the root, home or a drive, and **every shell rule** (`Bash`, `Bash(git:*)`, `Bash(npm test:*)`, any argument);
  - everything is on unless you untick it, but hooks and broad allow rules start off and need your tick on *I have read these hooks (and broad allow rules)…*;
  - *Explain with AI* asks an installed agent app what a hook does and how risky it looks. It is advisory and can be wrong: the command shown is what runs.

  Accepted hooks and allow rules act without asking, even in Read-only, and the mode chip then reads *Read-only + folder rules*. Codex cannot run a folder's hooks from Durbar, and the dialog says so. Reopen the list from the mode menu: *This folder's setup…*. Without your answer, nothing of it applies. Copilot's runtime would otherwise run a repository's hooks by itself (checked 2026-10-20), so Durbar switches that off.
- **Durbar never logs** tokens, session content or your prompts, and stores only what a feature needs, on this computer: a scheduled prompt as you wrote it (`durbar-schedules.json`, readable only by you), your notes (masked, above) and the session names you choose (in Durbar's folder file, and sent to the agent app that has the session). The agent apps keep their own session history; Durbar does not copy it.
- **Masking is best effort.** Debug logs and the agent text shown on the office floor (desk lines, tooltips, the inbox, session titles) are masked by known token shapes and the secret values Durbar already holds: a secret with no recognisable shape is not masked, so do not paste passwords into chats or notes.
- **Linux without a desktop keyring:** Durbar refuses to save MCP secrets (it never falls back to a fixed key), but the agent apps keep their own sign-ins in plain files there: Copilot's MCP sign-ins under `~/.copilot/mcp-oauth-config/` (encryption and file permissions not checked), Claude Code and Codex in a `.credentials.json` in their own settings folder. Durbar does not read or change them; protect your home folder accordingly.

What Durbar does not do (the same list is in Settings):
- **Copilot in Ask first: a command you approve can still write outside the session folder** (seen on Linux, 2026-10-25, [#755](https://github.com/three-feathers/agent-durbar/issues/755)); its sandbox adds a writable place of its own, so the chip says *Sandboxed (partial)*, not *Sandboxed*. Durbar asks Claude Code and Copilot to stay in their folders. In Read-only and Ask first their shell commands also run in their own OS sandbox where it can start (checked on a real session only for Claude Code on Linux in Read-only); their own file tools and Claude Code's MCP servers are held only by Durbar's checks. Codex is held there by its sandbox.
- Spending limits are soft by one call: the call already running finishes and can go a little over the limit; then the chat asks you what to do. The first message after you resume a session may not be held, because its earlier spending is known only after that message's first usage report.
- It does not see your bill; costs are estimates.
- It sends nothing to any server of its own.
- Rooms you hide or switch off still run and cost money.

Codex in Read-only and Ask first gets an OS-enforced permission profile limited to the session's folders, and Durbar refuses those modes when the profile cannot be enforced. Claude Code gets its permission mode, allowed read tools and a check that reads stay inside your folders. Details: [spec 003](../specs/003-permissions-and-approvals/spec.md) and [spec 012](../specs/012-claude-codex-adapters/spec.md). To report a security problem, see [SECURITY.md](../SECURITY.md).

## Costs and caps

- **Copilot** reports usage in AI credits (shown as AIU). A session can have a **spending limit**, at least 30 AI credits:
  - set it in the New session dialog or the limit chip;
  - a global default is in Settings;
  - it is saved per folder.

  It is a soft limit: when it is reached the agent goes on a coffee break "until you raise the limit" (spec 068) and the chat offers *Raise limit / Remove limit / Stop here*. Copilot's own runtime does not stop at the limit (real check, 2026-10-20: a 30-credit session reached 42.6), so **Durbar enforces it**: a turn that crosses the limit is stopped (the call already running can go over by its own cost), and a message sent at or over the limit is held until you choose. Checked on a real session (2026-10-20) and in tests ([spec 011](../specs/011-credit-caps-and-usage-display/spec.md)). Copilot plans, the free one too, have a fixed price: Durbar shows usage, it does not charge you. The office and each room show usage totals, kept across restarts, with a reset in Settings.
- **Claude Code** reports a dollar *estimate*, shown as `≈ $… est.` and never mixed with AIU. A session can have a **spending limit in dollars** (at least $0.01):
  - Durbar passes what is left to Claude's own `--max-budget-usd`;
  - when the limit is reached, the chat offers *Raise limit / Remove limit / Stop here*;
  - the limit is per session.

  With a Claude subscription, nothing is billed per token.
- **Codex** reports tokens, with no price.
