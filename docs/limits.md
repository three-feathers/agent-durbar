# Known limits and roadmap

What has not been verified, what is broad or unsigned, and what is planned. Moved out of the [README](../README.md) on 2026-10-31 so the README stays short (spec 021 FR-065); the text is unchanged except for its links.

## Where it has been run

The short version is in the README's status block; this is the full record.

- **Where it has been run:** Linux by hand every day. macOS by hand on the owner's and a teammate's Macs (macOS 26, Apple Silicon), from source and the simulator, including real Copilot sessions; fixes from those runs are merged. The Copilot MCP Sign in and the keychain change were checked on the owner's Mac with a test build (`v0.1.0-alpha.14-mcptest.1`) before they merged. Windows by hand on a real PC on 2026-10-21 by the owner with a colleague; its findings are filed ([#467](https://github.com/three-feathers/agent-durbar/issues/467): Copilot was not found or offered for install without Node.js).
- **What CI checks on Linux, macOS and Windows:** every change builds and starts the packaged app (spec 012 T044), and the UI checks run on all three (spec 008, [#389](https://github.com/three-feathers/agent-durbar/pull/389)). A real-account end-to-end workflow, where Copilot, Claude Code and Codex each install, sign in and answer on all three OSes, passed 9 of 9 on 2026-10-20 (spec 062, [#402](https://github.com/three-feathers/agent-durbar/pull/402)); real installs of each agent app as a standard and an admin user are checked in CI too (spec 060, [#393](https://github.com/three-feathers/agent-durbar/pull/393)). Since 2026-10-22 pull requests run Linux and Windows; macOS runs on every push to `main` and nightly (spec 008), and the real-account workflow runs on cheap models once a day (and by hand) instead of on every push; it was paused 2026-10-29 to 2026-11-02 while red runs were fixed (spec 062, [#856](https://github.com/three-feathers/agent-durbar/issues/856)), and a failed scheduled run opens a nightly-watch issue.

## Known limits

- **Windows has had one hands-on look.** Linux and macOS are used every day. On Windows the owner and a colleague tried it on a real PC on 2026-10-21 (findings [#467](https://github.com/three-feathers/agent-durbar/issues/467)); that was a manual look, not a scripted check. The packaged app is built and checked on all three systems in CI. **Codex's Read-only and Ask first modes refuse to start on Windows** unless Codex's elevated sandbox is set up and you use the native `codex.exe` (not a `.cmd` shim): Durbar says what is missing and what to do, and you can use Allow all, or Claude Code or Copilot. That refusal follows Codex's documentation and was not tried on a real Windows PC.
- **"Allow … for this session" can be broad.** For a simple shell command it approves every argument of that command name (allowing `git` for this session also allows `git push`), and a write grant covers every file in that folder; code and privilege commands are never offered the any-arguments grant, and you always choose it yourself. Undo it with the x on the grant chip. Not configurable yet (spec 003 FR-013; the approval card offers it as "run <command> (any arguments)").
- **Where your data lives:** the installed app keeps its settings, folders and saved MCP servers in `agent-durbar` under the OS app-data folder (`%APPDATA%` on Windows, `~/Library/Application Support` on macOS, `~/.config` on Linux). `npm start` and the simulator use their own `agent-durbar-dev` folder next to it, so developing never touches the installed app's data. To keep data from an older dev run, start once with `DURBAR_USER_DATA=<old folder>` or copy the folder by hand.
- **An unreadable MCP server file** ([spec 019](../specs/019-mcp-tools-and-context/spec.md)): a damaged or over-size `durbar-mcp.json` in that folder loads as an empty list. Before the next change is saved it is moved next to itself as `durbar-mcp.json.unreadable-<time>`, never deleted; nothing in the window says so yet, and Durbar does not read it back. A file that cannot be moved stops the save with an error instead.
- **Unsigned builds:** expect the OS warnings above.
- **Keychain prompts on a Mac:** macOS may ask whether a program can use your Keychain. Durbar's own item (`agent-durbar Safe Storage`, which protects saved MCP secret values) is read at most once per run, and only when a server with secrets starts or you change a secret; because Durbar's builds are not signed with an Apple Developer ID, **Always Allow** for it holds until the next update (code signing, [#4](https://github.com/three-feathers/agent-durbar/issues/4), would end that). Copilot's own items (your `copilot login` and, since Durbar asks Copilot to keep them (spec 058 FR-070), the MCP servers' sign-ins) are read by the one Copilot runtime Durbar starts per run and shares across all sessions. Since [#623](https://github.com/three-feathers/agent-durbar/issues/623) the mac package keeps **GitHub's own signature** on that runtime (it used to be re-signed ad-hoc with the app), so the Keychain sees the same program as the `copilot` CLI, and a new MCP sign-in made from Durbar asks nothing (checked on the owner's Mac, 2026-10-23). **When upgrading from an older Durbar:** on the first launches you may need to press **Always Allow** for each item twice, once per launch. After that there are no prompts. On the owner's Mac with 10 servers, the first two launches asked about 25 times each and the third asked nothing. If you also use the `copilot` CLI with the same MCP sign-ins, prompts may come back after the CLI saves them; this has not been checked. If prompts keep coming back: In a Copilot chat's **MCP servers** dialog, use **Sign in again…** on a server, or **Sign in again to all**: Copilot forgets the saved sign-in and you sign in again in your browser, so the current runtime saves it anew. The server stays signed out until you finish in the browser; Cancel or the time limit leaves it signed out. It is offered only for remote servers Agent Durbar knows by their address (not built-in or local ones). Whether this ends the prompts has **not been checked on a Mac yet** ([#623](https://github.com/three-feathers/agent-durbar/issues/623)). If it doesn't, you can delete the `copilot-mcp-oauth` items in Keychain Access and sign in again. Durbar never reads or changes the keychain itself ([spec 058](../specs/058-mcp-session-controls/spec.md) FR-162..FR-164). Claude Code and Codex use their own installed programs and their own Keychain items, as in a terminal.
- **Names in packaged builds:** the display name is `Agent Durbar` (Start menu and desktop shortcuts, Add/Remove Programs, `.app`, AppImage `Name=`), while the run-time identity stays `agent-durbar` on every OS (profile folder, Keychain, WM_CLASS). `scripts/check-names.js` compares the packed app with `package.json` on every package build. On Windows a packaged build sets the AppUserModelId `io.github.three-feathers.agentdurbar` so toasts and the taskbar match the Start menu shortcut. Checked on a real Linux build (AppImage `.desktop`, packed app started on the simulator); the Windows names and AUMID and the macOS bundle names are asserted only by the *Installed app* workflow in CI, and the taskbar, toasts, Mac menu-bar title and a Linux launcher or dock were not seen on a real desktop ([#9](https://github.com/three-feathers/agent-durbar/issues/9)).
- **No debugger in packaged builds:** release builds ignore `--inspect`, `NODE_OPTIONS` and `ELECTRON_RUN_AS_NODE` (Electron fuses; `scripts/check-fuses.js` reads them from the packed binary on every package build on Linux, macOS and Windows: `pack:dir`, the `dist*` scripts, and so the packaged-check workflow and the release build) and always drop `remote-debugging-port` and `remote-debugging-pipe`, whatever the spelling. Run from source (`npm start`) to debug. Checked on the packed Linux build, including `-remote-debugging-port` with one dash (`npm run check:fuses-launch`); the fuse check itself has been run locally on Linux only, and macOS and Windows have not been tried by hand (on Windows Chromium also accepts `/` and any case, which the guard covers by removing the switches by name). The ASAR integrity fuse has no effect on Linux.
- **A chat keeps its newest 300 messages** (spec 005 FR-238): older ones leave the view to save memory, a line says how many; read scrolled up, it is not trimmed. Simulator, Linux only.
- **An agent keeps its newest 50 finished helpers and 20 failed ones** (spec 005 FR-240, FR-241): older ones leave the office, the chat and the lists, and one line says how many are not kept; running and open ones stay. Measured on the Linux simulator only; Windows and macOS were not measured.
- **VS Code's own chats are read-only.** VS Code keeps them in an undocumented store that cannot be continued from outside; Durbar shows a copy. Copilot CLI/SDK sessions *can* be resumed.
- **Caps are soft:** one model response can overshoot them, and the figures are what each harness reports. Copilot's runtime stops only before its next step, and a limit set after a resume with none is not enforced, so Durbar stops a turn itself after the call that crosses it (real checks, 2026-10-20 and 2026-11-02). Durbar learns a resumed session's earlier spending only from the runtime's first usage report, so the first message after a resume is held only when Copilot refused to reopen the session at its limit (then the limit card asks).
- **A floor that is switched off is quiet.** The agents under it keep running and can spend credits or wait for an approval; nothing stops them for you.
- **Schedules run only while Durbar is open.** A schedule's limit counts what its run uses from the moment it is sent until that turn ends (a message you send during that turn counts too). They were tested on the simulator and with fakes, not on a real session. The agent apps' own schedules are shown only for Copilot, and only while Durbar is running and the app reports them.
- **Account limits** (spec 011 FR-080): the Copilot and Codex answers were checked on real accounts on Linux (2026-11-02, T059): both reads are free and start no turn; not checked on Windows or macOS, an API-key Codex account or a signed-out one. Claude Code reports none through a free call that we know of. The figures are the provider's, can lag, and are not a bill. The 10 % warning level awaits an owner decision.
- **Session names:** the rename into Copilot, Codex and Claude Code was checked on real accounts only by another team member's agent, which ran the raw protocol and CLI calls by hand and looked at the CLI lists (Durbar's own adapters ran on fakes only), not in VS Code; Claude Code applies the name at the next message (it relies on the undocumented `CLAUDE_CODE_ENTRYPOINT` value of spec 012 FR-159 to show in `/resume`), and the VS Code Claude extension's list did not show a `-p` session at all in a real check on a Mac (untested with that value).
- **A hung Copilot runtime:** Stop and End session go on after 5 seconds (10 and 15 with a spending-limit question open, one step at a time); the limit itself stays after a Stop, so the next message waits on the limit card, and raising the limit brings the session back (`real:` Linux, one paid exhaustion, the rest with the usage figure raised inside the test: [spec 052](../specs/052-usability-pass/spec.md) FR-231; measured on 1.0.24/1.0.101; 1.0.26 has the same refusal text (`read:`), behaviour not re-run); a message or a reopened session then waits up to 30 seconds for Copilot's late answer, and says so if none comes (`real:` Linux only). Nothing restarts a runtime that stays hung: its other sessions wait on it until the app restarts.
- **MCP sign-ins (Copilot):** **Sign in** in the MCP dialog calls the Copilot runtime's `mcp.oauth.login` (marked experimental in the SDK) and was checked once on a real account (Copilot, macOS, 2026-10-23, `agent365-teams`: it worked, but the row lagged behind the runtime's status, so Durbar now re-reads the server list every 5 seconds, for at most 10 minutes, while the sign-in page is open). The re-read (whether it can start other servers on a real runtime is unknown), how long the runtime waits for you, and what happens to its waiting listener after **Cancel** are unverified, and so are other servers, Windows and Linux. Whether a sign-in you made in the Copilot CLI (`/mcp auth`) is seen by a Durbar session, and the other way round, is not verified ([spec 058](../specs/058-mcp-session-controls/spec.md) FR-068/FR-074, real check T105 pending). Keeping sign-ins (FR-070) was checked for real on 2026-10-21 on GitHub's Windows and Linux runners with a demo OAuth server on loopback (a new session in a new runtime connected with no new sign-in); not on a Mac, a Linux desktop with a keyring, or a third-party https server. On Linux without a keyring the kept sign-in is a tokens file under `~/.copilot/mcp-oauth-config/`; whether it is encrypted and its file permissions were not checked.
- **Copilot sign-in app (experimental)** ([spec 058](../specs/058-mcp-session-controls/spec.md) FR-233..FR-241, issue #1667): with the Copilot SDK 1.0.32 runtime, Durbar tells Copilot which Microsoft Entra app ID its built-in MCP sign-in uses. By default that is Visual Studio Code's public app ID (owner decision, 2026-11-13: the old runtime used it by itself), so sign-ins show as Visual Studio Code in your organization's logs; a stored Off sends none (the runtime's own failure and the CLI steps), a custom value sends your organization's app ID. The choice is in *Settings > MCP servers > Copilot sign-in app for Microsoft (experimental)*: Visual Studio Code's app (the default), Off, or Custom app with your organization's app (client) ID; each change asks first and reconnects Copilot, and a one-time notice says the default is another app's identity. A sign-in error that Microsoft refused for the app (`ENTRA_CLIENT_NOT_PREAUTHORIZED`, `AADSTS65002`, `AADSTS50011`) is worded as such on the server's row (Settings and a chat's MCP dialog), not as a sign-in to repeat; the failed-call line in the chat still uses the old words (`[KNOWN GAP]`). Copilot CLI's own app is not offered (owner decision pending). **No real sign-in was run with any of these** (tests with fakes only). Linux: the runtime says Entra accounts work only on Windows and macOS, so the setting most likely has no effect there (`read:` runtime strings, not verified). macOS: the runtime's Microsoft sign-in libraries are re-signed ad hoc with the app, which may matter to the system broker (not checked); the runtime's macOS sign-in redirect address, read from its strings only and **unverified**, is `msauth.com.msauth.unsignedapp://auth`: a Custom app needs a redirect address registered for the computer, and Durbar does not tell you this one as an instruction until the owner's Mac test confirms it (spec 058 T221). Windows: the broker's redirect address was not read. The runtime's own log files (*Open log folder*) may record the ID; Durbar does not write or mask them.
- **"/" entries ([spec 073](../specs/073-slash-suggestions/spec.md)):** checked on real apps on 2026-10-22 (3 tiny prompts): Claude Code in Durbar's sessions ignores a folder's `/command` (it reached the model as text) but runs built-ins such as `/context` itself; Copilot's `session.send` does not run a typed built-in such as `/list-dirs` (so none are listed for Copilot). Codex was read from its app-server schema only, not run. Durbar's expansion (a command's `$ARGUMENTS` and `$1`..`$9`, a skill's `SKILL.md`) is unit-tested and simulator-tested only; Claude commands' `!` shell lines and `@file` references are sent as text and never run by Durbar. Of the allow-listed Claude built-ins only `/context` was run through Durbar. Nested command folders and parent-folder skills are not listed. Codex's named `$KEY` arguments are not filled in. VS Code prompt files (2026-10-23): the Copilot CLI does not list or run them (checked at no cost on runtimes 1.0.98 and 1.0.103), so Durbar sends their text; their `mode`, `agent`, `model` and `tools` settings are shown but not applied, editor variables such as `${selection}` are sent as written (the chat says so), an expansion over 256 KB is not sent (the line goes as typed, with a note), only VS Code's default profile folder is read, and the macOS and Windows user folders are taken from VS Code's docs, not checked on those systems.
- **MCP sign-ins (Claude Code):** **Sign in** uses Claude Code's undocumented `mcp_authenticate` request, read from version 2.1.304 only and not checked on a real account (T106). Without a system keyring (common on Linux), Claude Code and Codex keep an MCP sign-in in a plain `.credentials.json` file in their own settings folder; Agent Durbar does not read or change it.
- **Sign in after a failed renewal (issue #1229, spec 058 FR-229, not checked on a real server):** when Durbar's renewal gave up on a server (the line *needs you to sign in again*), the chat's **Sign in...** button and the MCP dialog's row now offer Sign in even if Copilot still reads the server *connected* or the session is not running (it is then started, as a send does, without a message). A block counts only for a server that is on, not refused by your organization and `connected`, `failed` or `needs-auth`. If the app answers *signed in* for a server Durbar knows is failing (Claude Code has no Sign in again), the row says so and points to the terminal steps; not checked with a real Claude Code. Cancelling or abandoning a started sign-in drops Durbar's mark, so the row then offers only Sign in again until the next failed call. Built from reading the code and fake-adapter tests only; whether a real Copilot runtime reports the server soon after the session starts, and whether its *Sign in again* gives a working sign-in for an expired refresh token, are for the owner's real check.
- **Copilot SDK 1.0.32** ([spec 058](../specs/058-mcp-session-controls/spec.md) FR-242..FR-244, issue #1667, test build only until the sign-in app setting lands): the shell guard (FR-243) was checked in Read-only only (2026-11-13, Linux, one session, two prompts, 0.35 AI credits); in Ask first the model did not try the command again, so that path is not shown on a real session. Replayed `checkpoint` records (FR-242) and the 90% *Close to the spending limit* prompt (spec 011 FR-096) are tested with made-up events only. The bigger runtime (about +28 MB Linux, +40 MB Windows, +50 MB macOS with Microsoft's OneAuth and MSAL libraries, which the macOS build re-signs ad hoc like every other library) was not packaged or started on Windows or macOS for this change.
- **MCP sign-in refresh** ([spec 058](../specs/058-mcp-session-controls/spec.md) FR-204..FR-217): Durbar cannot know when a sign-in *will* expire (that is inside the token, which it never reads), only what the agent app reports after a reconnect. The apps' reconnects were probed on Linux only (2026-11-03, T176/T177), against a local test server whose refresh tokens do not rotate, with no system keyring and no real provider (Entra, Okta, GitHub): Claude Code's `mcp_reconnect` renewed an expired sign-in; Copilot's `restartServer` renewed one that still read connected but answered with an error anyway (Durbar reads the list 1.5 s later), and in a second session on the same runtime only Copilot's own **Sign in** renewed it, with no browser. Under Copilot's OS sandbox (Read-only, Ask first) a reconnect did not renew an expired sign-in, so Durbar only shows the sign-in line there; a Read-only session after a real first message was not checked (it needs a prompt). Not checked: macOS keychain prompts, Windows, a provider that rotates refresh tokens (Durbar runs one reconnect per server at a time across chats for that reason), a tool call after expiry, an elicitation during a reconnect. A message that reaches the agent app another way (remote control from a phone, spec 054) is not covered. Codex chats are not reconnected (Codex renews with its next session). The launch check of the spec is not built yet, and its 30-minute recheck was replaced by the renewal below. **Renewal after a failed call** (spec 058 FR-218..FR-222, 2026-11-05, Copilot only): when a call to a remote server fails with a sign-in error, or Copilot reports it needs a sign-in after it was connected, Durbar reconnects that server **at once**, also in the middle of a turn (it waits only for another call to the same server in that chat to end), with a *Renewed 12:40* note on the server's row. **The call that failed still failed.** If the reconnect worked, Durbar sends the agent **one short automatic message** (`The MCP server "<server>" was reconnected after a sign-in error. Please retry the step that failed.`; the name is used only when it is a plain name of letters, digits, `_ . -`, otherwise the note says "An MCP server") so it continues on its own: **that is one extra message and uses AI credits**. It is sent once per failure and not again until a call to that server has worked (if it fails again after the note, Durbar gives up and shows Sign in again, no loop), never when the reconnect failed, never with *Refresh MCP sign-ins automatically* off, never in a chat held by a spending or usage limit (the server is still renewed), never after you pressed Stop, and behind a message of yours that is being sent; your own message is never resent. There is no timer and no restart in advance, so a sign-in that expires while nobody calls the server costs nothing. Probed on Linux against a local test server with 20-second tokens, on the shipped Copilot SDK 1.0.24 (runtime 1.0.101: the runtime kept saying *connected* after expiry, every call failed for the minute watched, it never recovered by itself, and a reconnect fixed it) and on SDK 1.0.26 (runtime 1.0.103: its own retries renewed tokens but calls still failed, and a reconnect fixed them; it also sent a *needs sign-in* status the 1.0.24 runtime did not, so on 1.0.24 only a failed call triggers the renewal; registering the SDK's OAuth handler instead broke a stored sign-in at start, so it is not used). The note is queued by the app behind a running turn, so the agent reads it when the turn ends; whether a real model retries the step after it was not checked. **Checked for real (2026-11-06, release 0.1.11):** on the owner's Mac with his own Microsoft Entra servers, a failed call was renewed, the automatic note appeared in the chat and the agent continued (his report in chat; no log is kept in the repo). **Not checked**: Windows, macOS Keychain prompts (none reported), how long the session was idle, the probes' other limits (the probe used a tool-list request), several chats or sessions sharing one server (each chat's own session is reconnected, one at a time per server, in unit tests with fakes only), macOS, Windows. A remote server that needs no sign-in is also reconnected after such a failure (Durbar cannot tell without reading a token). **Check before every message** (spec 058 FR-223..FR-228, 2026-11-05, Copilot only): beside every message you send, and when a chat starts, Durbar asks each remote sign-in server that reads *connected* for its tool list (a real round-trip, no AI, no credits; the message is never held). A server that answers *unauthorized* is reconnected at once through the same path as above; a server that answers is not restarted by the check (the separate reconnect before a message after a quiet hour can still restart a connected server), and one with a successful call, or any check outcome, in the last 5 minutes is skipped. Only a clear sign-in signal counts as unauthorized (an HTTP 401, Copilot's own "OAuth challenge required", `invalid_grant`, or an Entra sign-in code); other errors do nothing. A server that does not answer within 30 seconds counts as unknown (its row says *Did not answer a check*) and nothing else happens; **that request is not cancelled in the runtime**, and no second one is sent while it is outstanding. Nothing shows in the chat while all is well, only *Reconnecting <name>…* while such a reconnect runs, and the agent gets no note from it (it never failed). The activity-log row *renewed (automatic)* (this path and the one above) is written only with **Settings > Diagnostics** on (off by default). Probed on Linux against a local test server on the shipped Copilot SDK 1.0.24 (runtime 1.0.101): repeated tool-list calls on a healthy server changed neither the session's tool set nor produced any session event, and after expiry they failed with HTTP 401 while the list still said *connected*; a real model turn (prompt cache) was not measured. Not checked: whether this check itself fired on the owner's real Entra servers (macOS, 0.1.11, 2026-11-06: only the renewal after a failed call was reported), its latency there and whether Entra answers a tool-list request the same way, macOS Keychain prompts from a reconnect, Windows.
- **Imported MCP config:** importing from `.vscode/mcp.json` is a one-time copy per folder.
- **Organization policies of the agent apps** ([spec 076](../specs/076-managed-config/spec.md) FR-206): for Claude Code and Codex only the documented machine files are read (no MDM, registry or server-managed settings; Copilot's come through its runtime). Codex's MCP server rules and its fully qualified host name are not checked. The mapping comes from the vendors' docs, fixture tests and a fake Copilot runtime, not from a real managed machine.
- **MCP servers for all folders** ([spec 069](../specs/069-mcp-global-controls/spec.md)): the three agent apps read the written entries (T060, 2026-10-22), and Claude Code and Codex pass a referenced variable's value; whether Copilot expands `${NAME}` references (Q6) is not verified (it needs a signed-in Copilot session).
- **MCP context figures** ([spec 100](../specs/100-mcp-context/spec.md)) were checked on real Copilot, Claude Code and Codex sessions on Linux (2026-11-02), not on Windows or macOS. Copilot's call is experimental and may be missing on some plans; then the size reads *not reported by Copilot*, never an estimate. Claude Code's figures are its own estimates. Codex reports none: Durbar counts the tool definitions and shows "at most", since Codex loads them on demand, and that figure never warns. Not seen on a real session: Copilot's `deferTools: auto` and a Claude Code list that is partly loaded and partly on demand.
- **The session browser is new and only tried on test pages.** Each session has its own Browser tab, checked on Linux with Durbar's built-in test pages: not on real websites, a real desktop, Windows or macOS. A click on a link in a chat opens it in that session's Browser tab (Ctrl+click, or ⌘+click on a Mac, and the link's right-click menu open it in your usual browser; *Settings > Open chat links in* changes the plain click). A link click is not yet gated by network class (private and link-local addresses) because the agent cannot drive the browser yet. There is no setting to switch the Browser tab itself off: after you accept the one-time note the tab opens when you click it, and nothing loads before that. Up to four pages stay loaded at once, across every tab of every session: background tabs are dropped first, and a dropped page is reloaded when shown (a background tab brought back has lost its Back and Forward history); memory use of many open sessions and of 10 tabs has not been measured (spec 080 T013 AC5-AC6). Page tabs have no icons (favicons), cannot be reordered, pinned or reopened after closing, and are not kept across a restart; a page's script can still open a tab without a click (within the 5-per-load and 10-tab limits); a refused page popup or new-tab request opens nothing and is not yet offered for your usual browser. Whether ⌘W in the browser bar closes a tab or the window on a Mac, and the tab keys on Windows and macOS, have not been checked (spec 080 FR-130). Downloads are cancelled for now and `prompt()` does not work in a page. A page's own dialog does not say which session it belongs to (Durbar's message does, and brings that chat forward). Once any browser view exists, two small Chromium files appear in the app's default profile and what they hold is not identified; the session's own profile writes nothing. A browser's own `title` tooltips are drawn by the system above the page.
- **Agent-app updates are new and untested on real machines.** The update check and the update button ([spec 081](../specs/081-cli-updates/spec.md)) ran on the simulator and with fake tools only, not on a real Mac or Windows PC, and read documented output shapes (winget's table with English column names, Homebrew's and `claude update`'s output), not recorded runs. Homebrew's *latest* is only as fresh as Homebrew's local data (Durbar never runs `brew update`). The Claude channel files on `downloads.claude.ai` are not a documented API, and `codex update` is undocumented and runs a script Durbar cannot check. Scoop, Chocolatey, distribution packages and bun/pnpm copies are named, not updated. No organization policy can switch the start check off yet; only your switch does. A scheduled loop that wakes while its app updates counts that pass as failed instead of holding it. The fix for "Could not check: exit 127" on a Mac (an app opened from the Dock has a short PATH, so npm could not find node; it now says npm or node was not found and what to do) is from reading the cause, not seen fixed on a real Mac. The real-machine checks of the real updaters (spec 081 T040 to T042) have not been run, and the vendor texts it recognises (Claude Code's "updates are disabled" message, winget's table, a cancelled Windows UAC prompt) are documented shapes, not recorded output.
- **The OS sandbox floor is new and only partly checked.** For Read-only and Ask first Durbar asks each agent app to run commands inside its operating-system sandbox, and the chip (*Sandboxed* / *Not sandboxed*) and its tooltip show what it got ([spec 087](../specs/087-os-sandbox-floor/spec.md)). What was really tried (one Linux session, 2026-10-25): **Claude Code in Read-only: verified on Linux only**, its sandbox refused a write in the folder. **Copilot keeps a temp folder writable:** an approved command can write in the session folder and in Copilot's own temp folder (a real check on Linux, 2026-11-04: a folder under your home was refused, one under `/tmp` was allowed). So the chip says *Sandboxed (partial)* for Copilot in Ask first. Durbar now gives Copilot's runtime a private temp folder, so the shared temp folder is no longer writable (real checks on Linux and macOS, 2026-11-04, Ask first, with Durbar starting the runtime: a write in the private folder was allowed; a folder beside it in the shared temp folder, `/tmp` and the home folder were refused; no folder was left behind; not run on Windows or in Read-only) ([#755](https://github.com/three-feathers/agent-durbar/issues/755)). Copilot sessions of the same run share it. When the system temp folder is too long for a socket path (macOS), that private folder is made under `/tmp` (`/private/tmp`) instead, so MCP servers such as Playwright can make their sockets; not run on a real Mac, and whether the macOS sandbox grant follows it there is not verified ([#1173](https://github.com/three-feathers/agent-durbar/issues/1173)). **Not checked:** macOS and Windows, the network refusal, Claude's Ask first, Codex. Also not checked: that a write deny inside an allowed folder holds on a real session (Claude Code documents it), whether Copilot's session options update applies to a session that already exists, and what Copilot does on a host it does not support. Claude Code has no OS sandbox on native Windows: the chip says *Not sandboxed* and Durbar's own checks still apply. If an app's sandbox cannot start (for example Claude Code on Linux without bubblewrap and socat), Durbar tells you and asks before running that session without it (*Continue* this once, *Always continue* only where the cause cannot be fixed, or *Change mode…*); it recognises Claude Code's failure only by the word "sandbox" in its error, any other early exit shows as a crash. In Ask first, sandboxed commands have no network: `npm install`-style commands fail there (use Allow all). An organization can set `permissions.requireOsSandbox` in the machine `policy.json` on macOS (`/Library/Application Support/AgentDurbar/managed/`) and Linux (`/etc/agent-durbar/managed/`), root-owned only. A policy folder whose file is missing or broken requires the sandbox too. If a credential folder becomes a link, or a link is repointed, while a session runs, its new target is not denied on Linux until the next launch. Copilot's sandbox is **cleared in place** when you switch to Allow all (real: 2026-10-28, Linux, CLI 1.0.98, one probe session: write and network worked after the switch and were blocked again after switching back; [spec 087](../specs/087-os-sandbox-floor/spec.md) K16); Durbar's own switch was tested on the simulator and with fakes, and the same probe gave the same result on macOS (2026-11-01, CLI 1.0.101); Windows and newer Copilot versions on Linux are not verified. Copilot's reported network capability is not a reliable sign: on that host it said unsupported, yet the network was blocked. **Restart without the sandbox** (the fallback when Copilot refuses or does not answer the switch) is built and tested on the simulator and with fakes only, not on a real session on Linux, macOS or Windows. *End session* on an idle Allow all session does not ask, and the next message starts without the kept sandbox, as after a Durbar restart.
