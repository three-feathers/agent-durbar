Architect notes · EA Summit talk

For the Shy Architect (P4, an Enterprise Architect) and the Chief Architect (P5, a Principal Enterprise Architect). Each question appears on its own slide; Vikram, Paco or Ruben asks it, and you answer in your own words, about a minute each. These are suggestions to pick from, not a script. The thread through all of them: from documents, boards, supplier briefs and gatekeeping, to owning outcomes, building with agents, specs as living knowledge, guardrails as code, and measuring learning rather than people.

The Shy Architect · Q1 — What does an architect stop doing when agents do the building?

Asked by Vikram, after "agentic experiences".

  • Stop drawing the target picture and handing it over. Start with a spec small enough that an agent can build it this week, and look at what comes back.
  • Stop being the gate a project waits at. Put the rules where the work happens: a spec template, a checklist, a CI check that fails the build.
  • Stop writing documents nobody reads. A spec in the repository is read by every agent, every time, before it writes a line.
  • Keep the judgement: which problem is worth solving, which risk is acceptable. That is the part that does not get automated.

The Chief Architect · Q1 — How do we keep governance when an agent can ship in an hour?

Asked by Paco, after "the protocol" (agents reviewing agents).

  • Governance moves from meetings to guardrails as code: the gate in CI that refuses code without a spec is a policy that runs a thousand times a day.
  • Decide what needs a human, and write it down once: money, releases, settings, access. Everything else flows.
  • Make the trail automatic. Every decision on the issue or pull request, every change reviewed: the audit is a by-product, not a project.
  • Review the system, not each change: are the checks catching the planted bugs? If yes, trust the pipeline.

The Shy Architect · Q2 — What is the first process you would let an agent own?

Asked by Ruben, after "rules the agents agreed".

  • Something repetitive, well documented and reversible: keeping an inventory or a dependency map up to date, checking standards on every change.
  • The architecture compliance check: an agent can read every pull request against the principles and comment, the same day, every time.
  • Turning meeting decisions into tickets and records, so the board stays true.
  • Start where a mistake is cheap and visible; widen the scope as the checks prove themselves.

The Chief Architect · Q2 — Where should an architect spend the time agents give back?

Asked by Ruben, after "I trust the system, not each answer".

  • With the business: understanding the problem well enough to write the first spec yourself.
  • Building: prototypes in an afternoon, so options are argued with working software, not slides.
  • On the guardrails: the shared rules, templates and checks that make every team safer at once.
  • Teaching: pairing with teams so the way of working spreads; measure what they learn, never rank who is faster.

The Shy Architect · Q3 — What skill would you hire for today?

Asked by Paco, after "where things live".

  • Writing clearly: a good spec is the new source code, for people and for agents.
  • Systems thinking with hands on the keyboard: someone who can design it and also get an agent to build a first version.
  • Judging evidence: reading a review, a test result, a log, and knowing what is proven and what is not.
  • Comb-shaped curiosity: deep in one or two areas, comfortable reaching into many.

The Chief Architect · Q3 — Which architecture document would you replace with a living spec first?

Asked by Vikram, after the outcome (git log).

  • The solution design that is approved once and never read again: make it a spec in the repository that changes with the code.
  • Architecture decision records in a slide deck: move them next to the code, dated, linked from the change that made them.
  • Standards and principles: write them so a CI check or an agent can apply them, not only a human reviewer.
  • The integration catalogue: generate it from the code and the specs, so it cannot drift.

The Shy Architect · Q4 — What would you tell an architect who is afraid of being replaced?

Asked by Paco, after "check it yourself" (the audit log).

  • The agents in this story still needed humans for direction, for risk, and for saying no. That is architecture work.
  • What goes away is the waiting and the paperwork, not the thinking.
  • The architects who build with agents will replace the ones who only draw: start small, this month.
  • Your experience becomes rules everyone's agents follow: written once, applied everywhere.

The Chief Architect · Q4 — What is one thing this room should try on Monday?

Asked by Vikram, after "it can happen in our organization too", right before the word cloud.

  • Pick one repeated task you own and have an agent build the script for it, with a test.
  • Write one page of your knowledge as Markdown in the wiki, so people and agents can find it.
  • Turn the next meeting's actions into tickets or agent tasks before you leave the room.
  • Then tell your team what you learned, in writing.
