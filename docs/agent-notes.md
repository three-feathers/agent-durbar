# Agent notes

What coding agents on this repo learned the hard way, so the next agent does not have to. The rule to keep this file up to date is in [AGENTS.md](../AGENTS.md) (*Share what you learn*); team rules live there, not here.

Each entry has the date it was learned, what happened, and how to apply it, with its evidence (`real:` = run and seen, `read:` = from code or docs, a PR or issue number). Add an entry in the PR where you learned it. Fix or delete an entry that turns out to be wrong. **Never** put secrets, tokens, personal data or chat contents here.

## Shell and process pitfalls

- **Iterate with `npm test -- --bail`** (2026-10-22, spec 008 FR-115, issue #563). It stops at the first failing suite and stops the running ones (process group on POSIX, `taskkill /T /F` on Windows), so you see the failure in seconds. It is ignored when `CI` is set. It is for the loop only: the final run before a PR, PR CI and the merge queue run everything (`npm test` without the flag), so every failure shows at once and a flake can be told from a real break.
- **`pkill -f` / `pgrep -f` match their own shell** (2026-10-20). The pattern is in the command line of the shell that runs it, so a kill can end your own command (exit 144) and leave half-done state. The `[c]har` trick is not enough when the same command line also contains the plain name (a heredoc, a comment, a later `nohup <script>`). Do the kill in its own command, select targets by a field (`ps -eo pid,args | awk '$3 ~ /name/'`), or better, keep the PIDs of what you start.
- **Hand-run `claude` loads your plugins** (2026-10-19, `real:`). A plain `claude -p ...` probe loads the user's plugins and MCP servers; a chat-channel plugin then takes over the running session's bot and dies with the probe. Always pass `--strict-mcp-config --setting-sources ""` on a hand-run `claude`. Durbar's own adapter already passes its own `--setting-sources`.
- **Electron checks are heavy.** Run at most two Electron drivers at once, under `nice -n 10`, and keep the limits in `scripts/run-tests.js` and `scripts/check-parallel.js` so the computer stays usable. Run long checks in the background.

## CI, review and merge

- **Wait until every check has settled** (2026-10-20). Some workflows only add their checks after the first set finishes, so "no pending check" right after a push can be a false green. Before merging, wait until no check is pending through a quiet period (about 90 s), and require the CodeQL check itself to have passed.
- **A review can be a plain comment** (2026-10-20, PR #389). Paco's agent posted its required change as a normal PR comment, not as a *request changes* review, and a merge helper that looked only at checks and bot comments would have merged past it. Read every comment kind (`issues/<N>/comments`, `pulls/<N>/reviews`, `pulls/<N>/comments`, and unresolved `reviewThreads`); `scripts/pr-gate.sh <N>` lists those newer than your own last reply.
- **Bot comments can outlive their alert** (2026-10-20, PR #388). GitHub moves a line comment to the newest commit while its line still exists, even after the CodeQL alert was fixed. Gate on open alerts (`code-scanning/alerts?ref=refs/pull/<N>/merge` and `/head`), not on the bot-comment count; read the comment, then check the alert's state.
- **Read the PR's own security results**, not only `main`'s alerts: `gh pr checks <N>`, the bot's line comments (`gh api repos/{owner}/{repo}/pulls/<N>/comments`), and `code-scanning/alerts?ref=refs/pull/<N>/merge&state=open`. A comment on an old commit may be stale: compare its `commit_id` with the head.
- **Values spliced into page code in drivers** (2026-10-20, CodeQL `js/bad-code-sanitization`, PRs #348, #358). `JSON.stringify(x)` inside a `ctx.js(\`...\`)` string is flagged. Use `jsLiteral` from `scripts/check-office-overlap.js` for every value put into page code.
- **Static source checks and CRLF** (2026-10-20, PR #379, Windows CI). On Windows the checkout has CRLF endings, so `src.split('\n')` leaves a `\r` and a regex anchored with `$` never matches. Split with `/\r?\n/` or `trimEnd()` each line. The same bit the site test earlier.
- **Re-approval after a push: compare patch ids** (2026-10-20). See AGENTS.md *Re-approving after a push*; `git patch-id --stable` on the PR's own `src`/`scripts` diff tells you whether the code changed.
- **Union-merging CHANGELOG and index conflicts can duplicate rows** (2026-10-20). Keeping both sides of a conflict in `CHANGELOG.md`, `specs/README.md`, `README.md` or a `tasks.md` often leaves the old and the new version of the same row. After resolving, count rows per spec (`grep -c "^| \[012\]" specs/README.md`) and per task id, and merge duplicates by hand. Since spec 025's 2026-10-22 delta most of this is gone: a fragment in `changelog.d/` replaces the CHANGELOG line, and the specs index rows are not committed (each spec's `specs-index` block holds its row). A row that an old-style PR adds to `specs/README.md` is moved into its spec with `npm run specs:index -- --import`.
- **Reviewing a masking or parsing change** (2026-10-20, PR #369). Fuzz it: plant one secret in 20 or so shapes (flags, `export`, `$env:`, JSON, cookies, connection strings, escaped JSON) inside 10 or so wrappers (`sh -c`, `cmd /c`, PowerShell `-Command`, nested shells, quoted args), and compare leaks against `main`. Time hostile inputs too, and include **one long word** (`';'.repeat(n) + 'x y'`, runs of backticks): repeating short space-separated units misses quadratic regexes. Check that the time grows linearly from 20k to 200k characters.
- **Fuzzing shell wrappers: build the args form the OS really passes** (2026-10-21, #447, T067). For `sh -c` the OS removes one quoting level, so the script arg is the decoded text; `cmd /c` and `powershell -Command` parse their own command line, so their args keep `^`, `` ` `` and `''` escapes and cmd/PowerShell join every arg after the flag. A fuzz that keeps the outer quotes in the arg reports leaks that cannot happen, and one that strips the cmd/PowerShell escapes misses real ones. Also: `redact()` and the scheme rule take a `\` in their value class, so running them on raw escaped text (`Bearer x\"`) eats the backslash and breaks the quoting; only escape-aware rules (`maskEscapedPairs`) may run before a decode. And cut a repeated unit at the same phase for both sizes in a linearity row: a cut inside an unclosed quote takes a fail-closed fast path and makes the ratio look quadratic. Evidence: `test:` `scripts/test-redact.ts` §14d.
- **`\b` does not separate `_` from a letter in token regexes** (2026-10-22, review of #532, issue #541). `_` is a word character, so `/\bghp_…/` never matches `_ghp_…_` (Markdown emphasis) or `my_ghp_…` (`snake_case`), and the token is shown in full. Start a token shape with a lookbehind for the characters that may not precede it, for example `(?<![A-Za-z0-9])`, and keep a stricter start only where linearity needs it: `redact`'s JWT shape still never starts after a letter, digit, `_` or `-` and takes the wrapping as a bounded prefix group instead (`_{0,8}(?:[A-Za-z0-9]{1,40}_{1,3}){0,4}`, kept in the output). Only dropping `_` from its lookbehind is slow on `'_eyJ'.repeat(n)` (review of #543). Do not copy the shapes: `maskTokenShapes(text, mask)` in `src/shared/redact.ts` is the one list. Test each shape in `_x_`, `__x__`, `my_x` and Markdown wrappings, and mutate the start back to `\b` to see the test fail. Evidence: `test:` `scripts/test-redact.ts` §3b and §9.
- **Claude Code's auto mode refuses agent merges** (2026-10-20, `real:`, PRs #339, #369, #377). Its safety classifier denies `gh pr merge --admin --merge` as "Merge Without Review" even with a fresh approval, green CI and a `Bash(gh pr merge *)` allow rule. It sometimes also denies a chat message that asks the human to merge. Do not retry or reword the command: tell your human the exact command, or ask them to press Merge.
- **Every push dismisses approvals, and `main` moves fast** (2026-10-20, PRs #369, #377). Each merge of `main` cost a fresh approval, and the branch was conflicting again within the hour (CHANGELOG). Ask for re-approval only once CI is green on the new head. Batch docs-only edits into one push, and point the reviewer to the patch-id check.
- **An old git rerere resolution can silently drop a rule** (2026-10-22, PR #488, `real:`). Merging main (#515) into the stack, rerere replayed a night resolution for `styles.css` that deleted the `.mode-menu` base rule (both sides had changed it). The file showed no markers. How to apply: after a merge that says "Resolved ... using previous resolution", rebuild each such file with `git merge-file -p ours base theirs` and diff it against the result before you commit; `git rerere forget <file>` (during the conflict) drops a bad one.
- **A percent-encoded byte ends in a hex digit, so `(?<![A-Za-z0-9])` refuses a token after it** (2026-10-22, review of #543, T129). In `?q=token%3Dghp_…` or `%22ghp_…%22` the char before the token is `D` or `2`, and a lookbehind that bars letters and digits leaves the token in full. The same holds for a backslash escape: the debug log (`createDebugSink`) redacts *after* `JSON.stringify`, so a token at the start of a line is `\nghp_…` there and the `n` refuses it (review of #549). *How to apply:* give a token shape a second start, `(?<=(?:%|25)[0-9A-Fa-f]{2}|\\(?:[nrtbfv]|u[0-9A-Fa-f]{4}|x[0-9A-Fa-f]{2}))`, as `START` in `src/shared/redact.ts` does for every shape. `(?:%|25)XX` covers a `%` encoded any number of times (the last escape of `%252525…3D` always follows `25`) with a fixed-width lookbehind; an unbounded `%(?:25)*` would be quadratic on `2525…`. Keep every branch fixed-width so the lookbehind is O(1) (linear: 8x the input, 8x the CPU time). Test each shape after `%3D`, `%253D`, 4 and 6 levels of `%25` (a depth limit then fails), `\n`, `\t`, `\\n`, `=`, a record through `createDebugSink`, and a mutation that drops each branch. When a redactor runs on encoded text (JSON, URL, shell), ask what each encoding puts right before a token. A start that passes at every position of a run (`2525…` passes `25XX` everywhere) makes any forward prefix in the shape run at every position: the JWT's 40-character word prefix cost 40x (221 ms per 1 MB). Start such a shape at its literal (`eyJ`) and check the prefix in a bounded lookbehind behind it (3 ms). Evidence: `test:` `scripts/test-redact.ts` §3b, §8 and §9.
- **Timing checks: measure CPU time, not wall time** (2026-10-22, spec 041 T068, Ruben's note on PR #455). *What:* `test-redact` §14c "grew too fast" failed in 2 of 2 `npm test` runs on a loaded machine and passed alone: its absolute limits read wall time (`Date.now`, `hrtime`), which grows with whatever else holds the CPU, and `npm test` runs suites in parallel. *How to apply:* time a performance or ReDoS check with `process.cpuUsage()` (user + system; see `cpuMs` in `scripts/test-redact.ts`), compare two sizes far apart (8x: linear about 8, quadratic about 64) with the minimum of a few interleaved runs, and keep the limit between the two. Prove it by mutation: a deliberately quadratic rule must still fail. *Limits:* `process.cpuUsage()` is process-wide (worker and GC threads count too), so time code in a worker inside the worker with `process.threadCpuUsage()`, that thread's own CPU time: it exists in Node 22 (`real:` v22.23.4, CI's `node-version: 22`) and 24, not in Node 20.19, so fall back to `hrtime` there (§9 of `test-redact`; an earlier version of this note wrongly said Node 22 had none, review of PR #527). CPU time does not see a blocking wait (`Atomics.wait`, a sync sleep, `execSync`, sync I/O): add a loose wall-time backstop (10x the CPU limit, as `cpuMs` does), and know that a wait shorter than the backstop still passes. Windows counts CPU time in about 15.6 ms ticks, so keep a floor on the small size (`Math.max(t, 20)`). Evidence: `test:` 10 runs in a row and 3 runs beside 4 busy-loop processes, all green (PR for T068).
- **Checking your branch against another open PR with `git merge-tree`** (2026-10-22, spec 074, `real:`). `git merge-tree --write-tree --name-only HEAD origin/<their-branch>` lists every conflict, including the ones that branch already has with `main` (an old branch conflicts on README, CHANGELOG, `specs/README.md`). Compare it with the same command from `origin/main` and look only at the difference: `diff <(git merge-tree --write-tree --name-only origin/main B | grep ^CONFLICT | sort) <(git merge-tree --write-tree --name-only HEAD B | grep ^CONFLICT | sort)`. Empty = your branch adds no conflict for them.
- **Install Electron once before you start Electrons in parallel** (2026-10-22, spec 008 FR-114, PR #546 comment by fjcabello). *What:* Electron 44 has no postinstall; the first `require('electron')` downloads and unpacks the binary. Several jobs doing that at once race on `node_modules/electron/dist`: one runs the binary while another still writes it (`ETXTBSY`, exit 126 "Text file busy", Linux CI) or reads a half-written one ("Could not find sentinel", Windows, #424). *How to apply:* any runner that fans out jobs needing Electron calls `ensureElectron()` from `scripts/ensure-electron.js` before the first job (as `run-tests.js`, `check-parallel.js` and `ui-suite.js` do); it is a no-op (0.1 s) when the binary is there. *Evidence:* `sim:` 3 parallel first runs of a binary-less copy of `node_modules/electron` failed with ETXTBSY in 2 of 3 rounds, never with the step first (5 rounds).
- **A mask-before-cut test needs a bare token** (2026-10-23, review on #511, `sim:` `shots-001-lobby.js`). *What:* `redact()`'s header rule masks everything after `Authorization: token`, even a token already cut short, so a test with that prefix still passes when the code cuts first and masks after. *Why:* only the bare token shapes (`maskTokenShapes`) need the whole token (a `ghp_` needs 36 characters after it). *How to apply:* put a bare token across the cut, assert that no piece of it is left (`ghp_`, and a run of its body), and mutation-check by swapping the order.
- **Mutation checks** catch tests that pass for the wrong reason: undo the fix (or change the wiring) by hand and see the test fail before you trust it.
- **A test that awaits a promise that never settles passes** (2026-10-21, PR #473, found by Paco's agent). Node exits with code 0 when nothing is left on the event loop, without running the rest of `main()` or printing PASS, and `run-tests.js` reports ok. A "second call is refused while the first runs" test that `await`s the second call before releasing the first hangs exactly that way once the lock is gone. Start both calls, assert on what is synchronous (calls that reached the fake), release, then `await Promise.all`; and guard the script with `process.on('exit')` that sets `process.exitCode = 1` when a `done` flag was never set (`scripts/test-mcp-session.ts`).
- **End-anchored regexes on untrusted text can be quadratic** (2026-10-21, PR #463 review, `test:` timing cases). `/\s+$/`, `/\n+$/`, `/[ \t]+$/` and a lazy `(.+?)\s*$` retry the whole run at every position when a long run of blanks or newlines is followed by other text: 100,000 spaces in a streamed `Write` took 61 s in the main process. On model output, agent args or diffs use `trimEnd()`, a greedy capture plus `trimEnd()`, or a loop from the end, and add a timing case built so the run is *not* at the end (a run at the very end matches at once and hides the bug). Test the old code in its own process with a timeout: the cases can take minutes.
- **`until` in `scripts/driver-helpers.js` never throws** (2026-10-21, PR #463). A driver that only `await until(...)`s passes even when the condition never came true; assert on its result (`assert.ok(await until(...), msg)`), and mutation-check the new step.

- **git rerere can replay a stale resolution that drops a rule** (2026-10-22, PR #462 merge of #515).
  - *What*: merging `main` into a stack branch, rerere auto-resolved `styles.css` from an older night-stack resolution and silently dropped the whole `.mode-menu{position:fixed;...}` base rule (the file had no conflict markers and was not reported as conflicted).
  - *Why*: rerere keys on the conflict text; a similar hunk from another merge got the old answer.
  - *How to apply*: after a merge with `rerere.enabled`, run `git rerere status` and, for each file rerere touched, re-create the conflict (`git checkout -m -- <file>`) or diff it against both parents before committing; never trust "0 markers" alone.
- **A contrast fallback must not touch shared surfaces** (2026-10-22, review on #500, `test:` `test:theme-tokens`).
  - *What*: resetting both sides of a failing text pair to the default theme also reset `--surface`/`--bg`, which many pairs share; over a few passes one dim colour turned a whole dark theme light, with dark ink left on the pack's own dark `--surface-2` (about 1.3:1, a pair nobody checked).
  - *How to apply*: fix only the text or accent side, minimally (mix toward white or black until the pair passes), and test a dark theme with one failing pair: it must stay dark. A list duplicated between `src/renderer` (plain JS) and `src/shared` (TS) needs an equality test, or it drifts silently (#515 added pairs to one copy).

## Simulator and drivers

- **`\s` in a driver's page-code template is just `s`** (2026-10-23, `sim:` spec 068 T021). Inside a JS template literal `\s` is an unneeded escape and becomes `s`, so `` js(`x.innerText.replace(/\s+/g,' ')`) `` removes every letter s in the page and a text check fails (or passes by luck when the words have no s). *How to apply:* write `\\s`, `\\n`, `\\d` in page code inside backticks (as the older drivers do), and print the text you tested in the assertion message. Also: a time-left check ("back in 10 min") drifts while a long driver runs; match a range, not one value.
- **The answer bar is hidden while its request card is in view** (2026-10-23, `sim:` spec 074 #587). `#answerBar` shows only when the waiting request (`#chat .note.perm:not(.settled)` with buttons) has scrolled out of view, so a short chat that waits for you has no visible bar. *How to apply:* to check "this chat waits for an answer", count the unsettled `.note.perm` cards, not `#answerBar`'s visibility; to check focus is not on an answer control, test `activeElement.closest('#answerBar,#chat .note')`.
- **A real mouse click on a desk is not `el.click()`** (2026-10-23, `sim:` spec 074 #587). The desk handler used `e.detail===0` to tell a keyboard open from a mouse one; `el.click()` from a driver has `detail` 0 and looks like the keyboard. To check mouse behaviour, send `mouseDown`/`mouseUp` with `wc.sendInputEvent` at the element's centre (`shots-074-navigator.js`, `mclick`).
- **A button in a permission note makes it a waiting request** (2026-10-23, `sim:`, spec 003 FR-097, issue #618). The answer bar (`wireAnswerBar`) and Needs you (`paintInbox`) treat any `.note.perm:not(.settled)` with a `:scope > .note-actions button` as the agent's pending card and copy its buttons, pressing the original with `src.click()` (then the bar focuses the message box). A button that opens a menu (the Read-only denial's *Switch to Ask first…*) would then open it on an off-screen anchor and lose focus. *How to apply:* when you add a button to a permission note, decide what its copies do (the bar's copy anchors the menu to itself; the inbox closes first because it is modal), and test with the card scrolled out of view (`#chat.scrollTop=0`).
- **A real drag and double-click from a driver** (2026-10-23, `sim:` Electron 44 Linux Xvfb, spec 005 FR-045, issue #592). *What:* `webContents.sendInputEvent` reaches a handle's pointer events, pointer capture included: `mouseDown` (`button: 'left', clickCount: 1`), several `mouseMove`s with `modifiers: ['leftButtonDown']`, then `mouseUp`; a move past the window edge still lands on the captured handle. A `dblclick` comes from two down/up pairs with `clickCount: 1` then `2`. *How to apply:* use real input events (not `dispatchEvent`) when a check is about dragging, so `setPointerCapture`, `preventDefault` on `pointerdown` and focus behave as for a user; `scripts/check-composer-toolbar.js` (`drag`) has the pattern.
- **Do not wait for a short animation and its end state in the same poll** (2026-10-22, `sim:`, review on #511). `shots-001-lobby` waited for `.walker.walking` (a 1 s walk) and the empty desk together; a slow Windows runner polled after the walk ended and timed out every time. How to apply: install a `MutationObserver` before you trigger the change, let it set a flag when the transient state appears, then wait for the end state and assert the flag. Mutation-check it by switching the animation off. Also take "does it animate" from the page (`matchMedia('(prefers-reduced-motion: reduce)')`), not from an env flag: a CI desktop (the Windows runner, inferred on #511) can report reduced motion by itself, and then the app correctly skips the walk.
- **`#511` in a comment is a colour to the theme-tokens ratchet** (2026-10-22, `test:`, `test:theme-tokens`). The spec 070 guard counts `#` plus 3, 4, 6 or 8 hex digits in `app.js`, comments included, so "review on #511" adds a colour literal. How to apply: write "PR 511" in renderer comments.
- **One window global per renderer script** (2026-10-21, issue #474, `sim:`). The renderer's helper files are plain scripts that publish their API as `root.DurbarX=api`; a second file with the same name silently replaces the first (here `activitytable.js` and `activity.js` were both `DurbarActivity`, so Tools > Activity threw). Node tests `require` each file directly and never see the clash. *How to apply:* give a new renderer file its own `Durbar*` name; `npm run test:globals` fails on a duplicate. A screen that no driver opens can break unseen: add a driver that opens it.
- **Timing the renderer from a driver** (2026-10-21, `sim:`, spec 001 FR-033). `app.js` is one IIFE, so a driver cannot wrap `chooseLayout` or `renderOffice` from outside. To time or inspect them, patch a **copy** of the built `dist/renderer/app.js` (rename `function chooseLayout(` to a wrapper that records `performance.now()`, and expose what you need on `window` before the final `})();`), never `src/`. Machines here are shared and loaded: run old and new builds **alternately**, several rounds, and compare medians; a single run can be 30% off.
- **What a layout costs is style, not layout** (2026-10-21, `sim:`, spec 001 FR-033). In the hidden `#probe` a trial was about 7 ms of style recalculation, 5 ms of parsing and only 1.5 ms of layout. Two cheap wins that keep every box: leave out what is inside an `<svg>` (its box never depends on its children), and register custom properties that only their own element reads as `@property --x{syntax:"*";inherits:false}`, so changing them does not restyle every descendant. `contain`, moving the probe out of flow and dropping the `:has()` rules made no difference.
- **A desk scene is only redrawn when its `data-sig` changes** (2026-10-21, `sim:`, spec 040 FR-023). The office patches the DOM by key and `morphNode` keeps a scene SVG whose signature is unchanged, so anything a scene draws must be in its signature, the active theme included (`THEME.themeIdForCache()`), or a switch leaves the old drawing. A driver that clears `#stage` before its screenshot (as `shots-themes.js` does) hides such a bug: switch through the real path (Settings) and assert on the DOM. Figures built once (walkers) need the same key.
- **Theme values: two copies, one corpus** (2026-10-21, spec 070). The renderer's `theme.js` cannot import a TS module in the page and main needs the same rules, so the typed-token grammar lives in `theme.js` and `src/shared/themetokens.ts`. Change both, then run `test:theme-tokens`: it feeds one corpus to both and fails on any difference. A new colour literal in the renderer's CSS or JS fails the same test (a ratchet per file); use a token, or lower the ratchet when you remove literals (`THEME_LITERALS_WRITE=1 npm run test:theme-tokens`). A non-colour token is set on `<html>` only when the pack gives it: an inline custom property beats `html[data-ui=...]` rules in `themes.css`.
- **`app.js` is one IIFE** (2026-10-21, spec 003 T030): `bridge`, `sim` and the helpers are not globals, so a driver's `ctx.js('bridge.x()')` reaches something else (or throws). Assert on the DOM, or move the logic into a pure function in `src/main` and unit-test it (as `resumeModeOp`).
- **`until` in `driver-helpers.js` does not throw** (2026-10-21, `sim:`, spec 058). On a timeout it prints `[waits] timed out ...` and returns `false`; the driver goes on and can print PASS. Assert what you waited for (`assert.ok(await until(...))`, or a check right after), never rely on `until` alone. Also: a renderer handler that repaints with `await load()` right after starting a bridge call through `Promise.resolve().then(...)` reads the state before the call has run (microtask order); start the call first, synchronously, then repaint.
- **A covered driver window stops drawing** (2026-10-22, `sim:`, spec 008 FR-103). Chromium backgrounds a window that another window fully covers: `document.visibilityState` turns "hidden", animation frames stop and timers slow down, so the app's `scheduleRender()` never draws. Windows CI runs 2-3 drivers on one desktop, so Windows-only "random" driver failures were this. Test runs now set `backgroundThrottling: false` and `--disable-backgrounding-occluded-windows`. How to apply: to reproduce a Windows-only driver flake on Linux, put several drivers on one display: `UI_SUITE_JOBS=4 xvfb-run -a node scripts/ui-suite.js` (without the outer `xvfb-run` each driver gets its own display and it never shows). Put `document.visibilityState` in a failure message when a page "stops" updating.
- **Reduced motion takes other code paths: test them** (2026-10-23, `sim:` + Windows runs 39907250774, 39914744147, spec 001 FR-051). The Windows runner reports reduced motion by itself, so Windows-only driver flakes can be a bug in the no-animation branch, not slowness. Here a figure coming back from the Boss was dropped without a walk and nothing drew the office (the end of a walk does), so the agent stayed "away" for about 4 s. *How to apply:* rerun a Windows-only failure on Linux with `--force-prefers-reduced-motion` (or CDP `Emulation.setEmulatedMedia` before the load: the app reads `REDUCED` once) and log the state over time; when an animation's end does work (a render, a class change), the instant branch must do it too.
- **The office desks stay in the page in list view** (2026-10-22, `sim:`, spec 052 FR-173). `#stage .desk[data-id]` and `#list .lrow[data-id]` share ids, so a page-wide `[data-id="…"]` lookup in list view finds the hidden desk. Scope lookups to `#list` or `#stage`. A Windows-only driver flake that waits correctly and still fails is worth a look in the product: here a background re-render dropped the focus. How to apply: before "fixing" a flaky focus or click check, re-render on purpose (`window.__durbarSimEmit({type:'status',...})`) and see whether the state survives; and never sweep all desks in one synchronous `js()` loop: open the agent you need with `H.openSimAgent(pick, card)` (`scripts/driver-helpers.js`), which waits for the simulator's own state, clicks that one desk and returns what it saw for the failure message.

- **A UI change makes other specs' pictures stale** (2026-10-23, owner; PRs #511, #532, #552, #554). Each PR retook only its own spec's screenshots, and the README, website gallery and landing page kept showing the old lobby, desks and top bar for days. *How to apply:* after a UI change run `npm run shots:docs` (or `-- --only <driver,...>`; `-- --list` maps files to drivers), look at every changed picture, commit them with the change. - **A DevTools command before a window's first navigation never answers** (2026-10-23, `sim:` Electron 44, Linux Xvfb, spec 001 FR-084). `webContents.debugger.attach()` works on a fresh `BrowserWindow`, but `sendCommand` (any method, even `Emulation.setTimezoneOverride`) waited forever until something had been loaded; after `loadURL('about:blank')` every command answered at once. *How to apply:* do not put a CDP call before the app's first `loadFile`; pass a value in the query and act on it in the page's first script (as `simclock.js` does), or set process-wide things (`TZ`, `--lang`) in main before `ready`.
- **Two simulator captures of the same frozen state still differ** (2026-10-23, `sim:` `shots-hero` twice with the pinned clock). Desk scenes animate, so about 3,000 px of a 1440x900 office differ between runs, all inside desk scenes. A job that compares screenshots needs a tolerance or reduced motion; do not read a small diff in desk scenes as a change.

- **`safeStorage` is keyed by the app name** (2026-10-20, `real:` Linux gnome-libsecret; `read:` Electron source for macOS Keychain). Calling `app.setName()` **before** `ready` makes a new key, so secrets saved under the old name no longer decrypt; calling it inside `whenReady` kept the old key in the test. Durbar does not call `setName` at all (PR #377): the identity stays `agent-durbar` and only the menu labels say "Agent Durbar". Do not add a `setName` call; `test-profiledir` fails if you do.
- **macOS Keychain and unsigned builds** (2026-10-21, `read:` Chromium `os_crypt_mac`, Apple Keychain docs; not seen on a Mac). Every `safeStorage` call, `isEncryptionAvailable()` included, can read the Keychain item `agent-durbar Safe Storage`, and an app the item does not trust gets a prompt. Ad-hoc signed builds (`identity: "-"`) are a new app to the Keychain after every update, so "Always Allow" does not survive an update. How to apply: never decrypt in a loop or at load; keep secrets in one blob read lazily once per run (`McpStore`, spec 019 FR-023), and test it with a counting fake codec. The Copilot runtime inside the bundle reads Copilot's own Keychain items too; those prompts are not Durbar's store. Since spec 058 FR-070 (2026-10-21, `read:` SDK `types.d.ts` `mcpOAuthTokenStorage`) Copilot sessions set `persistent`, so the runtime also writes and reads MCP OAuth sign-ins in the OS keychain: expect up to one more prompt per signed-in server on a Mac (not counted on a real Mac; since #623 the runtime keeps GitHub's signature, see the next entries). Do not "fix" those prompts by switching back to `in-memory`: that loses the sign-in at every session end (owner's Q12 B).
- **electron-builder re-signs bundled third-party binaries** (2026-10-23, issue #623, `read:` `@electron/osx-sign` 1.3.3 `sign.js`, `app-builder-lib` 26.15.3 `MacTargetHelper`, Mach-O signatures of `@github/copilot-sdk-darwin-*` 1.0.22 and `@github/copilot-darwin-arm64` 1.0.103 parsed on Linux; not run on a Mac). *What*: with `mac.identity: "-"`, osx-sign walks every Mach-O in the `.app` (also `app.asar.unpacked`) and runs `codesign --sign - --force`, replacing GitHub's Developer ID signature (team `VEKTX9H2N7`, identifier `copilot`, the same designated requirement as the `copilot` CLI) on the Copilot runtime. *Why it matters*: the keychain trusts programs by signature, so the re-signed runtime is a stranger to the items `copilot login` wrote, and its trust changes with every SDK update. *How to apply*: keep vendor-signed binaries out of signing with `mac.signIgnore` (keep all files of a hardened-runtime vendor bundle together, or library validation refuses them) and check the packed files with `scripts/check-runtime-signature.js`, which reads signatures without `codesign` (works on Linux: download the npm tarball into an empty folder and pass the files). The Copilot runtime is a native child (`copilot-runtime`), never `ELECTRON_RUN_AS_NODE`, and one per app run (spec 058 FR-161).
- **Profile folders** (PR #377): installed builds use `<appData>/agent-durbar`, `npm start` and the simulator use `<appData>/agent-durbar-dev`, and `DURBAR_USER_DATA` (dev hooks on) wins. Use `DURBAR_USER_DATA=<folder>` to run against an existing profile.

- **A `src/shared` module in the page** (2026-10-21, `real:` simulator, spec 001 FR-031). The renderer has no bundler, but a shared module with **no imports** (like `redact.ts`) can load as a plain script from `../shared/<name>.js` after `exports-shim.js` (`self.exports={}`). Keep that global: tsc's CommonJS output reads its own exported constants back as `exports.NAME` at call time, so deleting `exports` after load makes every call fail (`redact()` then returns `[redaction failed]`). `test-liveact` fails if `redact.ts` gains an import. Reuse this instead of copying masking rules into `src/renderer`.
- **Blurred desk scenes: composited SVG animations** (2026-10-23, `sim:` Linux Xvfb, review of #554). An `opacity` or `transform` CSS animation on an element inside a scene SVG runs on Chromium's compositor (`LayerTree` reasons `ActiveOpacityAnimation`, `ActiveTransformAnimation`), and whatever is drawn **over** it goes to an `Overlap` layer. When Chromium cannot merge that layer into the page (it depends on the desks around it, so a layout change elsewhere flips it), it draws it in the SVG's scaled space, blurred: the DOM, the box and every computed style stay the same, only the pixels change, so a pixel check fails "at random". *How to apply:* animate a paint property for parts that sit **under** other drawing (the halo uses `fill-opacity`), keep `opacity`/`transform` animations for parts on top (hands, wave, bars). To find it: `webContents.debugger` `LayerTree.enable` + `LayerTree.compositingReasons`, and compare the share of a scene's pixels in its own flat fills (`check:office-fill`, *sharp*).

- **Reading files a repo ships: check the real target, and never open blocking** (2026-10-23, review of #535 by Paco's agent, `test:` `test:slashcommands`).
  - *What*: a containment check against the whole folder still lets a repo ship `.claude/commands/review.md -> ../../.env` (or a link to `.git/config`, `~/.codex/auth.json`), and sending that "command" sends the secret to the model.
